# 事件泵与桥接（2026-11-18）：一张 GUI 卡堵死全公司 → 已修

## 一、现场（只读探针 `work/probe-stuck.mjs`）

- 控制面**活着**：端口 3100 HTTP 200、pid 23652 已跑 11h59m、计划任务 Ready、崩溃重启 0 条；
  server 日志除启动那几行外**再无输出** —— 静默挂起，不是崩了。
- 库里 `done 70 / cancelled 8 / todo 2`、**没有 running run**、**2 条未处理事件**：
  `state_changed`（`T-4292b0fa`，04:37:04）与 `issue_assigned`（`T-4292b0fa` → engineering，04:37:37）。
- 两张排队卡：`T-4292b0fa`（engineering，"查清外部编辑器顶部标题栏计时…"）与
  `T-53a3d15b`（doubao，`dependsOn=T-4292b0fa`，即后来新下的那单）。父卡 `T-bd1f276a`（CEO 拆活卡）已 done。

## 二、审计还原的事故链

1. 04:35:13 CEO 建 2 张卡、接依赖；
2. 04:35:31 engineering 第一次 run `R-8089d3e0` 在 GUI 第 2 步**因「前台窗口不是目标窗口」中止**
   （`gui-driver.js` 抛 `GuiError('focus')`）；
3. 04:36:59–04:41:05 董事会连点 7 次「看板手动重派」，其间 04:37:00 还被 `gate_blocked user-active`
   挡了一次（要求静置 3 秒，而当时正在浏览器里点看板）；
4. 04:37:04 又一趟 run `R-e34b8cd8` 起来，04:37:37 被强制重派按中断收账；
5. 之后队列再无进展 —— **事件泵被 04:37 那趟 run 的 adapter await 占着，整条队列堵死**。

## 三、根因（两处结构性缺陷）

1. **泵是「单趟 + await 整个 adapter」**：`handleEvent` 里 `await adapter`，GUI adapter 一次要等报告文件
   `maxMinutes: 20`（每 5 秒轮询）。一张 GUI 卡就能把**整条事件队列**堵最多 20 分钟，
   外面排队的 `state_changed` / `issue_assigned` 永远轮不到 → 新下单的任务「一提交就像宕机」。
   强制重派只是把库里那趟 run 判死，**真正在跑的 promise 掐不断**，泵也没释放。
2. **事件认领不是原子的**：`markProcessed` 是无条件 UPDATE。一旦允许多趟泵，两趟会各派一次活，
   同一张卡起两个 Run 抢同一个窗口（真机踩过）。必须先改成原子认领，才敢放开并发。

## 四、改法（结构性，不缝补）

- `src/core.js` · `markProcessed`：改成 `UPDATE … WHERE eventId=? AND processed=0` 并返回 `changes`，
  实现**原子认领**；抢不到的事件直接跳过，多趟泵不会重复处理。
- `src/engine.js` · `pump`：从单例 `pumping` 改为 `activePumps` 数组 + `pumpUnblockMs()`
  （`AICOMPANY_PUMP_UNBLOCK_MS`，默认 20000ms）。满足条件时**再开一趟泵（扇出）**：
  最老一趟已跑 ≥ 阈值、外面还有排队事件、`running < maxConcurrent`、`activePumps.length < maxConcurrent`。
  每次扇出写一条 `pump_fanout` 审计（事后能查「为什么同时有两趟泵」）。
  同一张卡仍不会并行：`wake()` 的 `runningSame` 检查照旧兜住。
- `src/server.js`：`/api/bridge/*` 路由最前面加总开关 —— `engine.config.bridge.enabled === false` 时直接
  `503 {"code":"BRIDGE_DISABLED"}`。**代码、路由、`scripts/bridge.js` / `scripts/seat.js` 全部保留不删**。
- `config/company.prod.yaml`：新增顶层 `bridge.enabled: false`（早期实验，会和 GUI 抢同一张卡）；
  `engineering` 岗位显式 `dispatch: push`（只走 GUI 直派）。
- `config/company.schema.json`：顶层补 `bridge` 属性定义（`additionalProperties:false`，仅 `enabled: boolean`），
  否则严格校验报 `$.bridge: 不允许的多余字段`。改后 `npm run doctor:prod` 全绿。
- `tests/bridge-disabled.test.js`（新增 4 条）：BD-1 桥接 503 且任务 API 照常、BD-2 打开档位仍可走（开关不是删代码）、
  BD-3 原子认领、BD-4 用 700ms 慢 adapter 验证「一趟慢活占着泵时，第二张卡照样能被推进」+ `pump_fanout` 留痕。

## 五、回归：桥接 503 把看板初始化拖黑（当场修）

- 现象：董事会打开看板只看到「初始化失败：桥接已停用…」，任务卡区整块不渲染 —— 看起来像「任务卡没了」。
  数据其实一张没少（`/api/tasks` 仍返回 80 张，`T-4292b0fa` 进行中、`T-53a3d15b` 排队中）。
- 原因：`refresh()` 用 `Promise.all` 拉 18 个接口，`/api/bridge/status` 的 503 让整个 Promise 链 reject，
  后续 `state` 赋值与全部渲染都没执行。
- 修法（两道）：
  1. `src/server.js`：桥接关死时**只挡会领活/改状态的 POST**，只读 GET（`/api/bridge/status` 等）照旧放行；
  2. `src/web/board.html`：桥接状态这一路加 `.catch(() => null)`，读不到就按「没有桥接」渲染，
     不让任何单一面板把整个看板初始化拖黑。
- 回归用例：BD-1 增加「关死时 `GET /api/bridge/status` 仍须 200 且 `bridges` 是数组」，专项仍 4/4。

- 桥接活体验证：`POST /api/bridge/checkout` → **HTTP 503**（`ServiceUnavailable`），桥接不能再领活。

## 六、运维口径

- 桥接要恢复：把 `bridge.enabled` 改回 `true` 再重启；**不恢复就别删代码**（端点清单还被契约测试引着）。
- 泵扇出阈值默认 20 秒；GUI 一次 5～20 分钟时，第二趟泵会在 20 秒后接手队列里其他事件。
- 仍然存在的天然冲突：GUI 派活要抢键鼠，而 `requireIdleSec: 3` + 前台窗口校验会在你用电脑时挡下这一趟
  （`gate_blocked user-active`）。要么等静置 3 秒让自动化先跑，要么以后给工程岗配「夜间 / 闲置时段」。
- 本次事故里 bridge 并不是元凶（`dispatchMode=inline`、`engineering` 未配 pull、无 bridge 进程在跑），
  但「桥接随时可能被意外启动并抢活」这个风险是真实的，所以按董事会要求做成了关死的开关 + 明确 503。

## 七、真机事故：开关顺手把「派活」也关了（2026-11-18 当天修）

现场原话（工程岗 CTO）：

> 桥已根据 board 决策被禁用（已确认：spawn 返回 BRIDGE_DISABLED），因此无法向 doubao 派发 ——
> 控制平面会直接派发到这个 GUI 席位。代码修复是一个文件中的单点修改（自工作限制范围内）。
> 我会自行处理……同时将非代码职责（验证、部署、汇报）保留为 CTO 工作。

链条：
1. 董事会要「工程岗只走 GUI 直派」，于是 `bridge.enabled=false`；
2. 但开关写成了「非 GET 一律 503」，把 `POST /api/bridge/spawn` 一起挡了；
3. 中层唯一的向下派活通道就是 spawn（`seat.js spawn` 也是调它），于是它**手里没有任何派活手段**；
4. 它没有罢工，而是做了一次合理推断：「派不出去 → 我自己改」——正好退化成「中层不下场」被废掉；
5. 更糟的是这个退化看起来合规（它按 ≤1 文件 ≤40 行的自工作例外走了），人只能事后从日志里发现。

性质：这是**开关粒度**问题，不是 agent 懒。开关该挡的是「领活 / 改状态」（checkout / heartbeat /
progress / complete / snapshot / renew / change-request），不该挡「治理动作」。

修法：
- `src/server.js`：把例外从单一的 `review` 扩成 `managementChannel` ——
  `POST /api/bridge/review`（交验收结论）+ `POST /api/bridge/spawn`（向下派活）都在开关外面。
  503 文案也改了，明确写出「这两条不受开关影响」，免得下一个 agent 再靠猜。
- 安全性论证：`spawn` 不 checkout、不 lease、不改别人的卡状态，只新建一张子卡；
  `engine.spawnChild` 自带三道闸（必须是本卡承接人 / 必须有 delegate 能力 / 只能派进自己子树），
  另加「有下级就不许自派」。所以放行不等于放开。
- `src/org-chart.js` · `delegationBriefing`：补一条硬话 ——
  派活被拒（5xx / `BRIDGE_DISABLED` / 409 / 连不上）先重试一次，仍失败就把**原文错误**写成 blocked 上报，
  **不要因此改成自己下场**。「派不出去」是公司的问题，不是让 CTO 顶上来的信号。
- `tests/bridge-disabled.test.js` 新增 BD-1b：桥接关死时，CTO 对下级 spawn 必须 201、子卡落库
  （`assignee` / `parentTaskId` / `assignerId=cto` / `mode=delegate` 全对），同时 checkout 仍然 503。
  这条用例就是这次事故的永久回归闸。
