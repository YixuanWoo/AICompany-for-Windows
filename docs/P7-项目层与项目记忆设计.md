## 1. 一句话设计

**公司是大脑，项目是工地**：知识、经验、规范全部存在公司文件夹内、按项目分目录；项目文件夹可以在公司以外、保持干净、只出交付物。所有 AI 在引擎的规则下共同维护——没有谁绕过引擎读写知识。

## 2. 位置约定

| 位置 | 放什么 | 谁能写 |
|---|---|---|
| 公司文件夹（`work-prod/`） | `projects/<项目>/project.yaml`（规范）、`projects/<项目>/knowledge/memory.jsonl`（记忆）、任务流水、审计、账本 | **只有引擎** |
| 项目文件夹（任意盘，可在公司外） | 只有**交付物**（翻交付文件、代码……），由引擎验收后放进 | 引擎只写这个项目**自己配置的** `rootDir`（填了就是授权） |

不选「知识放项目文件夹」的原因：项目文件夹是用户资产，不放机器文件夹进去；项目整个搬走 / 换盘 / 删除，公司记忆不丢；重装公司实例，交付物不丢。

## 3. 维护规矩（谁供料、谁落笔）

```
你     → 定规范（或让 AI 起草、你拍板）→ projects/<项目>/project.yaml
员工   → 只供料：report.draft.json 的 summary / lessons / nextHints、变更请求、踩坑说明
引擎   → 收账时自动把供料提炼成一条记忆，追加进 knowledge/memory.jsonl（schema 校验不过不入库）
         派活时自动把「规范全文 + 相关记忆摘录」拼进 brief
所有AI → 只通过 brief 读；谁也不能直接改规范、直接写记忆
```

## 4. 记忆闭环：一读一写

**写（怎么产生）**：借员工交差的 `report.draft.json` 顺路带走，字段从 2 个扩到 4 个（**新增字段全部可选、向后兼容**，不动 P0 冻结的 completion schema）：

```json
{
  "status": "success",
  "summary": "做了什么、产出是哪个文件",
  "lessons": ["踩了什么坑、怎么绕过去的"],
  "nextHints": ["下一单同类活该先做什么"]
}
```

- 引擎收到 report → 校验 schema → 补齐元数据（taskId / 项目 / 时间 / 产物路径 / 难度）→ 追加一行进 `memory.jsonl`。
- **校验不过就不入库**，只留审计——记忆宁缺毋滥，写花了不污染库。
- 员工摸不到库的结构和历史，只能影响「本次新增的一条」。

**读（怎么被用）**：派活时引擎在 brief 里注入固定段落（放在硬性要求之前）：

```
【项目规范】project.yaml 全文
【相关经验】最近 N 条同类任务的 lessons / nextHints 摘录（N 可配，默认 10）
```

最小版按「最近 N 条」取；完整版按关键词检索（第 6 步接模型后一起做）。

## 4.1 记忆分级（L1 必读 / L2 焦点 / L3 按需）—— 暂缓，2026-11-23 董事会决定

**现状（当日已核实，不是推测）**

- `buildProjectContext`（`src/projects.js:266`）只做两件事：`project.yaml` 剥注释后全文 → 【项目规范】；`memory.jsonl` 最近 `memoryLimit` 条 → 【相关经验】。两段都**无条件**嵌进提示词，不按任务筛、不分级、也不校验读没读。
- 取的是「最近 N 条」而不是「相关 N 条」：处理第 15 份也会读到第 20 份的坑。
- 实测规模：5 个项目共 69 条记忆，其中 15 条 `lessons` / `nextHints` 双空（22%），集中在 cli-exec 席位没填。

**配置里已经有分级意图，但代码零处读取**

`work-prod/projects/demo/project.yaml` 写了：

```yaml
memory:
  requireLessons: true
  focus:
    - 外部编辑器（demo-editor 进程）占着文件时不许改盘上文件
    - 编号命名与 PDF 页码对照的坑
    - 文本偏离类型（A–F）怎么判
```

全仓 grep：`requireLessons`、`memory.focus` 除 `scripts/watch.js` 一个无关的 `focus` 参数外**没有任何读取点**。所以这两项当前只是文本——会被整段贴进提示词（`buildProjectContext` 只剥注释不剥键），但引擎既不据此强制写教训，也不给焦点更高权重；焦点条目还会跟「最近 10 条」抢 `memoryLimit` 窗口。

**将来要做时的三级结构（不要自创第四级）**

| 级别 | 内容 | 注入方式 | 校验 |
|---|---|---|---|
| L1 硬规矩（必读） | `redlines` / `workflow` / `acceptance` | 无条件全量，固定最前 | 缺失即拒绝派活（`assertPromptComplete` 已有机制，加一条） |
| L2 项目焦点（必读，短） | `memory.focus`，限 3–5 条 | 无条件，限条数 | 同上 |
| L3 历史经验（按需） | `memory.jsonl` | 按任务匹配取 top 3–5，不命中就不塞 | 不校验 |

L3 第一版算法（够用即止）：把 `title + instructions + acceptance` 拼成一段，对每条记忆的 `title/summary/lessons/nextHints` 做分词命中打分，命中 ≥1 才注入，最多 5 条——比「一律喂最近 10 条」省 token 也准。

可选对账（低成本，不上读屏）：提示词里给 L1/L2 打 `[必读]` 标，完成报告 `usage` 加可选 `readConfirm: ["redlines","focus"]`；不填不判失败，只写审计，用于统计哪些席位真读了。

**为什么现在不做**

记忆体量还小（最大 demo-editor 31 条，读窗口 10–20 已能覆盖），全量注入的 token 成本可接受；分级要动 `buildProjectContext` 与 `project.yaml` 解析，属于改契约，收益要等记忆过百条才明显。

**重启条件（满足任一即立项）**

- 单项目记忆 > 60 条；
- 注入段落在提示词里占比 > 20%；
- 出现「读到别的批次/别的工序的经验导致返工」的实例。

**改动落点（做的时候一次改完，别拆散）**

`src/projects.js`（`buildProjectContext`，另加一个结构化 `project.yaml` 读取函数，现在只是读文本）、`src/gui-prompt.js`（`projectContext` 分段渲染）、`scripts/cli/doubao-cli-bridge.mjs`（同步口径）、给 `project.yaml` 加最小校验（未知键至少告警，现在 `memory:` 段完全没人校验）。

## 6. 产物路由（解释今天「交付文件落错地方」怎么解）

1. 下单**必选项目**（看板下拉 + `npm run task -- --project <名>`），不靠 CEO 猜；
2. 产物先按现有规矩落 `workRoot/tasks/<id>/output`——**校验和、产物 API、验收链路一行不改**；
3. 验收通过后，引擎把产物**复制**到**这个项目自己的文件夹**（`rootDir`，可带 `deliverSubdir` 子目录），原件留在公司任务目录留档。

### 6.1 为什么落盘位置跟着项目走，而不是另开一个「授权目录」（2026-11-16 用户纠正）

第一版设计里我另造了一个 `archiveDir` 当「授权目录」，用户当场否掉：**项目在哪儿，产物就该落哪儿，这是项目自己的属性，不该再多一层授权。**

于是改成：项目注册时写 `projects.<id>.rootDir`（项目文件夹的绝对路径）+ 可选 `deliverSubdir`（落到它下面的哪个子目录）。

| 旧（已废） | 新 |
|---|---|
| 项目 = 规范 + 记忆；`archiveDir` 另授权 | **项目 = 规范 + 记忆 + 文件夹位置（rootDir）**，一个字段说清「它在哪」 |
| 不填 `archiveDir` = 不归档，两个开关 | 填了 `rootDir` = 产物落那儿；不填 = 产物只留在公司任务目录（开发类项目就这样，源码由人集成） |
| 说法上像「引擎往外写要许可」 | 说法上就是「这个项目的交付物放哪」 |

两条仍然保留的硬规矩（与「落哪儿」无关，是安全底线）：
- **`deliverSubdir` 只能是项目文件夹下的相对子目录**：配绝对路径或带 `..` 一律配置报错，防止一条配置把产物写到项目之外；
- **干活期间产物仍在公司任务目录**，验收通过才复制进项目文件夹——废稿不该进用户的地方，且打回重做要有原件可依。

### 6.2 产物落点前移 —— 已实施（2026-11-23 晚）

上面「产物先落公司、done 后复制」这条规矩，2026-11-23 被董事会指出与原则冲突：**公司只该存任务卡数据、项目经验记忆、产物清单与校验和；项目产物的本体不该留在公司，也不该由公司当资产仓。**

实测到的三处副作用：

1. `deliverTask` 用 `listOutputFiles` 无过滤全扫 `output/`，`copyArtifacts` 整批复制。`T-d396e200` 的 `output/` 里混着一次性脚本 `build_doc15_chujiao.py`，它会被一起拷进 `文档处理项目/04-out`——项目正文目录里躺临时脚本。
2. 代码类项目更严重：`copyArtifacts` 的规则是「同名不覆盖、重名加任务号后缀」，复制回仓库会产出 `xxx-T-1a2b3c4d.md` 这类文件名，当源码不可用。
3. `work-prod` 会随任务数线性增长，且项目资产在公司目录里存一份、项目目录里存一份。

**处置（当天完成，详见《全盘审查与维护记录-20261123》§3.1）**：

- 派活时引擎把项目落点算好注入 `ctx.project.writeDir`，提示词直接指向项目目录；
  项目产物禁止进 `output/`，`output/` 只放任务卡、说明、进度、完成报告。
- 席位在 `report.draft.json` 里报 `deliverables`（绝对路径清单）；控制面逐条核验
  （绝对路径 / 落点内 / 存在非空 / checksum 自算），不再靠「output/ 里有没有文件」判完成。
- `deliver.js` 对绝对路径产物只记账（`mode: 'in-place'`），不再复制；旧 `output/...` 产物仍走复制。
- 产出心跳同时盯 `output/` 与项目落点；`deliver-copy.js` 保留相对目录结构。

尚未做、留待立项的两件：`tasks/<id>/scratch/` 作为一次性脚本的指定位置（目前靠提示词约束
「脚本放项目工作目录」）；卡 done 后 N 天 GC 掉 `output/` 的清理策略（要配保留白名单，别误删证据）。

## 8. 实施记录（P7-1 ~ P7-4，2026-11-16）

实现时按现场情况做的四个判断，都记在这儿，免得以后被当成「随便加的规矩」：

| 判断 | 为什么 |
|---|---|
| **配了项目才必选；一个项目都没配时退化为旧行为** | 老配置（含全部测试与示例配置）不能被一个开关打翻；生产 `company.prod.yaml` 配了 `demo`，于是生产必选、旧实例照旧 |
| **规范里的注释行不进提示词** | 规范文件是给人读的，注释写的是「怎么改、为什么这么定」；塞进 brief 既占篇幅，又容易和「必须遵守」混成一片 |
| **记忆在卡「真正 done」时才落，不在报告通过 schema 时落** | 报告合格但被 CEO 打回重做的那些，如果先落记忆，等于把废稿写进教科书 |
| **`cowork` / `meeting` 不要求项目** | 这两种模式不建任务卡、也不产生产物；硬要求项目只会在表单上多一个必填项而没有去处。真接项目要等协作空间也带项目时再说 |

另外两处「不做」：**交付路径不写进规范文件** `project.yaml`（会诱导执行席位往公司外写，也容易被一单活顺手改掉），只认配置里的 `rootDir`；`threads` 表没加 `project` 列，避免为一个还没有消费方的字段改表。
