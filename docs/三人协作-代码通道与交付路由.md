# 三个人怎么干活：代码通道、交付路由、上报线

> 2026-11-16 落地。回答三件事：
> ① 代码更新为什么不再跟着「项目」走；② 视频计算脚本为什么不进 git；
> ③ 豆包干完活怎么知道该交给谁 —— 这三件其实是同一个问题：**产物分级 + 路由固化**。

## 一、先说结论

**能胜任，但靠的不是「嘱咐 agent 懂事」，而是三样硬机制：**

| 机制 | 管什么 | 不靠自觉的地方 |
|---|---|---|
| 仓库台账（repos） | 代码在哪、推哪、谁审 | 没登记的仓库，`scripts/repo.js` 直接拒绝；没开 `allowPush` 推不出去 |
| 产物分级（artifactKind） | 这活算不算「要维护的代码」 | 判成受管代码却没写仓库 → 引擎打回，不给 done |
| 交付路由（handoff） | 落盘 / 送审 / 上报 | 上报的卡不再自动重试；送审的卡在收账前必须有审查结论 |

判断权在执行岗，**否决权在引擎**。这就是「执行岗位自己判断」和「不能瞎判」的平衡点。

## 二、五层概念，别再混在一起

```
董事会（人）          最终拍板：花钱、对外承诺、定方向
   │
   ├─ 项目 project     这摊事归谁、规范在哪、经验记哪、产物落哪   ← 可选
   │                   （文档处理项目没有代码，只有这一层）
   │
   ├─ 仓库 repo        代码在这台机器的哪个目录、对应哪个远端、谁审  ← 可选，与项目解耦
   │                   （开源小工具可以没有项目，只有这一层）
   │
   └─ 卡 task          一次具体的工作
         └─ 产物 artifact   分类决定它往哪走
```

**为什么仓库必须独立于项目：**

- 一个项目可能没有仓库（文档处理项目：只有交付文件）；
- 一个仓库可能没有项目（AICompany 自己、随手写的小工具）；
- 一个项目也可能有多个仓库；一个仓库换项目也不影响代码归属。

把仓库塞进项目里，会出现两种坏结果：文档处理项目被逼着填一个不存在的仓库；一次性脚本被当成「项目代码」要求维护。

## 三、代码通道：三道闸

### 闸 1 · 只能碰登记过的仓库

`config/company.prod.yaml`：

```yaml
repos:
  demo-editor:
    displayName: 外部编辑器 demo-editor
    path: D:/开源/demo-editor
    remote: demo-owner/demo-editor
    branch: master          # 写错分支，push 会被拦
    reviewer: engineering   # 谁审这个仓库
    allowPush: true         # 不开就是只读
  aicompany:
    path: D:/开源/AICompany
    remote: null            # 还没上 GitHub：只本地留档
    allowPush: false
```

所有 git 操作走同一个入口：

```bash
node scripts/repo.js list                 # 登记了哪些、各自什么状态
node scripts/repo.js status demo-editor         # 只读体检：分支/脏没脏/领先几条
node scripts/repo.js commit demo-editor --message "改了什么"
node scripts/repo.js push demo-editor
```

它做的事和**不做**的事：

- 不做 `--force`，永远不带；
- 工作区脏就拒绝 push（不推半成品状态）；
- 分支和台账不一致就拒绝（不替人判断该推哪）；
- 默认只提交已跟踪文件（`--all` 才带上新文件）。

### 闸 2 · 代码必须有人审

执行岗交活时写 `artifactKind: managed-code`（或卡上带了 `repo`），引擎就：

1. 卡进 `in_review`，不直接 done；
2. 审查人 = 仓库的 `reviewer`（默认 engineering）；
3. 审查人不是总经理时**不直调**（拉模式席位叫不醒），卡排队等它来审：

```bash
node scripts/seat.js --as engineering reviews        # 有哪些等我审
node scripts/seat.js --as engineering verdict T-xxx --pass
node scripts/seat.js --as engineering verdict T-xxx --reject --reason "少了错误处理"
```

4. 通过 → 卡 done；打回 → 卡回 in_progress 并重投给执行人（打回必须写原因）。

**审查人的职责不是「看一眼」，是「看过之后由它提交推送」**：审完在仓库里
`repo.js commit` + `repo.js push`，再把 commit 记在审查结论里。

### 闸 3 · 受管代码必须登记仓库

判成受管代码、卡上却没有 `repo` → 打回，并在审计里记 `code_repo_missing`：

> 产物被判定为受管代码，但卡上没有 repo：补上 repo 后重交；
> 如果这只是一次性计算脚本，把 artifactKind 写成 scratch-code。

代码流到没人管的地方，比没写还糟：以后没人知道它在哪个仓库、该不该维护。

## 四、视频计算代码：怎么区分「受管」和「一次性」

| 类别 | 判据 | 去向 |
|---|---|---|
| `managed-code` | 以后还会改、还有人用（产品源码、工具、配置） | 进仓库 → 审查 → 提交推送 |
| `scratch-code` | 跑完就归档（渲染一条视频的脚本、一次性清洗数据） | 落盘归档当资料，**不进 git、不建审查** |
| `document` | 文档、报告、交付文件 | 落盘 / 项目交付 |
| `data` / `media` | 表格、数据集、图片音视频 | 落盘 |

**一句话判据：这段代码以后还要不要再改？** 要 → 受管；不要 → 一次性。

渲染视频的脚本通常属于「不要」：它的价值在产出的视频，不在脚本本身。归档进项目资料即可。
唯一例外：这套脚本要反复用来渲染一系列视频 —— 那它就是工具，按受管代码走。

## 五、三档交付：豆包干完怎么判

| handoff | 什么情况 | 引擎动作 |
|---|---|---|
| `land` | 产物本身就是结果，不需要第二个人看（交付文件、报告、一次性脚本） | 直接 done + 落盘，**不叫 CEO**（省一次按量计费的 Run） |
| `review` | 改动会被以后的人接着用（代码、配置、别人的仓库） | 进 `in_review`，等审查人 |
| `escalate` | 方向不对 / 需求矛盾 / 要动权限外的东西 | 卡转 blocked，**不重试**，给上级建一张「处理升级」的卡 |

不写 handoff 时的兜底：

- 卡上有 repo 或判成受管代码 → `review`；
- 其他 → 看 `artifacts.defaultHandoff`（现在配 `ceo`，即照旧请总经理验收；改成 `land` 就默认落盘）。

## 六、谁判什么：职责矩阵

| 事 | 董事会 | CEO | 工程执行（我） | 执行（豆包） |
|---|---|---|---|---|
| 定方向、对外承诺、花钱 | ✅ | 建议 | 建议 | ❌ |
| 这活要不要开工、归哪个项目 | ✅ | ✅ | ❌ | ❌ |
| 派给谁 | — | ✅（全公司） | ✅（只给自己的下级） | ❌ |
| 技术方案怎么定 | ❌ | ❌ | ✅ | ❌ |
| 写文档 / 改稿 / 点界面 | ❌ | ❌ | 少量 | ✅ |
| 写代码 / 改配置 / 跑命令 | ❌ | ❌ | ✅ 或拆给豆包 | ❌ |
| 代码审查、提交、推送 | ❌ | ❌ | ✅ | ❌ |
| 判断产物类型与去向 | — | — | ✅ | ✅ |
| 发现偏离后往上报 | — | 接 | 接（可再上报 CEO） | ✅（报给工程） |

**汇报线（配置里写死，代码不写死人名）：**

```
董事会
  └─ 总经理 ceo
       └─ 工程执行 engineering
            └─ 执行 doubao
```

豆包遇到技术岔路 → 先找工程（我）；我判断是技术问题就自己改方案返工，
判断会改变项目方向 → 再上报 CEO。**不越级、也不许压着不报。**

## 七、三个人的典型一天

**场景 A：董事会说「给外部编辑器加个导出按钮」**

1. CEO 判断：这是代码活 → 派给 engineering，卡上写 `repo: demo-editor`；
2. 我领卡 → 定方案 → 判断实现量大 → 拆一张子卡给豆包（`seat.js spawn`），
   子卡写清「改哪个文件、产物放哪、验收怎么判」；
3. 豆包干完 → `artifactKind: managed-code` → 卡进 in_review，等着我审；
4. 我审代码 → 通过 → `repo.js commit` + `push` → 审查结论带上 commit；
5. 我交自己那张卡（方案 + 审查结论）→ CEO 验收。

**场景 B：董事会说「把这条视频渲染出来」**

1. CEO 派给 doubao，`repo` 留空；
2. 豆包写脚本、渲染、交活时写 `artifactKind: scratch-code`、`handoff: land`；
3. 引擎直接 done + 落盘，不叫 CEO、不进 git；
4. 脚本作为附件归档在任务产物里 —— 以后要复用得先「升级」成受管代码。

**场景 C：豆包做着做着发现方向不对**

1. 交活时 `status: blocked` + `handoff: escalate` + 写清卡在哪；
2. 引擎不重试，卡转 blocked，给我建一张「处理升级」的卡；
3. 我看完：要么改方案让豆包重跑，要么判定项目方向偏了 → 上报 CEO。

## 八、已知边界（别把它当万能的）

- **审查是排队等人，不是自动跑**：我是拉模式席位，没人叫就不审。看板会显示
  「等 engineering 审」，`/api/reviews` 能看到积压。想自动，得给我配一个常驻进程。
- **GitHub 推送目前只对登记 + allowPush 的仓库开放**。AICompany 自己还没建远端仓库，
  所以只做本地提交；要上线 GitHub 需要董事会点头后填 `remote`。
- **`scratch-code` 不进 git 是设计，不是漏洞**。它靠「归档 + 项目记忆」留痕；
  真要维护，就在下一次派活时改成 managed-code。
- **CEO 的验收仍然存在**：`handoff: land` 只是允许执行岗跳过它，不是取消它。
  风险高的活（对外交付、客户能看到的东西）应该写 `review`。
