# G3 · 按难度分流（2026-11-15）

> 一句话：**任务卡上多了「难度」，岗位上也多了「最多能接几档」，派活时先看接不接得住，再挑最划算的人。**
>
> 验收判据（`docs/开发清单.md` G3）：**≥3 个岗位按难度分流，且调度器能按岗位选人。**

---

## 1. 这步是干啥（和之前的区别）

以前派活只看两件事：这个岗位**有没有执行能力**、**还剩多少额度**。所有执行席位在调度器眼里是一样的，谁额度多就派给谁。

问题很直观：

- 手里有「轻客服用的小模型」和「能啃硬骨头的大模型」两个席位，写个文件名整理它也派给大模型 —— 又贵又慢；
- 反过来更糟：一道难题派给只能干简单活的席位，它接不住，最后是**跑一半失败、退回、超时**，你只看到「任务卡住了」，看不到「一开始就不该派给它」。

G3 就是把这两件事堵上：**难度写在卡上，能力上限写在岗位上，派活先比这两样。**

一个比喻：以前是把活往人多的工位随便一放；现在是活上贴了「简单/普通/困难」，工位上也写了「本人只接简单活」，调度员派活前先看一眼贴纸。

---

## 2. 现在怎么判（三条规则）

| 规则 | 做法 | 效果 |
|---|---|---|
| **① 接不住的不许派** | 席位 `maxDifficulty`（上限）低于卡的 `difficulty` → 直接从候选里筛掉 | 硬活永远不会落到只接简单活的席位 |
| **② 刚够用优先** | 能接的席位里，**上限小的排前面**（再比额度余量） | 简单活先给轻席位，不拿强席位烧琐事 |
| **③ 人不许绕过** | 你在 `direct` 里点名一个接不住的席位 → **直接报错**，并列出能接的候选 | 不悄悄换人、也不悄悄照派，当场告诉你哪儿不对 |

细节补两条：

- **上限不写＝不设限**（等价 `hard`）。所以老配置升级上来行为一模一样，不会突然派不出活。想限制就显式写 `maxDifficulty: easy`。
- **额度用完的席位不会被「够用」这个理由推上去**。否则会出现「轻席位额度见底，明明旁边常规席位有空，整单却派不出去」。

### 各条入口的行为

| 入口 | 接不住的时候 |
|---|---|
| 自动选人（`autoAssign: true`，没点名） | 候选里就没有它，直接选能接的；**一个能接的都没有** → 报错说清「没有能接 hard 的执行席位」 |
| 人点名（`direct` + `addressedTo`） | **400 报错**：`席位 worker-light 只接 ≤ easy，这张卡是 hard（困难）；能接的席位：worker-heavy(≤ hard)`。**一张卡都不建** |
| CEO 拆活（`task-create`） | CEO 点了接不住的席位 → **改派**给子树里能接的（留一条 `difficulty_reassigned` 审计）；一个接得住的都没有 → **挂起父卡 + 通知你**（留 `difficulty_blocked`），**绝不当成完成** |
| 返工换人 / 救火席位 | 换人也得接得住这张卡的难度，接不住就不选它 |
| 循环任务（rrule） | 卡可以带难度；不写按 normal |

### 难度从哪来

- 人提需求：不写就是 `normal`；看板下单可以选；写错（比如 `urgent`）**直接报错**，不悄悄当 normal。
- CEO 拆活：可以给子任务标难度；**没标就继承父卡**（硬活拆出来的子活不会自动变简单）。

## 3. 怎么用

### 配置：告诉系统每个岗位能接几档

```yaml
agents:
  - id: worker-light          # 轻席位：只干简单活
    displayName: 轻活席位
    capabilities: [execute]
    status: active
    quotaDaily: 20
    reportsTo: ceo
    maxDifficulty: easy       # ← 新增：最多接 easy
    adapter: { type: process, config: { command: ${AICOMPANY_WORKER_CMD} } }

  - id: worker-heavy
    displayName: 重活席位
    maxDifficulty: hard       # 也可以不写，不写就是 hard
    ...
```

只跑 `npm run doctor` 就会校验：写错（`maxDifficulty: High`）会在启动前被 schema 拦住，不会带着错配置跑起来。

### 下单：告诉系统这张卡多难

```bash
curl -X POST http://127.0.0.1:3100/api/requests \
  -H "Content-Type: application/json" \
  -d '{"text":"把这座桥的荷载算一遍","mode":"direct","difficulty":"hard"}'
```

返回里带 `difficulty`，方便核对。看板左边「提一条需求」也多了难度下拉，任务表多了一列「难度」，席位卡片上写着「最多接 easy」。

### 查：事后能不能追

- `GET /api/tasks` 每张卡带 `difficulty`；
- 审计里能查到 `difficulty_reassigned`（CEO 的点名被改了，从谁改到谁）和 `difficulty_blocked`（派不出去、挂起等你处理）；
- 卡住时会发一条通知 `scene: difficulty`，写清两条出路：给某个席位调高 `maxDifficulty`，或者把任务降难度。

## 5. 验收证据

```
node --test tests/p6-gov.test.js      → 11/11
node work/g3-smoke.mjs                → 7/7   （真服务、真 HTTP，不直接调内部函数）
npm test                              → 201/201（原 190，新增 11 条）
npm run doctor                        → 5/5
```

冒烟实测的 7 条：

1. `hard` 卡自动派给重活席位（不是轻/常规席位）；
2. `easy` 卡优先给轻活席位（不是重活席位）；
3. 不写难度 → `normal`，落在常规席位；
4. 硬活塞给轻席位 → **400**，文案带「只接 ≤ easy」与能接的候选，**任务数 3→3 没多卡**；
5. 任务列表带 `difficulty`；
6. 看板页面含难度选择、难度列、席位上限；
7. 分流没挡住执行：`hard` 卡照样跑到 `done`。

单元测试里另外守住：CEO 拆活子卡**继承父卡难度**、接不了会改派并留痕、**全员接不了时父卡不 done**、非法难度报错、老库补列后旧卡按 normal / 旧席位按不设限（**不追溯改判**）。

## 6. 三条边界（别误会）

1. **难度不会自己判。** 系统不猜这张卡有多难：人下单时标，或者 CEO 拆活时标。你不标就是 normal。
2. **难度不保证质量。** 它只决定「派给谁」，不决定「干得好不好」。干得好不好仍然只看磁盘产物 + 验收条件（老规矩没变）。
3. **难度不是硬隔离。** 强席位照样能接简单活（只是排在后面）；它防的是「硬活塞给弱席位」，不是「弱席位永远闲着」。

## 7. 遗留 / 下一步

- **看板还没显示「这张卡为什么被卡住」**：现在只在通知与审计里。后面做生产常驻时一起补一个「卡住原因」标签。
