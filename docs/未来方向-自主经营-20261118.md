# 未来方向 · CEO 自主经营与公司自我发展

| 项 | 内容 |
|---|---|
| 日期 | 2026-11-18 |
| 状态 | **方向文档，不是当前版本已实现的功能**；用于后续排期与设计评审 |
| 适用范围 | AICompany 的 CEO 席位、经营类循环任务、内容/自媒体业务 |
| 前置条件 | 当前版本先通过 G-P5（真实 72 小时无脏状态）；本文所有能力都排在稳定性验收之后 |
| 一句话 | 把公司从「闹钟 + 派活」升级成「有章程、有台账、有市场输入、有承诺与催更」的经营系统 |

---

## 1. 为什么现在只有「闹钟」，没有「经营」

当前系统已经具备的能力是**可靠的执行骨架**，不是经营能力：

- 能定时：`rrule` 支持 HOURLY / DAILY / WEEKLY / MONTHLY，`tasks` 支持一次性 `at`；
- 能派活：CEO 可以输出 `tasks`、`recurringSuggestion`、`projectSuggestion`；
- 能收口：任务卡有父子、验收、升级、资产归口、项目记忆；
- 能出站：`web` / `desktop` / `im` / `webhook` 四条通知通道；
- 能审批：花钱、对外承诺、开新项目有人审闸。

但这些能力解决的是「到点把活派出去」。它回答不了四个经营问题：

1. **我们做的是什么生意、服务谁、什么算好？**（没有经营章程）
2. **过去押过什么方向、投了多少、该加码还是该砍？**（没有经营台账）
3. **外面发生了什么、观众要什么？**（没有市场与受众输入）
4. **答应了什么时候交、没交怎么办？**（没有承诺与催更闭环）

所以现状不是「CEO 不会自己设任务」，而是**CEO 没有稳定的判断依据，也没有把判断变成承诺的载体**。只加一个「每天让 CEO 想新选题」的循环，只会得到重复提案和模型幻觉。

---

## 2. 目标形态：一个有章程的小公司

自主经营不是让 CEO 无限自由，而是给它一套**可审计的经营框架**：

```
经营章程（我们做什么 / 不做什么 / 什么算好）
        ↓
经营例会（每周固定开，读章程 + 台账 + 信号 + 上期结果）
        ↓
经营台账（每个方向：押注、投入、截止、止损、结果）
        ↓
内容承诺（每个项目：哪一期、什么时候交、谁负责、现在到哪一步）
        ↓
任务卡（把承诺拆成可验收的活）
        ↓
催更（到期未交，按阶梯提醒董事会 / 负责人）
```

CEO 的自由度体现在**提方向、做判断、拆目标、安排负责人**；不体现在**绕过审批对外发布、花钱、开新账号、删除资产**。

## 3. 四件必须补的基础设施

### 3.1 经营章程（Operating Charter）

一份人类可读、机器可注入的短文档，放在公司配置或项目规范里，至少回答：

- 定位：这家公司做什么、不做什么；
- 受众：服务谁、他们的真实需求是什么；
- 内容支柱：长期做哪几类内容（例如文史哲解读、工具实测、生活记录）；
- 节奏：每周/每月产出多少，什么时间发布；
- 平台与形式：视频号 / B站 / 小红书 / 公众号，横屏或竖屏，时长区间；
- 质量底线：事实核查、引用来源、版权、隐私、不碰的红线；
- 成功指标：播放、完播、涨粉、转化、复用率，哪些是主指标；
- 预算与产能：每月可花多少、可占用多少人工时间；
- 禁区：不接的广告、不碰的题材、不做的标题党。

**作用**：让 CEO 的每次提案都能回答「这符合章程第几条」。没有章程，所谓自主判断就是随机发挥。

### 3.2 经营台账（Initiative Ledger）

每个「方向 / 业务线 / 内容系列」一条记录，不允许只存在对话里。建议字段：

| 字段 | 说明 |
|---|---|
| `initiativeId` | 稳定 ID |
| `title` | 方向名，例如「文史哲读书视频」 |
| `projectId` | 落在哪个项目下（账号/业务 = 项目） |
| `bet` | 我们押的是什么判断 |
| `audience` | 服务谁 |
| `cadence` | 更新节奏 |
| `budget` | 时间 / 钱 / 算力上限 |
| `deadline` | 本轮验证截止 |
| `killCriteria` | 什么情况下砍掉或转向 |
| `status` | proposed / active / paused / killed / graduated |
| `evidence` | 支持这个判断的数据或事实 |
| `lastReviewAt` | 上次经营例会结论 |
| `outcome` | 结果与下一步 |

规则：

- 同一方向被否后 **30 天冷却**，不得换个名字重提；
- 每个方向必须有负责人、截止、止损条件，三者缺一不予立项；
- 每轮经营例会最多新增 **2 个方向**，防止摊大饼；
- 台账只追加、不改历史；状态变化留审计。

### 3.3 市场与受众信号（Signal Scout）

选题不能靠模型想象。需要一类「侦察」任务，产出**带来源、日期、样本量**的信号，而不是结论：

- 平台热榜 / 同类账号近期高互动内容；
- 评论区高频问题与反对意见；
- 搜索指数、关键词趋势；
- 自己历史内容的完播、跳出点、评论主题；
- 竞品内容的选题、结构、时长、发布节奏。

硬要求：每条信号必须带 `sourceUrl`、抓取日期、可用于判断的原话或数据。**没有来源的「我觉得」不进台账。**

### 3.4 内容承诺与催更（Commitment & Nudge）

把「要做一期视频」变成一条有日期的承诺：

| 字段 | 说明 |
|---|---|
| `commitmentId` | 稳定 ID |
| `projectId` / `initiativeId` | 属于哪个账号/方向 |
| `episodeNo` | 第几期 |
| `title` | 本期主题 |
| `stage` | 选题 / 脚本 / 素材 / 剪辑 / 发布 / 复盘 |
| `dueAt` | 该阶段承诺完成时间 |
| `owner` | 当前负责人席位 |
| `taskId` | 对应任务卡 |
| `status` | planned / in_progress / at_risk / delivered / slipped / cancelled |
| `nudgeLevel` | 0–4，已催到第几阶 |
| `nextNudgeAt` | 下次催办时间 |
| `decisionUrl` | 董事会可点开做决定的深链 |

**催更阶梯（默认，可配置）**：

| 时点 | 动作 |
|---|---|
| 截止前 7 天 | 提醒负责人：选题/脚本是否已定 |
| 截止前 3 天 | 提醒负责人 + 看板黄标 |
| 截止前 1 天 | 董事会消息区提醒，附带「延期 / 换题 / 取消」三个选项 |
| 逾期 1 天 | 自动把承诺标 `slipped`，给负责人建补救卡 |
| 逾期 3 天 | 升级给 CEO，要求做「继续 / 砍掉 / 换人」决定 |
| 逾期 7 天 | 升级董事会，进入经营例会议程 |

催更必须**可决策**：只喊「请更新」是噪音；每条催更都要带一个明确选择（延期到哪天、换哪个题、取消并说明原因）。

## 4. 视频业务的组织方式：账号是项目，一期是一张卡

建议采用：

> **一个账号 / 一条业务线 = 一个项目；一期视频 = 该项目下的一张「期」卡（可再拆子卡）。**

不建议「一期视频 = 一个新项目」。理由：

1. 账号级的定位、规范、模板、历史经验应该复用，做成项目才能沉淀；
2. 每期新建项目会让 `projects/` 目录爆炸，记忆被切碎，跨期经验无法继承；
3. 期与期之间需要比较（完播、选题、结构），同项目下才容易做趋势；
4. 只有**新账号 / 新业务线 / 新内容形态**才值得新建项目。

一期视频的卡可以拆成：选题与资料 → 脚本 → 分镜/素材 → 剪辑 → 封面标题 → 发布 → 复盘。每张子卡有验收人；父卡等子卡齐了再向发布者交总账。发布动作单独设人审闸。

## 5. 自主边界：哪些事 CEO 可以自己定，哪些必须董事会点头

| 类别 | CEO 自主 | 必须董事会审批 |
|---|---|---|
| 调研、读资料、提选题 | 可以 | — |
| 写方案、拆任务、安排内部评审 | 可以 | — |
| 新建内部任务卡 / 循环任务 | 可以 | — |
| 调整内容日历、延期内部节点 | 可以，留痕 | — |
| 对外发布内容 | — | 必须 |
| 花钱、投流、买素材/服务 | — | 必须 |
| 开新账号、对外承诺合作 | — | 必须 |
| 删除项目、删除历史产物 | — | 必须 |
| 改变经营章程 / 止损条件 | 提议 | 必须 |

另外三条硬约束：

1. 每轮经营例会最多提 2 个新方向；
2. 被否方向 30 天内不得重提；
3. 连续两期内容不达既定指标，必须做「砍 / 改 / 换人」的决定，不能无限续命。

## 6. 和现有代码的接线点

这一节只标位置，不代表现在就要改。

| 能力 | 现有基础 | 需要新增/扩展 |
|---|---|---|
| 经营例会 | `src/recurring.js`、`src/rrule.js`、`RECURRING_KINDS` | 新增 `operating` 循环类型；每轮建「经营例会」卡，读章程/台账/信号/上期结果 |
| 一次性任务 | `tasks.at`（不写 rrule 即只跑一次） | 复用，不新造定时器 |
| 台账 | 项目记忆 `projects/<id>/knowledge/memory.jsonl` | 新增 `src/ledger.js` + `ledger.jsonl`，与项目记忆分开：记忆是经验，台账是经营决策 |
| 内容承诺 | 任务卡 / 项目 | 新增 `src/commitments.js` + `commitments.jsonl`，按 `dueAt` 扫描 |
| 催更出站 | `src/channels.js` 的 `im` / `webhook` / `desktop` | 新增 `src/nudges.js`；飞书机器人 webhook、服务器微信 agent 填 `AICOMPANY_IM_WEBHOOK_URL` |
| 催更决策 | 看板消息区、审批页 | 看板新增「经营 / 内容日历」面板；催更消息带深链，点开可延期/换题/取消 |
| 市场信号 | 无 | 新增 `src/signals.js`，侦察卡产出结构化信号，入台账前校验来源与日期 |
| 审批 | `src/approvals.js` | 新增 `publish` / `spend` / `new_account` / `charter_change` 四类 kind |
| 复盘回流 | 项目记忆、任务报告 | 复盘卡把数据写回承诺与台账，形成下一轮判断输入 |

建议新增模块都保持「零依赖、纯函数优先、可注入时钟」，与现有 `recurring.js` / `projects.js` 的风格一致。

## 7. 分阶段落地

### F0 · 章程与台账（先有判断依据）

- 写 `docs/经营章程.md`（或项目级 `charter.md`），并由配置注入 CEO / 工程岗提示词；
- 新增 `src/ledger.js`，支持追加、读取、状态流转、审计；
- 看板只读展示台账；
- 验收：CEO 的提案能引用章程条款；台账能查到每条方向的责任人、截止、止损条件。

### F1 · 经营例会 + 内容承诺

- `RECURRING_KINDS` 增加 `operating`；
- 经营例会固定输出：继续 / 加码 / 砍掉 / 新提（最多 2 个）；
- 新增 `src/commitments.js`，一期视频一条承诺；
- 验收：例会卡能自动建；承诺到期能被扫描出来；无来源的提案被拒。

### F2 · 催更出站 + 看板决策

- 新增 `src/nudges.js`，按阶梯发消息；
- 飞书 / 微信走现有 `im` / `webhook`，不新造通道；
- 看板新增「内容日历」和「待决策催更」；
- 验收：承诺逾期 1 天自动出催更；消息带可点深链；延期/换题/取消能落审计。

### F3 · 市场信号侦察

- 新增侦察卡模板与 `src/signals.js`；
- 信号必须带来源、日期、样本；无来源不入台账；
- 验收：一次侦察产出 ≥N 条可追溯信号；台账里能引用信号 ID。

### F4 · 双向回复与自动经营（最后做）

- 先做「看板深链决策」，再做带签名的 `/api/nudges/:id/respond`；
- 飞书卡片 / 微信 agent 固定选项回传；
- **不建议先做自由文本聊天解析**：歧义大、审计弱、容易被误触发；
- 验收：董事会回「延期 3 天」能自动改承诺日期并留痕；乱码/未知选项不误改数据。

## 8. 成功指标

| 指标 | 目标 |
|---|---|
| 无来源提案占比 | 0（台账每条都有证据） |
| 承诺按期率 | 先测基线，再逐月提升；不追求 100%，但逾期必须可见 |
| 催更响应率 | 董事会/负责人对催更做出明确决定的比例 |
| 重复提案率 | 30 天内同名/同方向重提 = 0 |
| 对外发布合规 | 未经审批发布 = 0 |
| 经营例会产出 | 每轮至少一个明确结论（继续/砍/换），不能只写「情况正常」 |
| 内容复用率 | 同一项目内模板、结构、素材的复用次数 |

## 9. 明确不做的事

- 不做「CEO 每天自由发挥想选题」的无约束循环；
- 不做没有来源、没有日期、没有样本的「市场分析」；
- 不做自动对外发布、自动花钱、自动开账号；
- 不做一开始就解析自由文本回复；先做可审计的选项式决策；
- 不让催更变成骚扰：同一承诺同一阶只催一次，升级有上限；
- 不在 G-P5 稳定性验收前动这些经营模块；
- 不把经营台账塞进项目记忆：记忆是「怎么干活的经验」，台账是「押了什么、结果如何」，两者不能混。

## 10. 与当前稳定性工作的关系

自主经营是**建立在稳定执行之上的第二层**。如果任务卡还会卡在排队、派不出去、验收超时误判，那么「自主经营」只会把故障放大：

- 经营例会本身是一张循环卡，卡住就整周不开会；
- 催更依赖承诺扫描，扫描不到就永远不催；
- 自动复盘依赖任务收口，收口错了台账就是假账。

所以顺序必须是：

1. 先完成 G-P5（真实 72 小时无脏状态）；
2. 再把本文 F0–F1 做成可验收的小步；
3. 最后才谈「公司自己找事做、自己催更」。

本文落地前，不应把「自主经营」写进任何已验收能力的承诺里。

## 11. 未来优化项：一条指令跨项目（项目按卡归属）

**现状（2026-11-20 实测确认，不是猜测）**：董事会一条指令进来，CEO 拆出的这一批子卡**只能共用一个项目**。

```js
// src/engine.js · decompose
let childProject = task.project ?? null;
const wantedProject = requested.find((c) => c.project)?.project ?? result.project;
if (wantedProject) childProject = assertProject({ ... requested: wantedProject }).project;
...
for (const spec of specs) buildCard({ ...spec, project: childProject, ... });
```

取的是**第一个**子卡的项目，整批共用。后果不是「标签难看」，而是三件硬冲突：

1. **规范注入错**：示例项目那张卡会收到外部编辑器的「只改 `D:\开源\demo-editor`，不得碰 `<项目根>`」，而它要改的正是 `<项目根>` → 执行岗原地卡住或违规。
2. **落盘错位**：产物按项目 `rootDir` + `deliverSubdir` 落。外部编辑器没配 `rootDir`，第十份文件落不进 `04-out`。
3. **阻断与经验错**：`deliverBlockers: ["demo-editor*"]`、项目记忆都按项目注入，混了就对不上；`project.yaml` 的 rules 互相打架。

**卡间依赖解决不了这件事**：`after` 只能排序，`project` 决定归属；一批一个值 → 一单跨项目必然有一张卡归属错。

**当前的做法**：一个项目一单，用发布时间控顺序（A 验收通过再发 B）。两单可以连续下，但两单之间没有自动依赖，先后只能人控。

**未来要做成什么样**（这才是「像真公司」的形态：董事会只给方向，公司自己拆任务、分项目、执行、汇报）：

- 子卡的 `project` **逐卡校验、逐卡生效**；不写才继承父卡。
- 父卡允许 `project = null`（混合项目），收束时按子卡项目分组汇总，总汇报按项目分节，不混成一份。
- 看板卡片显示真实项目归属；混合项目父卡打「跨项目」标记，别让人误以为一张单只涉一个项目。
- 项目规范注入按**子卡自己的 project** 走；父卡的规范只在父卡自己动手时注入。
- 校验规则沿用：`assertProject` 只允许「已有且配了规范」的项目；写错整轮回执，不许静默当没写。

**验收标准（做完了怎么算过）**：

- 一条「改外部编辑器预览 + 把第十份转批注」的指令，CEO 一轮拆出 2 张卡，分别落在 `demo-editor` 与 `demo`；两张卡收到的项目规范各自正确。
- 两张卡的产物分别落到各自 `rootDir` / `deliverSubdir`；`deliverBlockers` 只对对应项目的卡生效。
- 父卡收束的总汇报按项目分节，能看出「哪个项目干成了什么」。
- 回归：现有「一批一项目」的用例全部保持通过（不能为了跨项目把老路径改坏）。

**成本与风险（为什么现在不动）**：

- 动的是 decompose 的核心路径，牵父卡收束、看板、记忆、审计四层，属于结构性改动而非补丁；
- 当前唯一执行席位是串行的，一次只能干一件，跨项目并行本来也拿不到收益；
