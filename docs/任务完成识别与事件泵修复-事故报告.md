# 事故报告：干完了却一直显示“干活中”

> 事故卡：`T-af72158d`（接管外部编辑器仓库并出基线体检报告）
> 时间：2026-11-16 17:43 派活 → 18:02 才收单（本应 17:52 收）
> 影响：单卡白等 10 分钟；后面 3 张卡 + 2 张验收单全被堵住，链路看起来像卡死

## 一、这步到底是咋回事（大白话）

豆包工作干完了活，报告也写好了，但控制面（引擎）没听见“我干完了”这句话，于是一直以为它还在干。

## 二、为什么会这样（三个叠加的毛病）

### 毛 病 1：找产物只看了“门口”，没进屋

豆包把报告放在 `output/docs/reports/` 这个“里屋”，而控制面判断“有没有产出东西”时只看了 `output/` 这一层“门口”，看见的是个文件夹，就认定“空手而归”。

结果：豆包明明交了草稿报告，控制面却认为“还没写东西”，继续傻等。

### 毛病 2：报信的人半路倒了，没人知道

控制面内部有一条“流水线”（事件泵），一条一条处理“该派活了 / 该验收了”这类通知。

17:43 它开始跑第一张卡，被豆包的 19 分钟执行占住；18:02 收完单接着往下走，处理下一个通知时**出了个错，流水线直接断掉**。而触发它的地方写的是“出错就当没发生”（`.catch(() => {})`），所以：**没人重试、没人报警，队列里的事件就那么排队排到天荒地老。**

### 毛病 3：本该救场的心跳，被自己堵死了

每分钟有一次“巡检”，专门把躺着的卡重新投出去。但它有条规则：**“这张卡还有待处理的派活通知，就跳过”**。

于是死锁：流水线死了 → 通知永远待处理 → 巡检永远跳过 → 流水线更不会被拉起来。

### 附加毛病：豆包把草稿写错了地方

第二张卡（`T-3ff55213`）里，豆包把草稿写进了 `output/report.draft.json`，而协议要求放在任务目录。它自己在经验里解释了原因：任务说“产物只能进 output”，它就把草稿也当产物塞进去了——**这是提示词的锅**，两条规矩打架，它选了硬的那条。

## 三、怎么修的

| 修哪里 | 怎么修 | 为什么这样修 |
|---|---|---|
| 找产物只认门口 | `hasNonEmptyFile` 改成**递归**进子目录找 | 产物按子目录组织是常态，只看顶层必然误判 |
| 流水线半路断 | 每个事件单独 try/catch，出错记审计 `pump_step_failed` 后**继续处理后面的** | 一个坏事件不该拖死整条队列；异常必须留痕，不能再静默 |
| 心跳被堵死 | 巡检只要发现**队列里有待处理事件**就先泵一次 | 打破“死泵 ↔ 永远待处理”的死锁 |
| 草稿写错位置 | ① 提示词加粗写明“草稿必须放任务目录，绝不进 output”；② 控制面兜底读 `output/report.draft.json` | 先教对人，再兜住错；两边都做才不会因为一句话的歧义卡单 |

三条回归测试把这两次事故钉住了（`tests/p3.test.js`），全量 **284/284 通过**。

## 四、怎么把卡住的链救回来的（没破坏任何东西）

1. **不重启**（重启会掐断正在跑的豆包），直接用控制面自己的补全逻辑，把草稿补成正式报告 `completion.json`——这本就是“超时后”它自己要走的路径，只是提前执行；
2. 流水线几秒内收单：17:43 的卡 **18:02 转 success**，进待验收；
3. 流水线继续跑，派了第二张卡；第二张卡草稿写错位置，把草稿复制回正位，**18:10 收单**；
4. 全程没有改任务内容、没有重派、没有丢产物。
