# 豆包 CLI 接入实测与 AICompany 优化总方案

- 日期：2026-11-22
- 作者：MainAgent（只读排查 + 实测）
- 范围：仅文档与方案，不含任何代码改动
- 前置：本文件记录时，生产环境仍在跑任务，未改动 `src/`、`config/`、数据库

---

## 一、结论先行

1. **豆包 CLI 可用，但有硬前提：必须给它一个伪终端（PTY）。**
   无 TTY（标准输入输出被管道重定向、由服务/计划任务直接 spawn）时，CLI 会进入"非交互待授权"分支，每 10 秒查一次派发授权，既不执行也不报错，表现为静默挂起。
2. **`-p` 非交互模式 + `--json` 输出已经跑通，可直接作为机器契约。**
   成功行形如：
   ```json
   {"type":"result","subtype":"success","is_error":false,"session_id":"<REDACTED>",
    "result":{"type":"text","content":"OK"},"tool_calls":[],"tool_calls_truncated":false}
   ```
3. **这改变了此前"CLI 待授权验证、暂不进 P0"的判断。**
   现在 CLI 席位可以立项，接入层用 `node-pty`（Windows 走 ConPTY），不再走 `child_process` 管道。
4. **paperclip 的监控思路可以借鉴，但只能借鉴"骨架"，不能照抄"进程判活"。**
   paperclip 面对的是本地 CLI harness（有子进程、有工具调用流）；我们的痛点是 GUI 黑盒（没有子进程语义、只有窗口）。判活的落点必须换成"产物增量"，否则照抄只会得到第二个假心跳。

### 2.2 对照实验（同一命令、同一登录态，只差 TTY）

| 调用方式 | 结果 | 耗时 | 日志特征 |
| --- | --- | --- | --- |
| 管道式（PowerShell 捕获 stdout，无 TTY） | 不执行，静默挂起 | >10 分钟 | 每 10 秒一条 `cli_dispatch_authorization stage=query status=200 code=0`，连续 40+ 次 |
| `winpty` 包裹（有 PTY） | 正常执行并返回 | 16.7 秒 | `cli_task_started` → `sandbox_prepared` → `im_stream_*` → `SSE_REPLY_END` → `cli_task_finished` |

**结论：不是账号授权、不是网络、不是本地存储、不是沙箱插件**，是 CLI 检测到"当前没有终端"后走了另一条路径。

### 2.3 已验证可用的调用

```powershell
# 伪终端包裹；当前机器用 Git 自带 winpty 即可
& 'C:\Program Files\Git\usr\bin\winpty.exe' -Xallow-non-tty -Xplain `
    node 'D:\npm-global\node_modules\@bytedance\doubao-cli\scripts\run.cjs' `
    -p "只回复 OK" --json --effort low
```

实测输出（关键行，其余为 `[cli-chat]` 日志）：

```json
{"type":"result","subtype":"success","is_error":false,"session_id":"<REDACTED>",
 "result":{"type":"text","content":"OK"},"tool_calls":[]}
```

同时可见内部生命周期事件：`cli_task_started`、`cli_device_ready`、`sandbox_prepared`（`scope=agent`）、`im_task_started`、`im_stream_first_event`、`SSE_REPLY_END ×3`、`im_task_finished`、`cli_task_finished(code=ok, duration≈11.6s)`。

### 2.4 已知坑（务必写进接入手册）

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 无 TTY | 静默挂起，只轮询授权 | 必须用 PTY 启动（`node-pty` / `pywinpty` / `conpty`） |
| `-C <dir>` 在 `-p` 后 | `invalid_arguments: 无法识别参数 -C`，退出码 2 | 2.36.2 帮助与实现不一致；用进程工作目录（`cwd`）代替 |
| `headless` 子命令 | `无法识别参数 headless` | 该构建没有 headless REST 接口；不要按文档新版写法接 |
| 退出码 3 | 任务实际已完成，但进程以 3 退出 | 是 `winpty` 收尾断言（`cols > 0 && rows > 0`），不是 CLI 错误；用 `node-pty` 设置 `cols=120/rows=30` 可消除 |
| 日志混流 | `[cli-chat]` 日志与 `{"type":"result"}` 都在 stdout | 解析时按行匹配 `"type":"result"`，忽略其余行 |
| 编码噪声 | `IDNToASCII failed to open UTS46 data` | 无害，可忽略 |

### 2.5 尚未验证（不要写成"已支持"）

- `--permission-mode ask_always | ask_risky | always_allow`：文档列出，未在 PTY 下逐一实测。
- `--dangerously-bypass-approvals-and-sandbox`：此前在无 TTY 下测过，卡住原因同 2.2；PTY 下未复测。
- `--resume <session-id>`：文档支持，未实测续会话后是否复用同一 conversation。
- `--service-start`（后台服务、跨设备派发）：未实测。
- 长任务（>10 分钟）下的稳定性与心跳表现：未实测。

## 三、优化总方案

### 3.0 病灶回顾（为什么需要这些改动）

| 现象 | 真因 |
| --- | --- |
| 离开电脑就不派活，回来才动 | 两个席位都是 GUI 型，必须找到"可见窗口"；窗口进托盘后 `IsWindowVisible=false`，adapter 抛 focus 错误 → `deferred` → 退回 todo → 每 2 分钟重投 → 无限循环。`run_params.locked` 197 次派发里从未为 true，锁屏闸形同虚设 |
| 同一任务被重复派 | 补审循环只判 `in_review + 无 running + 无排队事件`，不认识 `assetAck=pending`（等归口），把"等人工"误判成"事件被吞"，反复补审并重派 |
| 干完系统读不到 | 60 分钟判 `no_draft` 时，agent 其实早已完成（第二趟 3 分钟交付）；首趟零产物，判定只认磁盘文件，无中间证据 |
| 卡住却显示在跑 | `run-heartbeat.json` 由 adapter 轮询写，只证明"adapter 还活着"，不证明"agent 在产出"；看门狗据此 10 分钟内不重派 |

### 3.1 P0（止血，不改架构，1～2 天）

| 编号 | 改动 | 落点 | 验收 |
| --- | --- | --- | --- |
| P0-1 | 补审白名单：`in_review` 且存在 `assetAck=pending` 或 `waitingHuman` 标记时，跳过补审 | `src/engine.js` 补审循环（`review_stuck` 判定处） | 归口等待期间不再产生 `review_requeued`；审计里 5 次连续补审归零 |
| P0-2 | 新增 `waitingHuman` 状态：卡需要人动作时显式置位，不占 run、不计重派、不上看板"卡住" | `src/enums.js`、`src/engine.js`、看板模板 | 归口卡停在 `waitingHuman`，解除后一键恢复 `todo` |
| P0-3 | GUI 席位窗口自愈：`activate` 找不到可见窗口时，先按席位命令 `-Launch` 拉起进程，再重试激活 | `scripts/win/kb.ps1`（`激活` 分支）、`config/company.prod.yaml`（doubao 席位补 `-Launch`） | 窗口进托盘后 30 秒内自动恢复可见，`deferred` 不再连续出现 |

| P0-4 | 汇报纪律写进提示词：`changeRequestHint` 从"方向不对/范围要改"扩到"任何需要人配合、确认、给信息、给权限的事"，并明写"会话窗口没人值守，不要在那里提问；问了也不会有人答" | `src/gui-prompt.js:114-115`（两个槽位文案） | 新派单的 brief 里能看到这三句；一周内 `awaiting_decision` 由窗口提问导致的 0 次 |

> 注：P0-3 与"托盘化不修改、用户自己放出 agent"不冲突——它只在窗口确实消失时兜底，不改变用户手动操作习惯。

### 3.2 P1（判活与可观测，3～4 天）

| 编号 | 改动 | 落点 | 验收 |
| --- | --- | --- | --- |
| P1-1 | 三源 vitals：`run-vitals.json` 记录①任务目录产物增量（文件数/mtime 最大时间/size 总和）②窗口文本增量（UIA 读可见文本长度与哈希）③进程 CPU 时间增量 | 新增 `src/run-vitals.js`；`gui-adapter.js` 轮询时采样；`engine.js` 看门狗读取 | 空转 run 的 vitals 三源均不增长，10 分钟内被判 `no_progress` 并重派；正常 run 至少一源持续增长 |
| P1-2 | 心跳语义拆分：`adapter-heartbeat`（证明适配器活）与 `progress-heartbeat`（证明有产出）分文件、分用途 | `gui-adapter.js` `pollForReport` 写文件处；`engine.js` `evidenceWatch` | 看门狗只认 `progress-heartbeat`；`stall_wait_heartbeat` 不再掩盖空转 |
| P1-3 | 结构化 run 记录：每次 run 落 `run.json`（runId、taskId、seat、via、pid、startedAt、endedAt、exitReason、duration、attempt、sessionId、产物摘要） | 新增 `src/run-record.js`；各 adapter 结束时调用 | 任意一次 run 可在不翻日志的情况下还原全过程；审计与 run.json 可对账 |
| P1-4 | 统一 lease：`lease.json`（{runId, taskId, owner, ttlSec, renewedAt, renewalCount}），续租只能靠"产物增量"换取；到期自动回收 | 新增 `src/lease.js`；`engine.js` 派发前 acquire、结束 release | 无产出 run 最长占用 ≤ TTL（建议 15 分钟）；有产出可续租至 `maxRunHours` |

| P1-5 | 沉默检测 → 代挂起：vitals 三源连续 10 分钟不动、且无 `change-requests/`、无 `report.draft.json` 时，控制面代建一条 `kind=clarify / severity=needsDecision` 变更请求，把卡转入 `awaiting_decision`，附最新截图与窗口标题，并推送董事会 | 新增分支在 `src/engine.js` 看门狗内，复用 `submitChangeRequest`（engine.js:817 起） | 窗口提问这类隐性等待被显性化：不再耗到 60 分钟，10 分钟内出现在"待决策"里 |

### 3.3 P2（生命周期与防重，5～7 天）

| 编号 | 改动 | 落点 | 验收 |
| --- | --- | --- | --- |
| P2-1 | 派发幂等键：同一 `taskId + attempt` 在 lease 未释放前禁止二次派发；手动"重派"必须先显式中断旧 run 并记录原因 | `engine.js` 派发入口；看板重派接口 | 连续两次点击重派只产生一个 run；`run_interrupted_by_redispatch` 必带操作人与时间 |
| P2-2 | orphan 回收：按"持有 lease 的 pid 是否存活"判僵尸，pid 不存在立即回收（不等 TTL） | `src/lease.js` + 启动时 reconcile | 控制面重启后 1 分钟内清空僵尸 lease，不再出现"锁死到超时" |
| P2-3 | 60 分钟硬超时改"软超时 + 强制取证"：到 60 分钟先要求交 `partial.md`（进度+已做+未做+阻塞点），交了就续租，交不出才判失败 | `gui-adapter.js` `effectiveMaxMinutes` 分支 | 长任务不再"一刀切失败"；失败 run 必有 `partial.md` 或明确 `no_draft` 证据 |
| P2-4 | 提示词契约强制 `blocked`：brief 模板要求"遇到需人工动作，写 `blocked.json`（reason、需要谁做什么），然后停"；adapter 检测到 `blocked.json` 直接进 `waitingHuman` | `src/core.js` brief 模板；adapter 结束判定 | 归口类任务不再空转 60 分钟；blocked 原因可在看板直接看到 |

### 3.4 P3（架构演进：cli 席位，CLI 已可用后立项）

| 编号 | 改动 | 落点 | 验收 |
| --- | --- | --- | --- |
| P3-1 | 新增 `cli` 席位类型：`node-pty` 启动 `doubao -p "<brief>" --json`，`cwd`=任务工作目录，`cols=120 rows=30` | `src/cli-adapter.js`（新增）；`config` 席位定义 | 单次任务 30 秒内出 `{"type":"result"}`；无窗口依赖，锁屏/托盘/最小化均不影响 |
| P3-2 | run 表增列：`pid`、`sessionId`、`exitCode`、`stdoutTail` | 迁移脚本 + `src/*db*` | 任一次 cli run 可凭 pid/sessionId 追溯 |
| P3-3 | 会话复用：同 task 的连续 attempt 用 `--resume <sessionId>`，避免每次冷启动重建上下文 | `cli-adapter.js` | 第二趟耗时显著低于首趟；上下文不丢 |
| P3-4 | 灰度迁移：先迁"非界面依赖"任务（写文档、算数据、整理报告），GUI 席位保留给必须点界面的活 | `config/company.prod.yaml` 路由规则 | 一周内 GUI 席位占比下降，`deferred` 归零 |
| P3-5 | 长任务探针：CLI 侧边轮询 `doubao --list`/`auth status` 与 stdout 行增量，作为 P1-1 的第三源补充 | `cli-adapter.js` | 长任务 >10 分钟仍能判活 |

### 3.5 不做 / 暂缓

- **不做**托盘化改造（用户明确接受手动放出 agent，P0-3 只做兜底拉起）。
- **暂缓** `--dangerously-bypass-approvals-and-sandbox` 常态化：权限放宽应绑定席位与任务类型，不做全局默认。
- **暂缓** `--service-start` 跨设备派发：未实测，且会与"单机单席位"模型冲突。
- **暂缓** 项目记忆分级（L1 必读 / L2 焦点 / L3 按需）：记忆体量尚小，全量注入够用；现状核实、方案与重启条件见 `docs/P7-项目层与项目记忆设计.md` §4.1（2026-11-23 决定）。
- **未决** 产物落点前移（产物写项目目录、公司只留清单与校验和）：方向已认可，但改的是验收证据的根，等董事会点头后再动；口径见 `docs/P7-项目层与项目记忆设计.md` §6。

## 四、paperclip 可借鉴清单

对照原则：只借"骨架"，判活方式必须换成本地现实（GUI 黑盒 / CLI 可观测）。

| # | paperclip 机制 | 它的做法 | AICompany 可借鉴的 | 不能照抄的原因 / 本地化改法 |
| --- | --- | --- | --- | --- |
| 1 | DB-backed wake queue + coalescing | 派发请求写库，同一任务的重复唤醒合并成一次 | P2-1 幂等键直接借这个思路：以 `taskId` 为 key 合并重复派发 | 我们已有 SQLite，可直接在 `dispatch` 表加唯一约束，不必引入队列服务 |
| 2 | 原子 checkout + execution lock | 取任务时用事务把状态从 queued 改 running，防双取 | P2-1 落地形式：`UPDATE ... WHERE status='todo'` 成功才算抢到 | 同左，纯 SQL 即可 |
| 3 | 短生命周期 run token | 每次 run 发一个短期凭证，过期即失效 | P1-4 lease 借鉴其"短 TTL + 续租"，凭证换成 `lease.json` | 我们是单机，不需要 JWT，文件 + 时间戳足够 |
| 4 | active-run-watchdog 按 OS 子进程存活判 orphan | 拿 pid，进程没了立刻回收 | P2-2 全盘借用：lease 里记 pid，pid 消失即回收 | **GUI 席位没有"子进程"语义**（窗口属于桌面端进程），只能对 cli 席位用 pid 判定；GUI 仍靠 TTL |
| 5 | 5 分钟 reaper 兜底僵尸锁 | 定时扫过期锁并清理 | P2-2 的兜底分支 | 同左 |
| 6 | adapter 契约极薄（收心跳 → 干活 → 回报） | adapter 只做三件事，不掺业务 | P3-1 `cli-adapter` 照此设计：spawn → 解析 result 行 → 写 report/completion | 同左 |
| 7 | 每次 run 结构化日志 + 成本事件 | run 级 JSON 日志、token 成本、session 状态 | P1-3 `run.json` | 我们的成本在服务端计费，本地只记 `usage` 快照（若 `--json` 有返回则记，无则留空，不臆造） |
| 8 | full tool-call tracing | 记录每次工具调用及参数 | P1-1 vitals 的"产物增量"就是本地等价物；cli 席位可额外抓 `tool_calls` 字段 | **挡不住只输出文本的模型**：所以 vitals 必须含"文件是否真的写了"这一条，不能只看 tool_calls |
| 9 | 会话跨 heartbeat 复用（Claude Code session id） | 同一会话不重建，省上下文成本 | P3-3 `--resume` 复用 `session_id` | 已实测 `--json` 返回 `session_id`（conversation id），具备条件 |
| 10 | 预算在 run 之间生效 | 每次 run 前检查剩余预算 | 只在"派发前"做额度检查，不在 run 中打断 | 这是 paperclip 自身的已知局限（长 run 仍可能超），我们不要假装能解决 |
| 11 | 工作区 / secret / skill 预加载 | run 启动前把上下文准备好 | P3-1 里用任务目录做 `cwd` + brief 注入，避免 agent 自己找文件 | 同左 |
| 12 | 审计事件全覆盖 | 每次状态迁移都落审计 | 我们已有 audit 表，补 P0-2/P2-1 的新事件类型 | 同左 |

**一句话总结**：paperclip 的"锁 + lease + orphan 回收 + 薄 adapter + 结构化 run"这套骨架可以直接搬；它的"按进程判活"只对 cli 席位成立，GUI 席位必须用"产物增量 + 窗口文本增量"替代，否则就是把假心跳换个名字。

## 五、实施顺序与风险

1. **顺序**：P0-1/P0-2（补审与 waitingHuman）→ P0-3（窗口自愈）→ P1-1/P1-2（真判活）→ P1-4（lease）→ P2-1/P2-2（幂等与回收）→ P3-1（cli 席位灰度）。
2. **每条改动前**：先备份 `aicompany.db`；改动只碰单个模块，禁止顺手重构。
3. **可回滚**：P1/P2 新增均为"新增文件 + 读取分支"，关掉开关即回旧逻辑；P0-1/P0-2 改判定分支，保留旧判定在注释与开关后。
4. **验收方式**：不看"有没有报错"，看"审计里 `review_requeued` / `deferred` / `stall_wait_heartbeat` 三个计数是否下降，以及同一 task 的 run 数是否收敛到 1～2 次"。
5. **风险点**：
   - 补审白名单过宽 → 真吞事件也被跳过：需同时校验"存在 pending 标记"，不能只判 `in_review`。
   - 窗口文本增量在 GUI 转场时可能抖动：用"长度 + 哈希"双条件，且允许 1 次抖动。
   - cli 席位与 GUI 席位争抢同一账号并发：CLI 侧并发需串行（同设备单会话），否则互相打断。

## 七、专题：执行中要人配合，必须走汇报流程

### 7.1 现场还原

现象：某一轮执行，agent 需要用户配合（关掉另一个程序的窗口），它没有提交变更请求，而是在自己的会话窗口里直接写"请你先关掉 X，然后告诉我"，然后停在那里等回复。用户当时没看那个会话窗口，所以没人回答；系统看它还在"跑"，一直等到 60 分钟超时才判失败、重投，第二趟才完成。

**关键是：这不是 agent 违规，而是它遵守了它收到的提示词——提示词只教了它一种上报方式，且条件写得很窄。**

### 7.2 病根（三处，全部可验证）

| # | 病根 | 证据 |
| --- | --- | --- |
| 1 | 上报条件写窄了 | `src/gui-prompt.js:115` 的 `changeRequestHint` 原文是「发现方向不对 / 范围要改时，不要只在屏幕上说明，写 change-requests/<crId>.json」。**只覆盖"方向/范围"，没覆盖"要人配合/要个信息/等个确认"**。agent 遇到"请你关掉外部编辑器"这种，按字面理解不属于"方向不对"，于是走了它最熟悉的渠道：对着窗口说话 |
| 2 | 没有明说"窗口没人看" | 提示词通篇没有一句"这个会话窗口没有人值守，你在这里提问不会被回答"。agent 在豆包桌面端里天然被当成"与人对话的助手"，它的默认行为就是提问 |
| 3 | 系统看不见"窗口里问了话" | 判活只看磁盘：`report.draft.json` / `completion.json` / `output/`。会话里的提问不产生任何文件，所以在控制系统眼里，这个 run 一直"正常在跑"，直到超时 |

顺带一个次要病根：即使 agent 真走了上报，也未必叫得醒人——`docs/董事会拍板渠道-补丁说明.md` 自己写着"看板不开着就收不到提醒"，目前只有看板内的黄条和标签标题。

### 7.3 好消息：上报链路本身是完整的，不需要重建

读了 `engine.js` 的 `submitChangeRequest`（817–916），现有能力已经够用：

- agent 交 `change-requests/<crId>.json`（`change-request/v1` schema）→ `severity=needsDecision`；
- 任务自动转 `awaiting_decision`（`engine.js:850`），**挂起、不烧额度**；
- 自动落现场快照（`buildSnapshot`），失败也留痕；
- 决策者是员工时自动开处置卡并唤醒他（`openEscalation`）；决策者是董事会/人时进 `board_messages` 的 `kind=decision`；
- 同时 `notifier.send`（`scene: decision`）走已有通道；
- 拍板后按 `decision` 唤醒原卡继续（`engine.js:1915`）。

**所以方案不是造新通道，而是让 agent 一定会用这条通道，并且系统在它不用时能兜住。**

### 7.4 方案（四层，从便宜到贵）

**第一层：约束（改提示词，成本最低，当天可做）**

把 `changeRequestHint` 从"方向不对/范围要改"扩写成一份明确的"沟通纪律"，建议文案：

```
【沟通纪律】你看不到我，我也看不到你的对话窗口。这个窗口没有人值守。
（注：控制面读不到你的窗口，但董事会本人可以在豆包工作客户端里用 /resume 打开这段会话看到全过程——别以为没人看得见。）
凡是需要人配合、需要人给信息、需要人开权限、需要人确认某件事，一律不许在窗口里提问，
必须写 change-requests/<crId>.json（severity=needsDecision，reason 写清"要谁做什么"），然后停手。
写完就停，不要等回复；控制面会把它转到能拍板的人那里，拍板后你会被重新唤醒。
只有一种情况可以在窗口里说话：你已经把活干完、报告已落盘。
```

同时在 `noScreenOnly` 旁边补一句正向替代："没有人回答时，按最保守的假设继续做完，并在报告里列出你替人做的假设（假设项标 `assumed`），不要停在那里等。"

**第二层：检测（系统代它上报，防止不自觉）**

在 P1 的 vitals 看门狗里加一条判定（不需要读窗口、不需要 UIA）：

```
vitals 三源连续 10 分钟零增长
 且 change-requests/ 目录无新文件
 且 report.draft.json 不存在
 且 run 未结束
→ 判定：疑似中途等人（隐性等待）
→ 动作：控制面代建 change-request（kind=clarify, severity=needsDecision,
        reason="席位疑似在会话中等待人工确认，未提交变更请求，已代为挂起",
        agentId=该席位），任务转 awaiting_decision
→ 附件：最近一张 screenshots 截图 + 当前窗口标题 + 已跑时长
→ 通知：board_messages(kind=decision) + notifier(scene=decision)
```

这样"它在窗口里问了什么"不需要机器读懂——人点开截图就能看到原话，成本几乎为零。这条同时解决了"看板关着收不到"的问题：decision 走 `notifier` 已有通道，可挂系统托盘/飞书。

**第三层：闭环（挂起后别让它继续空转）**

代挂起的同时，adapter 要主动收掉当前 run（发 Esc 或直接停止轮询并把 run 标 `suspended`）。否则会出现"任务已挂起，窗口里的 run 还在傻等"的两套状态。拍板后走 `engine.js:1915` 的 decision 唤醒，把答案注入新的 brief（answer.json → 提示词补一段"上次你问的那件事，答复是…"），必要时用 CLI 的 `--resume` 续同一会话，避免它把上下文丢了。

**第四层：根因（席位身份）**

GUI 席位的本质问题：它既是"执行者"，又坐在一个"人类聊天窗口"里，天然会把人当对话对象。所以 brief 开头要明确身份：

> 你不是在和人聊天。你是一台无人值守流水线里的工人，你的上级是汇报线上的席位与董事会，这个窗口只是你的工作面。除了交付，任何话都不会被读到。

配合 P3 的 cli 席位更彻底：CLI 没有"用户正在看我"的暗示，`-p` 一次跑完、`--json` 出结果，从物理上就没有"在窗口里等人回答"这个动作。

**第五层（可选）：提问也要能对上号**

如果以后想精确知道它问了什么，可以再加 UIA 读文本（`kb.ps1` 目前只有 `focusinput` 找输入框，没有读文本动作，需要新增 `readtext`）。但按"成本优先"原则，先不做——截图已经够人看了。

### 7.5 落地顺序与验收

1. P0-4（提示词纪律）→ 观察一周：`awaiting_decision` 的数量应上升（这是好事，说明它开始走正路），"窗口提问导致超时"应归零。
2. P1-5（沉默检测代挂起）→ 人为造一次"派单后让它等人"的场景，验证 10 分钟内自动进待决策、附截图、通知到达。
3. 第三层闭环（代挂起时收 run + 拍板后注入答案）→ 验证挂起期间无僵尸 run、拍板后能续上。
4. 第四层（身份文案）随 P0-4 一起改，不单独排期。

### 7.6 不做什么

- **不去做"监听对话内容并语义判断是否在提问"**：误判率高，且要读屏/读 UIA，成本与收益不匹配。用"产物零增长"这个客观信号代替。
- **不把 `awaiting_decision` 的自动恢复打开**：`/api/change-requests/expire` 现在是 24h 提醒、72h 取消、绝不自动恢复，这个保守设定是对的，别改。
- **不指望 agent 自觉**：第一层是"教它"，第二层才是"保证"。只做第一层，等于把稳定性押在模型是否听话上。

### 8.1 先说结论

"像对真人一样对话、多轮汇报、下级提问题上级答复再继续"——**能力其实已经存在，缺的是闸门和旁路**。因此不建议现在改，建议先按第三～七章收敛，等 `deferred` / `review_requeued` / 空转三个计数归零之后再动这一层。

### 8.2 能力盘点（读协议与代码确认，不是推测）

| 想要的能力 | 现有实现 | 状态 |
| --- | --- | --- |
| 下级提问题 | `change-request` 的 `kind: direction / clarify / scope / blocked`，`severity: needsDecision / advisory` | ✅ 已有，其中 `clarify` 就是"我要问清楚" |
| 上级给答复 | `decision` 的 `decision: resume / redo / derive / cancel` + `chosenOption` + `newInstructions` + `newAcceptance` | ✅ 已有，`newInstructions` 就是"我下令你怎么改" |
| 答复后继续干 | `engine.js:1915` 起按 `decision` 唤醒原卡，注入新指令 | ✅ 已有 |
| 多轮往来 | `thread` 协议 `aicompany.thread/v1`：`mode=cowork/meeting`、`wakePolicy=never/onRollCall/onMessage`、`ceoVisibility=none/cc/decide`、`ttlDays`、单向 `promote`；`/api/threads` 全套接口 + `threads` 表 | ⚠️ **协议冻结并有接口，但没有消费方**（P7 自己写明"threads 表没加 project 列，避免为还没有消费方的字段改表"） |

| 对话不污染任务状态机 | `thread` 设计上就不进状态机，唯一出口是 `promote` 一次成卡 | ✅ 设计已有，未接 |

**所以"上报不完善"的准确说法是：不是缺通道，是缺三道闸——轮次预算、同级旁路、以及"对话不进状态机"的实际接线。** 单轮已经能跑（`clarify` → `decision.newInstructions` → `resume`），多轮一放开就会变成没有刹车的循环。

### 8.3 如果将来做，接法应该是这样（不新建体系）

1. **用 `thread` 承载多轮，不用任务卡承载。** 对话期间任务停在 `awaiting_decision` 或 `blocked`，不产生新 run；`thread` 里来回发消息，`ceoVisibility=decide` 时才上升。
2. **`wakePolicy=onRollCall` 默认。** 只在"点名"时唤醒席位，不是每条消息都唤醒——这一条直接决定 token 是线性还是乘法。
3. **同一 run 内续问，不新建 run。** GUI 席位在同一会话里追问；cli 席位用 `--resume <sessionId>`。**这是成本的关键**：我们实测的一次任务已经跑过 9 个 run（3 次 defer + 1 次手动重派 + 5 次补审），如果每轮对话再各开一个 run，成本不是加法是乘法。
4. **轮次预算硬编码在闸上**：每张卡最多 2 轮 `clarify`，每轮对话预算（token/时长）独立计算；超限自动降级为"按最保守假设继续 + 报告标 `needsReview`"，不允许无限问。
5. **同级自治只开白名单**：`clarify`、接口约定、信息缺失这三类允许在 `thread` 内由相邻层级解决（`ceoVisibility=none`）；一旦涉及范围、验收、钱、对外发布，立刻 `promote` 上抬。
6. **验收/归口只在最终一次**：对话期间的中间产物不触发 `review` 与 `assetAck`，避免"每轮都验收一遍"的浪费——本次会话实测的 5 次补审 + 归口两趟就是这种浪费的原型。

### 8.4 为什么现在不做：成本不对称

- 现在的病灶是"假活"（空转被判成功、重复派、读不到结果），修它花的是**一次性工程成本**，收益是每天都不再浪费；
- 自由多轮的病灶是"真贵"（每轮都是一次完整派单 + 上下文重建 + 验收 + 归口），做错一次就把省下来的全赔进去，而且**没有闸门时无法回滚**；
- 更关键：多轮的价值依赖于"判活可信"。如果系统连"它到底在不在干"都判不准，多轮对话只会在错误的信号上叠加更多轮次。

**所以顺序必须是：先让系统"看得准"（P0/P1），再让它"聊得动"（阶段3）。反过来做，等于在沙地上盖二层。**

### 8.5 本次只留的三个接口位（不动代码）

1. `thread` 表与 `/api/threads` 保持原样，不删不改——它已经是阶段3 的容器。
2. `decision.newInstructions` 保持"可带一段自由指令"的语义，阶段3 直接复用，不要把它收窄成枚举。
3. `change-request` 的 `kind=clarify` 保留，不要合并进 `scope`；它是同级对话的入口类型。

### 9.3 CLI 实测的三个坑（后续改这段代码必须知道）

1. **无 TTY 直跑会假死**：管道环境里静默卡在 `cli_dispatch_authorization stage=query`，轮询 40+ 次、10 分钟不干活。必须伪终端。
2. **node-pty 两处细节**：`pty.spawn('node', ...)` 报 `File not found`，必须传 `process.execPath` 绝对路径；ConPTY 在控制面（无 console）报 `Cannot launch conpty`，必须 `useConpty:false` 退回 node-pty 自带 winpty 后端。
3. **默认沙箱写不了文件**：`Write` 工具"文件写入暂时不可用"、Bash `failed to initialize sandbox sdk in shell host`、提权提示 `approvals are unavailable in non-interactive mode`。所以 CLI 席位必须带 `--dangerously-bypass-approvals-and-sandbox`。

> 已知安全面：带绕过参数的 CLI 席位对本机有完全读写权限。当前只挂在 `cli-exec` 一个岗位、日配额 3，不要扩散到别的岗位；后续若要收紧，做法是给桥接脚本加"只允许写任务目录"的路径校验，而不是依赖 CLI 自己的沙箱。

### 9.4 依赖策略

`node-pty` **不进** `package.json`（工程零运行时依赖，测试 P2-6 强制）。桥接脚本动态 `import('node-pty')`，缺包时返回 `failed` 并提示 `npm i node-pty`；`devDependencies` 保持 `{}`。

## 十、二次事故复盘与修复（2026-11-23 下午，已上线）

### 10.1 事故是什么

卡 `T-a4d59e96`（示例项目批量文档标注）实测一趟走成四连坏：CLI 交活 → 报告被拒两次 → 转工程 → 工程两趟都没被认到 → 人手动取消 → 取消后系统还在等重派那趟的结果。

### 10.2 真因（一句话）

桥接脚本往 stdout 吐的是信封 `{status, usage, result, sessionParams}`，而 process adapter 的约定是**最后一行直接就是完成报告**。`normalize()` 原先把整段当 `result`，于是信封被拿去当完成报告校验，报「缺 schema/taskId…、多 result/sessionParams」。

产出其实全在：`output/` 六个文件、`report.draft.json`、`completion.json` 都齐。**报告写进了文件，没写进它唯一会读的那一行。**

### 10.3 为什么一件小事炸成四连

| 环节 | 机制缺陷 | 后果 |
|---|---|---|
| 报告校验 | 信封被当报告（契约不一致） | `report_rejected` 第 1 次 |
| 重试策略 | 格式错误是确定性错误，却按「可重试」处理；重试时还不告诉席位错在哪 | 白烧一次额度，同一个错误再犯一遍 |
| 救火路由 | 第二次仍不合格 → `escalate_to_rescue` 换岗 | 一张纯文件活被转给 GUI 工程岗 |
| GUI 准入 | 工程第一次被「前台是 msedge 不是 WorkBuddy.exe」判 deferred | 白跑一趟 |
| 重派 | reconcile 又派一趟，旧会话没被真掐断 | 两个会话一个目录；旧会话先干完，结果按「已判死」丢掉 |
| 取消 | `cancelTask` 只改库、不中断 run、不作废排队事件、不通知会话 | 人取消了，系统还在等；9 秒后还在 `reconcile_requeue` |

核心一句话：**「判死一趟 run」原来只是改了个数据库字段，现场一点没变。**

### 10.4 本轮改了什么

| 编号 | 改动 | 落在哪 |
|---|---|---|
| A2 | `normalize()` 兼容信封：无 `schema` 且带 `result` 的，拆包取 `result`；裸变更请求按 schema 推断成 `change_requested` | `src/adapters.js` |
| B1 | `report_rejected` 时把拒收原因作为 `reviewNote` 带进重试；「同一轮里紧挨着的上一次」错在同一处 → 不再重试，直接 blocked + 报人 | `src/engine.js` |
