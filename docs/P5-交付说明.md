# P5 交付说明 · 试运行与观测

> 对应清单：P5-1 ~ P5-4（4 项）+ G-P5 门禁。
> 结论先说：**四项全部落地并验证；G-P5「连续 3 天」不打勾**——因为它要求真实墙钟累积，
> 而我只能给你「压缩时钟跑通」的证据，不能替时间签名。原因与你自己怎么补，见第 7 节。

---

## 1. P5 到底在干什么（大白话）

前四个阶段是在**造车**：发动机、方向盘、刹车、仪表盘都装好了，实验室里每一项都测过。

P5 是**把车开出去连跑几天**，看它会不会自己出毛病。因为很多问题只有「时间长了」才会冒出来：

- 任务卡在一个状态里忘了收尾；
- 同一件事被反复叫醒，白烧额度；
- 挂了三天等人拍板，没人管，也永远不超时；
- 干完了但报告文件没落盘，账面上却写着完成。

这些都不是「代码写错了」，而是**跑久了才会露出来的脏**。P5 就是给这些脏装一套体检。

---

## 2. 五项指标：到底在量什么

| 指标 | 一句话 | 怎么算的 |
|---|---|---|
| **误唤醒率** | 明明不该叫醒，还是去叫了 | 对「已挂起 / 已完结」的卡发起的唤醒 ÷ 全部被拒唤醒。配额、并发、离线属于正常延迟，不算误 |
| **空转 Run 率** | 跑了一趟，什么也没干成 | 跑完但没带来状态变化 / 没建卡 / 没返工 / 没验收的 Run ÷ 成功 Run |
| **报告不合格率** | 交上来的东西被打回几次 | 验收打回 ÷（验收通过 + 验收打回），等于返工率 |
| **GUI 失败率** | 桌面自动化那类席位挂了几次 | GUI 席位非成功 Run ÷ 该席位 Run 总数，含环境检查不过与超时 |
| **额度消耗** | 这个周期用掉了多少配额 | 各席位已用 ÷ 上限 |

**关键设计**：每个指标的口径原文写进代码常量 `METRIC_DEFINITIONS`，报告里原样印出来。
这样三个月后你看到「误唤醒率 3%」，能立刻知道它到底在算什么，而不是猜。

## 3. 四项结论：§6C / §6D 的承诺兑现了没有

| 结论 | 判定标准 | 本次 5 天压缩跑的结果 |
|---|---|---|
| 直投是否绕开 CEO | 直投卡里 CEO 一次都不该被唤醒 | ✅ 75 张直投卡，CEO 零唤醒 |
| `cowork` 是否误建卡 | 协作会话里不该冒出任务卡 | ✅ 15 个会话，零建卡 |
| 挂起是否被误重跑 | 挂起后除「决策出口」外不该有新 Run | ✅ 15 次挂起，零插队 |
| 决策超时率 | 挂 72 小时该自动取消 | ⚠️ 15 次挂起里 6 次超时被取消（40%），说明拍板跟不上——这是**真实信号**，不是 bug |

最后一条特意标成「需要关注」而不是「通过」。试运行的价值就在这里：**它会告诉你制度哪里不顺手**。
15 次挂起有 6 次没人管到超时，要么提醒不够显眼，要么挂起门槛太低。这条可以直接拿去做 P5-2 的调参依据。

## 4. 调参：原来「cooldown」根本没实现

P5-2 要求「据此调 cooldown / 配额 / 提示词模板」。做完发现一个尴尬事：

**任务书 §7.3 的 Run Policy 第 4 条写着「max concurrent runs 与 cooldown 是否放行」，但代码里并发上限是写死的 3，cooldown 压根不存在。** 也就是说，这一项如果直接跳过，就是「调一个空气」。

所以本轮先把它补齐：

- `runPolicy.maxConcurrent`：并发上限可配（默认 3，与旧行为一致）；
- `runPolicy.cooldownSec`：同一席位两次唤醒的最小间隔（默认 0 = 关闭，老配置不受影响）；
- 治理类唤醒（决策 / 返工 / 升级 / 改方案）**豁免冷却**，否则会把卡在半路；
- 被冷却 / 配额 / 并发 / 离线拒绝时，卡**退回 `todo`** 等补偿扫描重投——不能停在 `in_progress` 却没有 Run，那在仪表盘上看起来就是卡死。

调参本身有两条硬约束：

1. **只许改白名单里的键**（`src/tune.js` 的 `TUNABLE`），改未定义字段一律拒绝；
2. **每次都留审计**，`action = config_change`，`oldValue` / `newValue` 都是 `{key, value}`，看板能直接查出「谁在什么时候把预警线从 0.8 调到 0.7、为什么」。

持久化**不改写 YAML**（会破坏你手写的注释和顺序），而是落一份 `config/runtime-overrides.json`，
在 schema 校验之前合并。删掉这个文件就回到配置文件原值。

## 5. today 席位：不配，理由写进配置了

§3.3 早就定了「保留但挂编制外」。P5 要的是**把它落成不留「待定」的结论**，所以：

- **示例 profile 里不配 today 席位**；
- 配置里留了注释说明为什么（见 `config/company.example.yaml` 的 agents 段上方）；
- 理由不是「懒得配」，而是：today 是**只读巡检**，靠外部定时拉 API 出简报，不派活、不验收、不进状态机。
  一旦把它写成席位，调度器就会把它当可用工位派活，等于给它开了它本来不该有的权限。
- 它想要的那份简报，控制面自己就能给：`/api/dashboard` + `/api/audit` 定时拉取即可。

## 6. 脏状态检查：11 条规则，逐条能指到记录

「连续 3 天无脏状态」不能靠感觉。代码里定义了 11 条可机检的规则：

| 规则 | 抓什么 |
|---|---|
| `orphan_run` | Run 指向不存在的卡 |
| `stuck_running` | Run 一直 `running` 没收尾（超 `maxRunHours`，默认 2h） |
| `stale_event` | 事件积压超 10 分钟没被处理 |
| `awaiting_overdue` | 挂起超 72 小时仍没被取消（说明超时扫描没跑） |
| `done_without_report` | 卡标成 `done`，报告文件却不存在（只查执行席位） |
| `in_progress_without_run` | 卡在 `in_progress` 但从没跑过 Run |
| `quota_anomaly` | 配额为负或超上限两倍 |
| `decision_without_cr` | 决策指向不存在的变更请求 |
| `revision_gap` | 当前 `revision` 与版本快照表不一致 |
| `promoted_not_archived` | 空间已提升成卡却没归档 |
| `terminal_rewoken` | 已终态的卡之后又被跑了一次 |

这 11 条我用**故意造脏**的方式逐条验过（`tests/p5.test.js` 里一次性造出 8 类脏，全部被抓到）。

## 7. G-P5 为什么没打勾（最重要的一节）

清单原文：**连续 3 天无脏状态，不过不宣布上线。**

我做了什么：

- 真实墙钟模式（`--mode real`）：进程真等，每 60 秒做一轮维护与采样，跑满 72 小时才可能判通过；
- 压缩时钟模式（`--mode compressed`）：用虚拟时钟把 5 天压进 8 秒，**跑的是同一套引擎、同一个状态机**。

压缩模式 5 天的结果：**120 小时，120 次采样，零脏状态，零报错，超时取消路径也走到了。**

但我仍然**不勾 G-P5**，原因只有一句：

> 压缩时钟证明的是「这套逻辑在多天维度不会自相矛盾」，它证明不了「连续 72 小时真实墙钟不出事」。
> 真实世界里会出事的东西——机器休眠、时钟跳变、磁盘写满、进程被杀——压缩模式一个都碰不到。

所以门禁判定写死了：

| 模式 | 结论 |
|---|---|
| compressed | `level: simulated`，**永远不给 passed**，报告里明写「不能用模拟代替」 |
| real 但不满 72h | `level: insufficient` |
| real 满 72h 且中途脏过 | `level: dirty`，不通过 |
| real 满 72h 且全程零脏 | `level: real`，通过 |

**你自己怎么补这 3 天**（一条命令，挂着就行）：

```bash
npm run soak:real        # 等价于 node scripts/soak.js --hours 72 --mode real --interval 60
```

跑完（或被 Ctrl+C 打断）都会在 `work/soak/<runId>/` 下出 `report.json` / `report.md` / `samples.jsonl`。
`report.md` 顶部那一行就是门禁结论。**满 72 小时且写「通过（real）」，就可以把 G-P5 打勾了。**

在这之前我会一直留着 `[ ]`，不虚报。

## 8. 这轮修掉的坑（都是跑起来才暴露的）

| # | 坑 | 怎么发现的 | 怎么修 |
|---|---|---|---|
| 1 | `compensationScan` 偷用真实 `Date.now()` | 压缩时钟跑时，任务时间戳都在「未来」，补偿扫描永远跳过 | 改成可注入 `now`，否则长跑验证是假通过 |
| 2 | `completionReportPath` 是相对**任务目录**，我按 `workRoot` 拼了 | 一跑就报 45 处「报告缺失」 | 改成 `workRoot/tasks/<id>/` |
| 3 | 把「制造变更请求的那次 Run 自己」算成误重跑 | 15 次挂起全被判 fail | 排除 `cr.runId`，并用严格大于 |
| 4 | 指挥岗（CEO/组长）也被要求交 `completion.json` | delegate 主卡全是「报告缺失」 | 只查执行席位（`capabilities` 含 `execute`） |
| 5 | 终态唤醒被**静默丢弃**，查无可查 | 误唤醒率永远「样本不足」 | 事件泵拦截时写 `wake_rejected` 审计 |
| 6 | 探针污染误唤醒率（100%） | 报告数字吓人且失真 | 探针带 `source=soak-probe`，单独计数 |
| 7 | cooldown 拒绝后卡停在 `in_progress` | 被脏状态规则抓到 | 退回 `todo` 等补偿扫描 |
| 8 | 调参深合并把 `agents` 数组整个冲掉 | `agents` 是数组，不是对象 | 席位级额度单独存 `agentQuotaDaily` 映射 |
| 9 | 报告文案说「都在 72 小时内被拍板」 | 实际是「还在等」 | 拆成「已拍板 / 仍在等 / 已超时」三个数 |

## 9. 怎么用

```bash
# 压缩跑（8 秒出结论，用于开发自查）
npm run soak -- --hours 120 --mode compressed

# 真实跑（真等 72 小时，用于过 G-P5）
npm run soak:real
```

程序化调用：

```js
import { createSoakRunner, buildSoakConfig, judgeGate } from './src/soak.js';
import { computeMetrics, detectDirty, buildObservation } from './src/observe.js';

const runner = createSoakRunner({ workRoot: './work/x', config: buildSoakConfig({ workRoot: './work/x' }) });
await runner.drive({ hours: 72 });
const obs = runner.observation({ mode: 'compressed', hours: 72 });
```

## 10. 边界：这一轮没做到什么

- **没有真跑 3 天**：只做了压缩跑（见第 7 节），G-P5 留空；
- **没有接真实 agent 模型**：soak 用的是确定性 mock adapter。它验证的是引擎与治理逻辑，
  **不验证模型质量**。真模型下的报告不合格率、误判率必须用真实配置跑才准；
- **GUI 失败率恒为「样本不足」**：soak 的四个席位都不是 `gui-template`。要测这条，
  得配一个真 GUI 席位（P3 已支持），这是你接真实环境时才会有数据；
- **`cooldown` 只做了「同席位最小间隔」**：没有做「失败后指数退避」；
- **调参不回写 YAML**：覆盖层是 `config/runtime-overrides.json`，配置文件本身不动；
- **看板未在真实浏览器点测**：只做了语法与 id 引用一致性校验。
