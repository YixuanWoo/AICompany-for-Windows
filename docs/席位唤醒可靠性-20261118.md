# 席位唤醒可靠性：输入框聚焦 + 窗口身份识别

日期：2026-11-18
范围：`gui-template` 席位（工程执行 WorkBuddy、执行 豆包工作）
状态：已实现、已重启生效、434/434 测试通过、真机两轮实测通过

## 一、问题现象

工程执行席位（WorkBuddy GUI）唤醒时经常出现：

- 窗口起来了，但输入框里没有光标，快捷键也不起作用；
- Ctrl+N 看起来发了，但界面还停在首页 / 上一个会话；
- 接着粘贴的提示词没有落进输入框，控制面却记成「已发送」；
- 偶发窗口以「上次退出时的怪尺寸」恢复（如 1200×800），按全屏坐标点击会点到窗口外。

## 二、查到的四个根因

1. **没有「聚焦输入框」这一步**
   旧步骤是 `activate → newSession → paste → press`。`activate` 只把窗口提到前台，
   不保证光标在输入框里；窗口刚起来、页面还在首页时，粘贴会落到空白处。

2. **Ctrl+N 在首页不一定生效**
   实测 WorkBuddy 5.11.3：在首页按 Ctrl+N 不会新建会话，页面仍停在首页。
   旧流程把 `newSession` 当成了「必成」的动作，实际它可能什么都没做。

3. **窗口尺寸会被还原成上次的怪状态**
   `SetForegroundWindow` 内部走 `SW_RESTORE`，会把最大化窗口还原成上次退出时的尺寸。
   先最大化、后抢前台，等于白做；坐标按全屏算就会整体偏掉。
   正确顺序：先抢前台，再最大化，且最大化后不要再调用带 `SW_RESTORE` 的激活。

4. **窗口身份只靠标题**
   桌面客户端标题可能随会话名变化。只按标题找窗口 / 校验前台，
   会在「同一个窗口、标题变了」时被判成「窗口找不到 / 被抢焦点」。

## 三、改了什么

### 1. `scripts/win/kb.ps1`

- 新增动作 `focusinput`：
  - 先用 UI Automation 找窗口里的 `Edit` 控件（会话页的输入框是原生 Edit），点它的中心；
  - 找不到 Edit（首页没有原生输入框）就按**窗口客户区百分比**点击，默认 `(55%, 43%)`；
  - 点之前如果窗口最小化，先 `SW_RESTORE`。
- `activate` 新增参数：
  - `-Launch <路径>`：没有可见窗口时先拉起应用，最多等 15 秒；
  - `-Maximize`：抢到前台**之后**再最大化（顺序修正，见根因 3）；
  - `-ProcessName <进程名>`：按进程名找窗口，标题变了也能认出来。
- 新增动作 `process`：打印前台窗口所属进程名（只读，供「按进程校验前台」用）。
- `WinKb` 新增 `Find(title, processName)`、`ProcessOf()`、`IsIconic()`、`ClientRectOf()`。

### 2. `src/gui-driver.js`

- 新增 `focusInput()`：执行 `commands.focusInput`，没配就跳过（老配置行为不变，测试里的 simulation 返回 `simulated`）。
- 新增 `foregroundProcess()`：执行 `commands.foregroundProcess`，拿前台进程名。
- `assertForeground` / `waitForeground` 支持 `process`：
  配了进程名时按进程校验前台，不再依赖会变的窗口标题。

### 3. `src/gui-adapter.js`

- 新增步骤 `focusInput`，失败归为 `kind=focus`（引擎按「稍后再来」处理，不算一次执行失败）。
- `focusOptions` 支持 `config.windowProcess`，前台校验改按进程。
- 步骤白名单从 7 个扩到 8 个（`activate / newSession / hotkey / focusInput / paste / press / verify / restoreFocus`）。

### 4. `config/company.prod.yaml`（工程席位）

```yaml
windowProcess: WorkBuddy.exe
steps:
  - action: activate
  - action: newSession
  - action: focusInput
  - action: paste
  - action: press
    key: enter
  - action: restoreFocus
```

`activate` 命令带 `-Launch "D:\WorkBuddy\WorkBuddy.exe" -Restart -Maximize -ProcessName "WorkBuddy.exe"`；
`focusInput` 命令带 `-ProcessName "WorkBuddy.exe"`；新增 `foregroundProcess` 命令。

## 四、实测结果

### 第一轮：只粘贴、不发送

按生产命令链执行：

```
activate（含 Launch/Maximize）→ Ctrl+N → focusinput → setclip → paste
```

截图确认测试文本出现在输入框里，未按回车、未产生对话。**通过**。

### 第二轮：点击 + 发送

同一链路加 `press enter`，发送一条最小提示词：

> 【唤醒链路测试】请只回复“收到”，不要执行任何任务。

结果：

- 消息成功进入会话；
- WorkBuddy 在 11 秒内回复「收到」；
- 会话标题自动生成为「测试唤醒链路会话响应」；
- 证明「激活 → 聚焦 → 粘贴 → 发送」全链路可用。

### 第三轮：托盘唤醒（用户把应用收到托盘后）

实测状态：进程在跑、`MainWindowHandle=0`，`find` 找不到可见窗口。

链路 `activate -Launch ...` → `focusinput` → `paste` → `press enter`：

- 应用被从托盘拉起，窗口恢复最大化；
- 首页输入框成功聚焦并粘贴；
- 发送后 8 秒回复「收到」。**通过**。

### 第四轮：发现「输入僵死态」+ 重启自愈

第三轮发完一单后继续在**会话页**复用同一个实例，出现：

- 窗口在前台、`WindowFromPoint` 也落在应用上，但**鼠标点击与键盘粘贴都不生效**；
- 侧栏会话点不动、输入框贴不进字；换成 UIA / 首页点位 / 会话页点位都不行；
- 这不是坐标问题（点位都在输入框内），而是应用进入了「不接收合成输入」的僵死态；
- `Stop-Process` 后重启，实例立刻恢复接收输入。

结论：**GUI 席位按无状态处理**。`activate` 新增 `-Restart`：
杀掉同名进程 → 重新启动 → 等可见窗口 → 最大化。每单都在「首页 + 全新实例」上执行，
既绕开僵死态，也绕开「会话页输入框点位不稳」的问题。

随后用 `-Restart` 链路完整跑了一遍：

```
activate -Restart -Maximize → focusinput（home,verified）→ setclip → paste → press enter
```

发送「请只回复：收到」，5 秒后回复「收到」。**通过**。

## 五、焦点自检（新增的硬保障）

`focusinput` 不再「点一下就当聚焦成功」，而是**逐个候选点验证**：

1. 点击候选点（UIA 找到的 Edit → 首页输入框 → 会话页输入框）；
2. 贴一个固定探针字符串；
3. `Ctrl+A` / `Ctrl+C` 后读剪贴板，内容等于探针才算光标真在输入框；
4. 验证成功后 `Ctrl+Z` 撤销探针，不破坏原有草稿；
5. 三个点都验不过就明确报错（`kind=focus`），上层按「稍后再来」重试，不会把空粘贴当成已发送。

## 六、边界与后续

- `focusinput` 的 UIA 分支依赖应用暴露 `Edit` 控件；首页暴露不到时走百分比兜底，两个分支都经过实测。
- 会话页输入框依赖「点的位置在输入框内」；这条路径在僵死态下无效，所以生产配置直接用 `-Restart` 回到首页，
  不依赖会话页点位。
- 若应用整体卡死（渲染进程无响应），重启是目前唯一可靠的恢复手段；`-Restart` 已内建。
- 本次只改工程席位；执行席位（豆包工作）保持原步骤。若后续也出现「无光标」，
  给它的 `steps` 加同样的 `focusInput` 即可，命令模板照抄。

## 七、二次修复：focusInput 的 `{{windowTitle}}` 占位（2026-11-18 21:00）

**现象**：工程席位所有任务都停在「已启动、粘贴不上去」，Run 状态反复 `deferred`，
错误固定为「输入框聚焦失败：GUI 命令模板有未填占位 …… -WindowTitle "{{windowTitle}}"」。

**根因**：`createCommandDriver().focusInput()` 调用 `run(commands.focusInput, {})`，
传的是空变量；`activate` 会传 `{ windowTitle }`，所以启动正常、只有聚焦这一步永远渲染失败。
`renderCommand` 的「有未填占位就报错」本身是对的，问题在调用方漏传。

**修复**：`src/gui-driver.js` 的 `focusInput()` 改为
`run(commands.focusInput, { windowTitle: config.windowTitle ?? '' })`，与 `activate` 使用同一份标题。

**验证**：
- 单测 `G3 · focusInput 也能拿到 windowTitle，不会留下未填占位`；
- 全量 `npm test` 439/439；
- 重启后真实任务 `T-0959e8b2` 自动重派，`R-cd1d385d` 在 21:02:25 写出 `dispatch.json`（送达确认），
  之后进入正常轮询，不再出现 `wake_deferred`。
