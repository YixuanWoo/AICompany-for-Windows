# 循环任务首次触发被静默跳过 —— 事故报告（2026-11-16 20:30）

## 一句话

周一 20:30 的 demo-editor 周体检**一次都没跑**，而且没报错、没留审计、面板上看不出任何异常——
`nextFireAt` 却照常前进到了下周一。等于「这个循环从未存在过」。

## 一、现象

20:33 董事会反馈「8 点 30 过了，自动触发没触发」。

查到的现场：

| 检查项 | 实际 |
|---|---|
| 调度器 | `running: true`，79 ticks，没停 |
| `recurring_jobs.lastFiredAt` | `2026-11-16T12:30:08.652Z` ← **写进去了**（= 北京时间 20:30:08） |
| `nextFireAt` | `2026-11-23T12:30:00.000Z` ← **前进了一周** |
| `cycles` | **0 行** |
| `cycle_fires` | **0 行** |
| `tasks`（20:25 之后） | **0 张** |
| 审计（20:25 之后） | **一条都没有** |
| 服务日志 | 无 error，无 tick 失败 |

最刺眼的是：`lastFiredAt` 有值，说明 tick 确实处理了这个 job、并且认为「已经触发过」。

## 二、根因

`occurrencesBetween()`（`src/rrule.js`）用的是**左开区间**：

```js
if (candidate > fromLocal && candidate <= toLocal) { ... }
```

而 `tick()` 里算搜索起点是这样写的：

```js
const from = job.lastFiredAt ?? job.nextFireAt;
```

首次触发时 `lastFiredAt` 是 `null`，于是 `from = nextFireAt` —— **正好等于这一刻的触发点本身**。
左开区间把它排除掉，`selectFires` 返回空数组，for 循环一次都不进。

然后 `tick()` 尾部无条件执行：

```js
fresh.nextFireAt = nextFireAt(...);   // 前进一周
fresh.lastFiredAt = at;               // 记成「已触发」
```

结果就是：**什么都没干，但账上写着干过了。**

用真实参数复现：

```
nextFireAt = 2026-11-16T12:30:00.000Z
from=nextFireAt     → 找到 []
from=nextFireAt-1s  → 找到 ['2026-11-16T12:30:00.000Z']
```

## 三、为什么 315 条测试没抓到

`tests/` 里**只有一条**用例真正走过 `tick()`（P2-6「真实 tick」），而它是这样写的：

- 用的 `rrule` 是 `FREQ=HOURLY;BYMINUTE=0`（每小时）
- `to` 恰好落在整点 `T(1,2)` = 02:00

于是 `from` 虽然漏掉了 01:00 那个点，区间 `(01:00, 02:00]` 里还有 **02:00** 兜底，
`fired` 依然是 1、`cycles` 依然是 1，断言全过。

真机是 `FREQ=WEEKLY`，下一次触发在一周后 —— 没有「下一个整点」来兜底，漏洞就直接暴露成「完全没跑」。

**教训：用高频 rrule 测低频调度，等于用稠密数据掩盖边界 bug。**

## 四、修法

### 修 1：首次触发的搜索起点往前挪 1 秒

`src/recurring.js` `tick()`：

```js
const from = job.lastFiredAt
  ?? (job.nextFireAt ? new Date(Date.parse(job.nextFireAt) - 1000).toISOString() : job.nextFireAt);
```

只影响「首次触发」，`lastFiredAt` 有值后的行为一个字没动。

### 修 2：到点却算不出触发点时留痕

```js
const fires = selectFires(job, from, at);
if (!fires.length) {
  writeAudit(db, { actor: 'scheduler', action: 'job_due_no_occurrence',
    newValue: `${job.jobId}:nextFireAt=${job.nextFireAt} from=${from} at=${at}` });
}
```

以前这类「算不出来」是一声不响的。现在不管什么原因，只要到点了却没建卡，审计里必有一条。

### 修 3（补跑时才发现）：中文 jobId 根本没法通过 URL 操作

CEO 起的循环任务 id 是中文标题（`JOB-demo-editor-每周体检-…`），而 `url.pathname` 保持 URL 编码态。
路由拿到的 `jobId` 是 `JOB-demo-editor-%E6%AF%8F…`，查库永远查不到 —— `fire` / `pause` / `resume` / `revise`
一律回「循环任务不存在」。**看板上那些按钮其实一直是坏的**，只是之前没人点过。

`src/server.js` 加 `safeDecode()`，循环路由的 jobId 与 revise 的 jobId 都先解码。

## 六、这次的教训（给以后的自己）

1. **调度器只有「跑起来」和「静默消失」两种状态时，等于没有调度器。** 任何「到点却没动静」的路径都必须留审计，不能只在成功时记账。
2. **推进时钟和完成动作必须是同一件事。** 现在的 `tick()` 尾部无条件推进 `nextFireAt`，跳过一次就等于放弃一整周。修复只是补住了首次这一步，结构性隐患还在——如果哪天 `fire()` 抛异常被吞，同样会白白推进。RT-4 的审计是给这种情况留的报警器。
3. **测试的 rrule 频率要和生产一致。** HOURLY 掩盖 WEEKLY 的边界，是这次漏测的直接原因。
4. **中文 id 进 URL 这件事，全项目只此一处，但恰好是最关键的操作入口。** 凡是「id 由业务数据生成」的地方，都要过一遍编码。

## 七、还没做的

- `tick()` 尾部「无条件推进时钟」的结构没改。稳妥做法是：只有 `fires.length > 0` 或明确判过「确实无触发点」才推进，且推进量要等于最后一个 scheduledAt 之后。改动面比这次大，需要单独一轮 + 完整回归，留作待办。
- 月度体检（`JOB-demo-editor-每月体检…`）同样受「首次触发」bug 影响，修复后已自动免疫；下次 12-01 10:00 触发时按 RT-1 的路径走，第一次真机验证点。

## 八、补记（21:05）：修完「没触发」，又发现「完了不结账」

补跑那一轮验收通过、卡已 `done`，但核对时发现 `cycles.status` 还停在 **`todo`**。

根因在 `recurring.onTaskTerminal`：它只处理 `trigger.type === 'onCompletion'` 的 job，cron 型**直接 return，连收账都不做**。
后果比看起来严重——`overlapPolicy: skip` 会检查「有没有未收账的轮次」，于是**下周一 20:30 会被自己的上一轮挡掉**，
表现为又一次「到点没跑」，但这次审计里会写 `overlap_skip`。

修法：**先收账，再决定是否派生**。收账（`completeCycle`）对所有触发类型都做；
只有 `onCompletion` 型才派生下一轮，cron/event 归各自的触发器。`paused` 的 job 也照样收账（卡跑了就得记账）。

原 G2 测试断言是 `out.skipped === true`——等于「什么都不做」也算过，正好漏掉了收账这一半。
改成断言 `closed: true` + 不派生 + `cycles.status === 'done'`。新增 RT-6 覆盖「上一轮收账后，下一轮不会被 overlap=skip 挡住」。

真机：第 1 轮用 `POST /api/recurring/<id>/complete-cycle` 补收账（cycleNo=1, status=done），
`cycles.status=done`、`lastCycleNo=1`、`nextFireAt=2026-11-23T12:30:00Z`、`consecutiveFailures=0`。

全量 **327 / 327**。
