# 运行观测台：怎么盯、看什么、出问题怎么给我

> 2026-11-17 建立。公司刚开始真机测试，这套东西是**长期工具**，不是一次性脚本。
> 目标：你正常下单，我（或你）能在事后 10 秒内从数据里说清「它卡在哪、谁没被叫、为什么」。

## 一、现在就已经在跑

上一轮已经挂了一个常驻观测进程（每 5 秒采样一次，只读数据库，跑 6 小时自动收）：

```
work-prod/watch/watch-2026-11-17T12-22-26.md      ← 人读，一直在覆盖写
work-prod/watch/watch-2026-11-17T12-22-26.jsonl   ← 机器读，一行一条采样/审计/事件/日志
work-prod/watch/console-latest.log                ← 进程自己的输出（告警也会打在这里）
work-prod/watch/watch.pid                         ← 进程号（当前 37648）
```

**你直接下单就行**，不用管它。它会在新卡出现时自动聚焦，并把这张卡的状态变化、谁被叫过、跑了几轮、报告有没有落盘，逐条记下来。

## 二、两个命令（以后都能用）

```powershell
cd D:\开源\AICompany
npm run watch                    # 常驻观测（默认 5 秒一采，Ctrl+C 停）
npm run watch -- --minutes 120   # 跑两小时自动收
npm run watch -- --task T-xxxx   # 只盯某一张卡

npm run trace -- --latest        # 单卡透视：最新一张
npm run trace -- T-xxxx          # 单卡透视：指定卡
```

`trace` 打印的东西（一张卡的全部证据，按时间摆好）：

- 这张卡被要求做什么（最新 revision 的指令 + 验收条件）；
- 任务目录里到底有什么：`brief.md`、`output/`、`completion.json` 在不在、多大；
- 子卡 / 处置卡：卡住的时候「谁在替它做事」；
- Runs：谁跑的、什么唤醒原因、跑了几分钟、结束没有；
- 变更请求：它有没有「想问你」（这是它唯一合法的询问通道）；
- 事件：谁被叫过、叫了几次、有没有 `processed=0` 卡住没处理；
- 审计时间线：状态机 + 升级 + 补审 + 收尸的完整轨迹；
- 审批单：唯一合法的人工停点。

## 三、观测台会自己抓这几类问题

| 规则 | 阈值（默认） | 说明 |
|---|---|---|
| 卡停在同一状态 | 10 分钟 warn / 30 分钟 alert | 覆盖 `todo`、`in_progress`、`awaiting_decision` |
| **blocked 但没人管** | 5 分钟 alert | 停在 blocked、又没有处置卡、也没有待批单 —— 这是上一轮「卡死 28 分钟」的形状 |
| run 跑太久 | 15 分钟 warn / 45 分钟 alert | GUI 一次能跑几分钟，短的不算异常 |
| 事件积压 | 5 分钟 warn / 15 分钟 alert | `processed=0` 的事件超过阈值，说明泵或有东西没消费 |
| 关键审计 | 即时 | `reported_upward`、`blocked_escalated`、`review_requeued`、`run_timeout`、`stuck_escalated`、`report_rejected`、`wake_deferred`…… |
| 日志异常 | 即时 | 日志里出现 `ERROR` / `Exception` / `异常` / `被拒` / `启动失败` |

阈值都能临时改：`--stall-warn 20 --stall-alert 60 --run-alert 90 --blocked-alert 10`。
同一件事 5 分钟内只报一次，不会刷屏。

## 四、出问题时怎么给我

最省事的说法：**「刚才那单出问题了，卡号 T-xxxx（或直接说卡标题）」**。我会：

1. `npm run trace -- T-xxxx` 看这张卡的全链路；
2. 从 `work-prod/watch/` 里最近那份 `.md` 对时间线（告警 + 状态变化 + 审计）；
3. 需要的话再跟 `work-prod/logs/server-YYYY-MM-DD.log` 对一下；
4. 然后告诉你：是模型没照流程、是引擎漏了事件、是 GUI 没起来，还是配额/锁的问题 —— 以及要不要动代码。

你也可以自己先瞄一眼 `.md` 的「## 现在」和「## 告警」两节，通常 30 秒就能判断「它是在跑、还是在等人」。

## 五、常见形状对照（先自己看一眼也能定性）

| 你看到的 | 十有八九是 | 去看哪里 |
|---|---|---|
| 卡显示「进行中」但一动不动 | GUI 席位没被叫醒 / 抢不到前台 / 某条命令挂住了（现在命令有 60 秒上限，挂住会明确失败） | 先在看板点这行的「重派」；再看 `trace` 的 Runs 段有没有 `running` 不结束 |
| 卡显示「待验收」很久 | 验收事件被吞（上一轮已修，现在 1 分钟自动补审，最多 5 次） | 审计里找 `review_requeued` / `review_stuck` |
| 卡显示「阻塞」很久 | 要么已上报但上级处置卡也没动静，要么根本没人管 | 审计 `reported_upward` / `stuck_escalated`；`trace` 的子卡段 |
| 工程岗说「已派给下级」，子卡却一直是待办 | 父卡占着会话在等下级接单（旧制度就是这么教的），引擎腾不出手叫下级 | 审计 `parent_wait_cut`；父卡会被自动置为「等子卡」（生产 8 分钟触发） |
| 父卡把自己派出去的子卡取消了 | 这就是绕过流程（现在会被硬闸拒绝：`PARENT_CANNOT_CANCEL`） | 审计 `cancel_child_rejected` / `cancel_task` |
| 「挂起待决策」 | 变更请求在等拍板；决策者是员工时应已自动建处置卡 | `trace` 的变更请求段 + 子卡段 |
| 员工在会话里问「要不要…」 | 它没走变更请求通道（提示词已明令禁止，但仍可能犯） | `trace` 里变更请求为空 + run 超时 / 报告不合格，就是这种形状 |
| GUI 没起来 | 激活慢、被弹窗挡住、锁被别人占 | `trace` 的 Runs 段 + 审计 `wake_deferred` + 日志 |

## 六、边界（刻意为之）

- 观测台**只读**数据库，不写库、不唤醒任何人、不改任何状态 —— 观测不许影响被观测的系统；
- 它不替代引擎的看门狗：引擎自己在心跳里补投/上报，观测台只负责**留证据**；
- 关掉进程就停（`Stop-Process -Id (Get-Content work-prod\watch\watch.pid)`），不留系统配置、不留计划任务；
- 采样文件按启动时间命名，一天可以起很多份，不会互相覆盖。
