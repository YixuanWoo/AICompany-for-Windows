# 交付路由：谁发布，谁审计

> 一句话：**活是谁派的，结果就回谁那儿。董事会派的不惊动总经理，总经理派的不许员工自己结案；董事会有权让任何一张卡直接落盘，也有权自己看。**

落地时间：2026-11-16。全部有测试与真机验证，`npm test` 341/341、`doctor:prod` 8/8。

---

## 一、为什么之前不对

之前只有一个全局开关 `artifacts.defaultHandoff`（`ceo` 或 `land`）：**所有卡一刀切**。
问题：

- 董事会直投给豆包一张译稿，干完还要叫总经理跑一轮验收 —— 白烧一次按量计费的额度；
- 总经理拆给豆包的活，豆包自己写 `handoff: land` 就能免掉验收 —— 发布者永远不知道结果。

这两种错误方向正好相反，一个开关治不了。正确的解法不是再调开关，而是**看发布者是谁**。

---

## 二、三种发布者，三种默认

| 谁发布的 | 默认去向 | 谁审 | 为什么 |
|---|---|---|---|
| **董事会**（人） | 干完直接落盘 | 不审（机器按卡上的验收条件判） | 只对董事会负责，不必层层上报 |
| **上级 agent**（总经理派给员工、工程派给豆包） | 回发布者审 | 发布者本人 | 谁派的活谁负责，发布者必须看到结果 |
| **认不出**（老数据 / 系统代派） | 按下单时配的兜底 | `defaultHandoff` 决定 | 保守：默认交审 |

补充两条硬规则：

1. **受管代码永远要审**（`managed-code`），不管谁发布的 —— 代码是以后还要改的东西。审查人默认工程岗。
2. **卡上写明了「谁来审」，就是要审** —— 即使董事会直投，也不会被默认落盘吞掉。

## 三、董事会怎么改路由

三种写法，任选：

### 1）原话里说（最省事）

下单文字里出现「给我审」「等我批」「我先看」「我过目」这类明确说法，引擎自动把这张卡记成**董事会亲审**，并留一条 `review_intent_detected` 审计。

否定说法会被排除：「不用给我看」「不必我审」不会被误认。

### 2）下单时写字段

```json
POST /api/requests
{
  "mode": "direct",
  "addressedTo": "doubao",
  "text": "翻译第三段",
  "reviewBy": "human",      // 交董事会自己审；写 board / me / 我 也认
  "handoff": "review"       // 可选：land=直接落盘、review=交审、escalate=上报
}
```

- `reviewBy` 也可以写岗位（`engineering`）或担任者 id，引擎会归一成「人」；
- 写不存在的岗位直接报错，不静默当没写；
- `handoff: land` 是「明确要求直接落盘」，优先级高于一切推导（受管代码除外）。

### 3）看板上改

任务卡现在直接显示「谁发布的 / 审查人」两列。要看结果就去「待我拍板」区。

## 四、待董事会拍板长什么样

董事会亲审的卡交活后：

1. 卡停在 `in_review`，任务表里标「**等你拍板（审批区里能看到结果）**」；
2. 「待我拍板」区出现一张单，摊开的是**结果本身**，不是卡片元数据：
   - 谁干的、归属项目、**干了什么**（执行人写的总结）
   - **产出哪些文件**（逐个列出）+ 文件在磁盘上的位置
   - **验收条件过没过**（✓ / ✗ 逐条）
3. 两个按钮 + 一个意见框：
   - **通过** → 卡立即 `done`，写项目记忆、落盘（项目配了 `rootDir` 才落），出简报；
   - **打回重做** → 卡退回 `in_progress`，重新叫醒执行人，**意见原样带过去**（它下一次只看这一句）。

实现位置：`kind: 'task_review'` 的审批单；判定在 `engine.decideApproval` 的 `task_review` 分支。

## 五、三道闸（员工不能自己放水）

| 闸 | 拦什么 | 后果 |
|---|---|---|
| 自报落盘降级 | 上级派的活，员工写 `handoff: land` 想免审 | 改成交审 + 审计 `handoff_downgraded` |
| 审查人越权 | 员工把审查人指成自己或同级 | 忽略 + 审计 `review_by_rejected` |
| 代码免审 | 受管代码想走落盘 | 强制 `review`，审计记 `codeForced` |

例外只有一种：**发布者在卡上写了 `allowSelfLand: true`**（授权员工自己判）。
CEO 拆卡时对纯归档的活可以这么写；否则默认不给。

> 为什么这么设计：判断权可以下放，但「免除审计」的权力必须留在发布者手里。
> 员工能自己免审，等于没有审计。

## 六、谁在代码里干什么

| 位置 | 作用 |
|---|---|
| `tasks.assignerId` | 发布者落库（`human` = 董事会，其余是 agent id） |
| `tasks.handoff` | 发布者指定的路由，空 = 按发布者推导 |
| `tasks.allowSelfLand` | 是否授权员工自己判落盘（默认 0） |
| `resolveHandoff()` | 路由判定：卡上写死 > 执行者自报（受限）> 按发布者推 > 兜底 |
| `issuerOf()` | 认发布者：岗位 id 与担任者 id 两种都认 |
| `reviewerOf()` | 认审查人：显式指定 > 代码默认工程岗 > 发布者 > 总经理 |
| `checkReviewBy()` | 员工指定审查人的闸（只能指汇报链上级 / 默认审查人 / 董事会） |
| `requestTaskReview()` | 董事会亲审时把结果摊成待拍板单 |

`config/company.prod.yaml` 的 `artifacts.defaultHandoff` 现在是 `byAssigner`，**只对认不出发布者的卡生效**，正常卡不看它。

## 七、真机验证（2026-11-16 22:04）

```
提交：mode=direct → engineering，原话「…写完交活，给我审一下」
  ↓  引擎自动识别：reviewBy=human（审计 review_intent_detected）
领活 → 写 output/routing-check.md → 交活（handoff=review）
  ↓  卡停在 in_review；生成 AP-c3605a04（kind=task_review）
  ↓  审批单里能看到：谁干的 / 干了什么 / 产出 output/routing-check.md / 验收条件
点「通过」（decidedBy=board）
  ↓  卡 done，简报 BRIEF-26 生成
```

## 八、和「代码审查」的关系

代码走的是另一条线，不要混：

- 受管代码 → 永远 `in_review`，审查人是工程岗（或仓库台账里写的 `reviewer`）；
- 工程岗用 `node scripts/seat.js --as engineering reviews` 看待审、`verdict` 给结论；
- 审过才 `node scripts/repo.js commit / push`。

董事会亲审只针对「你想亲自看结果的活」，不替代代码审查。
