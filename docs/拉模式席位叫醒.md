# 拉模式席位为什么「排队中」，以及叫醒怎么补

> 2026-11-16 真机事故：董事会在看板上直投一张卡给工程执行岗，看板一直显示「排队中」，
> 他收不到任何提示，以为系统连不通。实际链路全通——是没人叫醒那个席位。

## 一、事故复盘：断的不是管道，是叫醒

| 时刻 | 实际发生了什么 |
|---|---|
| 23:12:00 | 董事会在看板投卡 → 建卡成功（T-c9f6783b），事件 `issue_assigned` 落库 |
| 23:12:00 | 调度器处理事件，发现工程岗 `dispatch: pull` → 写一条审计 `queued_for_pull`，**然后就没有然后了** |
| 23:12 → 23:33 | 卡停在 `todo`。看板显示「排队中」。董事会什么都没收到 |

**为什么工程岗是 pull**：它的担任者是一个会话里的 agent，没有常驻进程。控制面在它不在的时候
派活，只会白烧一次 Run 然后失败。所以设计成「卡留队列，等它自己来领」。
这个设计本身没错，错的是**没告诉人**。

## 二、修了什么

### 1. 排队必须出声（`notePullWaiting`）

卡排进 pull 席位时，立刻做三件事：

- 消息区写一条 `notice`：`等你领：<卡名>`
  - 正文讲清三件事：**谁派的、为什么停着（人叫才醒、没有常驻进程）、怎么让它动（说一句「领活」）**
- 桌面通知同步弹（`scene: 'pull'` 已加进通知渠道白名单，否则会被静默吞掉）
- 同一张卡只提醒一次：重投、依赖放行不会刷屏

### 2. 看板上不再只有「排队中」

`holdReasons()` 给拉模式排队的卡补一句：

```
等「工程执行」来领：该席位人叫才醒，不叫不会自己动
```

### 3. 卡在等人审的循环卡，也照样提醒（上一轮已有）

循环轮次卡停在工程岗手上时，会留一句「等你审：第 N 轮做完了」，否则下一轮会被
`overlapPolicy=skip` 当成「上一轮还没完」跳掉，而循环卡本身不出声。

## 三、仍存在的根本限制

提醒解决了「不知道为什么排队」，但**没有解决「自动开工」**。工程岗依然需要一个
会话来驱动。可选的三条路：

| 方案 | 效果 | 代价 |
|---|---|---|
| **定时自动化叫醒** | 每 N 分钟自动检查一次队列，有卡就领了干 | 每次运行消耗少量额度；无卡时几乎为零 |
| **工程岗改常驻 agent** | 像执行岗一样被直接派单、立即开跑 | 需要独立的模型通道，费用更高；且那不是「我」 |
| **保持现状 + 提醒** | 看到提醒说一句「领活」 | 每次都要人开口 |
