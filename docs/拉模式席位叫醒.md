# 拉模式席位：从「排队干等」到「主动唤醒」

> 2026-11-16。真机事故：董事会在看板直投一张卡给工程执行岗，看板一直显示「排队中」，
> 他半小时里没收到任何提示，以为系统连不通。两轮修完：先让它**出声**，再让它**真的把人叫起来**。

## 一、为什么工程岗会「排队」

工程岗配的是 `dispatch: pull`：担任者是一个会话里的 agent，**没有常驻进程**。
控制面在它不在的时候派活只会白烧一次 Run，所以设计成「卡留队列，等它自己来领」。

设计没错，错在两点：
1. 排进队列时**一句话都不说**，人只看到「排队中」；
2. 就算说了，活还在原地 —— 没人来领。

## 二、参照：剪辑工作台怎么做到「随时能醒」

工作台的「交给 Agent」按钮（`工具/agent-bridge/bridge.js`）做了这件事：

```
写任务包 → POST /wake（本地 18765）→ 转发 CodeBuddy Gateway /api/v1/runs
        → 网关往「当前会话」投一条用户消息 → 会话里的 agent 就醒了
```

关键点：**它不需要常驻 agent，也不需要外部 API key**，靠的是「会话宿主的网关能往会话里塞消息」。
凭据（端口 + 密码）每个会话都不同，由 `SessionStart` hook 每次写进
`%LOCALAPPDATA%\LiteCut\bridge-creds.json`，桥接每次重读。

## 三、AICompany 怎么接上这条

### 1. 唤醒客户端（`src/wake.js`）

| 步骤 | 做法 |
|---|---|
| 读凭据 | 只读文件，不写不落日志；显式给 `credsFiles` 就只认它（防串到别的会话） |
| 探忙闲 | `GET /api/v1/status` 看 `data.busy` |
| 投唤醒 | 空闲 → `POST /api/v1/runs`（`type: user_message`，网关只认 `text`） |
| 忙时 | **排队等空闲**，不能硬发 —— 网关会把忙时的消息直接丢掉 |
| 冷却 | 同一张卡 10 分钟内不重复叫（打回重做、心跳重投不刷屏） |

### 2. 接进引擎（`wakePullSeat`）

卡排进 pull 席位的瞬间（`queued_for_pull`）：

1. 消息区留一条「等你领」（讲清谁派的、为什么停着、怎么让它动）
2. **调网关把会话叫醒** —— 唤醒内容写明「哪张卡、跑哪条命令领活」
3. 结果留痕：`wake_sent` / `wake_queued` / `wake_failed`
4. 叫不醒（宿主没开、凭据过期）就**安静退回第 1 步那条提醒**，绝不假装叫过

### 3. 看板不再只有三个字

`holdReasons` 给排队中的拉模式卡补一句：

```
等「工程执行」来领：该席位人叫才醒，不叫不会自己动
```

## 四、边界（必须知道的几条）

| 情况 | 行为 |
|---|---|
| 会话宿主完全没开 | 网关探不通 → 记 `wake_failed`，只剩提醒 |
| 登录会话正忙（正在跑别的回合） | 排队，等空闲补发；最多等 10 分钟 |
| 一张卡反复排队 | 10 分钟冷却，不重复叫 |
| 同一会话多张卡 | 每张各叫一次，网关侧合并；不会刷出一堆重复消息 |
| 关掉唤醒 | 配置 `wake.enabled: false`，退回「只提醒」 |

## 五、代价与取舍

唤醒消息会**出现在那个会话的对话框里**（它本质是一条投给会话的用户消息）。
这是「主动唤醒」的必然表现：要想让会话里的 agent 动起来，就得往会话里投东西。
内容里已标明「这条不是董事会发的，是控制面在叫醒你」，不会和真人发言混淆。
