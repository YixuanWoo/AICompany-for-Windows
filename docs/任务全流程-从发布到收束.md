## 一、一张卡的一生（状态机）

状态转移写死在 `src/core.js` 的 `TRANSITIONS`，非法跳转直接抛错并留 `illegal_transition` 审计 —— 卡不会静默乱跳。

| 状态 | 人话 | 谁能推到下一步 |
|---|---|---|
| `backlog` | 收件箱 | → `todo`（被排期） |
| `todo` | 排队，等被叫 | → `in_progress`（事件泵派活成功）/ `paused` / `cancelled` |
| `in_progress` | 正在做（有 run 或马上有） | → `in_review`（交活合格）/ `blocked`（走不下去）/ `awaiting_decision`（等拍板）/ `cancelled` |
| `in_review` | 待验收 | → `done`（审过）/ `in_progress`（打回返工）/ `cancelled` |
| `blocked` | 卡住，已向上汇报 | → `todo`（处置卡救活）/ `cancelled` |
| `awaiting_decision` | 挂起等决策（不烧额度） | → `in_progress`（决策回来了） |
| `done` / `cancelled` | 终态 | 不可再动 |

终态只有两种正常出口：**验收通过（done）** 或 **走不下去（blocked，且必然伴随一张向上级的处置卡）**。人只在一种情况下被拉进来：汇报线到顶（见第六节）。

## 二、全流程 8 步

### ① 下单（董事会 → CEO）

- 入口：看板 / `POST /api/tasks` / `POST /api/bridge/submit`，统一走 `engine.submit → route()`。
- 默认 `mode: delegate` → 承接人固定是 CEO；`mode: direct` 才是人直接点名某个席位（跳过 CEO）。
- 建卡（`buildCard` + `insertCard`）→ 状态 `todo` → **发一条 `issue_assigned` 事件** → `pump()` 立刻消费。
- 人写的原话同时进 `instructions`（不只是标题），否则席位收到一句空话。

### ② 派活（事件泵 → 席位）

`pumpOnce()` 取事件 → `handleEvent('issue_assigned')` → `wake(taskId, agentId, wakeReason)`。

`wake` 是一串闸门，任何一道没过都不会开新 run（`src/engine.js:1059`）：

| 闸 | 拦下之后 |
|---|---|
| 配额（`runPolicy` → `checkQuota`） | `wake_rejected quota` → 卡退回 `todo`，等心跳重投 |
| 卡间依赖 `dependsOn` 没满足 | 不派；上游 `done` 时由 `releaseReadyDependencies` 放行 |
| 全局并发上限 `maxConcurrent`（公司档 2） | 退回 `todo` |
| 冷却 `cooldownSec` | 退回 `todo` |
| 席位 `dispatch: pull` | 不发事件，走 `queued_for_pull` + 叫醒 + 冷却 |
| 环境检查（GUI 窗口 / 锁 / 依赖） | `env_check_failed`，退回 `todo` |
| 临时闸 `precheck`（用户正在用键鼠） | `gate_blocked` → 退回 `todo` + 秒级自检（不记失败、不烧额度） |

全过 → 建 `run`（`status=running`）→ `adapter.execute(ctx)` 跑**整趟会话**（GUI 席位就是几分钟）。`ctx.briefing` 由引擎统一注入身份、边界、派活 SOP —— 所有 adapter 共用同一份，不再各拼各的。

### ③ 执行（席位内部）

- GUI 席位：起窗口 → 新开会话 → 贴指令 → 轮询 `output/report.draft.json`（或 `completion.json`）→ 收尾。
- 每条 GUI 命令 60 秒上限（`gui-driver`），超时杀进程树并抛 `GuiError('timeout')`。
- 拒答"卡住了"的两种正常产出：`change-requests/<id>.json`（要拍板）、`report.handoff = escalate`（主动上报）。

### ④ 交活（`handleResult`，所有分叉都在这里）

顺序很重要：

1. **这一趟是不是已经作废**：run 被 `interrupted`（强制重派 / 重启收尸）→ 结果只留档，`run_result_after_abandon`，不推进状态机。
2. **报告不合格**（schema 错 / `status ≠ success`）→ `attempt+1`：第 1 次自动重投（`retry`），第 2 次 → `blocked` → `escalateToRescue`（转救火席位，或出审批单）。
3. **父卡还有子卡没收尾** → `parent_waiting_children`：卡挂起 `waitingChildren=1`，**不送审**（"我拆了 N 张"不算交付）。
4. **合格** → `inferArtifactKind` 判产物类型 → `resolveHandoff` 判去向（`land` 直接落盘 / `review` 交审 / `escalate` 上报）。

### ⑤ 验收（去哪、谁审）

`resolveHandoff` 的决定顺序：卡上写死的 `handoff` > 执行者自报（只能往"更严"改）> 按发布者推（董事会→`land`，上级 agent→`review`）> 受管代码强制 `review`。

`reviewerOf` 决定"谁审"：

| 优先级 | 规则 |
|---|---|
| 1 | 卡上 `reviewBy`（建卡时就定的） |
| 2 | 代码活：仓库台账的 `reviewer` → 公司默认 `artifacts.defaultReviewer` |
| 3 | **谁发布谁审**：发布者是员工 → 该员工本人；发布者是董事会 → CEO |

三种落地方式：

- 审的人 = **CEO** → 发 `review_requested` → CEO 跑一轮验收 run → `verdict=pass` 即 `done`（落盘 + 项目记忆）；`reject` → 退回 `rework`（自动一轮，二轮转救火/审批）。
- 审的人 = **董事会（人）** → 出「待你拍板」审批单，不叫任何 agent（`task_review_waiting`）。
- 审的人 = **其他员工**（如工程岗审子卡）→ 只写 `review_queued`，卡留 `in_review`，等它自己 `seat.js reviews` / `verdict` 来审（**拉式**）。
- 直投卡（`mode=direct` 且不需要审）→ 机器验收直接 `done`（`machine_acceptance`）。

### ⑥ 收束（子卡 → 父卡 → 发布者）

子卡到终态（`done` / `blocked` / `cancelled`）时，`transition()` 会调 `settleParent()`：

- 父卡必须正挂着（`waitingChildren=1`）；
- 子卡全部收尾 → CAS 抢位 → 拼 `output/总任务汇总.md` → 父卡转 `in_review` → 按父卡自己的路由送审（通常就是 CEO）；
- 父卡 `done` 才是"整摊活收账"。

所以"最终向 CEO 收束"是成立的，但有两条不同的路：

1. **逐张收束**：每张卡干完各自回发布者审（发布者是 CEO 就到 CEO）；
2. **汇总收束**：中层父卡挂起等子卡 → 全部收尾 → 一份总账送 CEO。

### ⑦ 落盘与记忆

`done` 之后：`deliverAccepted` 把产物放进项目目录（`work-prod/projects/<项目>/…`）、`flushProjectMemory` 写项目记忆、`noteTaskTerminal` 在消息区给人一句人话（不含技术细节）。

### ⑧ 依赖放行

某张卡 `done` → `releaseReadyDependencies` 检查哪些卡的 `dependsOn` 全满足 → 给它们发 `issue_assigned`。这是"接管做完才发版"这类顺序的落地。

## 三、父子卡机制（这是最容易被误解的一段）

**关系只有两个字段**：子卡 `parentTaskId`、`assignerId`。没有别的父子结构。

**派子卡要过四道闸**（`spawnChild`）：

1. 只有**这张卡的承接人**能拆它（`assignerId === parent.assignee`）；
2. 席位必须有 `delegate` 能力；
3. 只能派进自己的汇报子树（`assertMayAssign`）；
4. 有下级时**不许派给自己**（`spawn_self_rejected`）—— 防"换个名字继续自己干"。

**子卡什么时候开始跑？** 派出去那一刻就开始排队，**不需要父卡结束**：
`insertCard` 直接发 `issue_assigned`，事件泵消费到就开跑；只有显式写了 `after`（依赖）才串行。

**但当前有一个真实限制**：事件泵是串行的（一次只 `await` 一趟 run），所以"父卡自己的会话还在跑"时，子卡的事件只能排队 —— 看起来就像"父卡不结束、子卡起不来"。这也是 2026-11-17 那次"父子互卡"的真正机械原因。压住它的两条措施：

- 制度：父卡**派完即交活、会话立刻结束**（`org-chart.js`）；
- 兜底：父卡有未收尾子卡却还占着会话超过 8 分钟 → 引擎判 `interrupted` + 置 `waitingChildren=1`（`parent_wait_cut`）。

**父卡会等子卡吗？** 会，但只在"父卡已经交活、子卡还没收尾"时：卡挂起（`waitingChildren=1`），**不占 run、不占会话**，等最后一张子卡收尾自动汇总。

**子卡失败也算收尾**：`blocked` / `cancelled` 进入 `CHILD_CLOSED`，父卡照样汇总，只是汇总里标"没成"。

## 四、向上汇报是什么形态

**不是一份文档，也不是一条消息，而是一张卡**：

```
role: escalation
parentTaskId: 原卡
assignee: 汇报线上的上级（doubao → engineering → ceo）
instructions:
  【原卡】【执行人】【卡在哪】【已做到哪】【产物】【仓库】
  【你要决定的一件事】1) 改方案返工 2) 改派 3) 上报总经理
acceptance: 明确给出一条处置
```

同时原卡转 `blocked`（`escalated`），同一张卡不会重复建第二张（`hasOpenEscalationCard`）。

处置卡收尾后 `resumeParentAfterEscalation`：

- `blocked → todo` / `awaiting_decision → in_progress`、`attempt` 归零；
- 发 `rework` 事件，带 `reviewNote = 上级处置：…`，原执行人带着意见重跑；
- **最多救活 2 次**，第 3 次继续往上汇报（防"上报→返工→再上报"的额度黑洞）；
- 处置卡自己也办不成 → 再往上一层报。

**到顶才算人工停点**：决策者就是自己（`resolveDecisionMaker` 返回 CEO 自身）时归 `human`，出审批单 —— 这是全流程**唯一**合法停下来等人的地方（`reported_to_board`）。

## 六、三个"名义上成立、实际有差"的地方（必须知道）

**① 泵串行 = 实际并发 1。** `maxConcurrent: 2` 只在"两趟 run 真的同时开"时才有意义，而现在 `pumpOnce` 是 `await handleEvent` 串行跑，一趟 GUI 会话（几分钟）就把队列按住。后果：父卡派完子卡后，子卡要等父卡那一趟结束（或 8 分钟兜底）才开跑。

**② 中层验收：2026-11-17 已修（原来实际由 CEO 代审）。** 以前验收请求只写一条 `review_queued` 就撒手，中层是拉模式、不会被叫醒；心跳补审 60 秒后又一模一样发给 CEO。修完之后：

- 交活时就**直接把验收请求发给真实审查人**（`review-seat:<task>:<run>`，不再等心跳）；
- 心跳补审按真实审查人分流：人审 → 不补（审批单已经出了）；中层 → 先叫它审；超 `seatReviewFallbackMinutes`（生产 20 分钟）还不审才转 CEO（留 `review_fallback_ceo` 账）；
- 中层被叫起来的那一趟是**验收会话**，它的提示词单列一段「这次是验收，不是干活」（`reviewerBriefing`），结论只有两条合法来路：会话里 `seat.js verdict`，或报告里给 `verdict`；
- 它跑完不给结论 → 引擎**不替它判**（`seat_review_no_verdict`），卡留在待验收，心跳继续兜底。


**③ CEO 的卡拆完立刻 done。** `tasks_created` 之后 CEO 卡直接 `in_review → done`（它只负责排班）。所以"一张总账收束到 CEO"只发生在**中层父卡**（`waitingChildren`）那条路；CEO 这一层收到的是 N 张子卡各自来验收。

## 七、拿真机的一张树对照着看

```
T-54be99b6  CEO：'桥接不碰，其余该修就修，安排下去'          → done（排完班即收账）
├─ T-61275b02 工程岗：第一批（写盘原子）                      → 派子卡 → waitingChildren=1
│   └─ T-a2a8d257  doubao：写盘收成唯一原子入口                → 执行中
├─ T-ce6f865d 工程岗：第二批（归档/撤销）                     → 独立执行
└─ T-2b69dbca 工程岗：第三批（配置隔离 + 改根目录提示）        → waitingChildren=1
    ├─ T-4f1f38d8 doubao：数据目录隔离
    ├─ T-4c84816f doubao：改根目录要提示
    └─ T-d93c1fb7  ← 曾被工程岗自己取消（现已被硬闸禁止）
```

看这张树时的三个判据：

1. 父卡 `waitingChildren=1` + 子卡 `todo/in_progress` → 正常，子卡在排队/在跑；
2. 父卡 `in_progress` 但有子卡且没有 run → 刚被 `parent_marked_waiting` 接手，下一拍会置等子卡；
3. 子卡 `cancelled` 且取消人是父卡 → 现在会被 `PARENT_CANNOT_CANCEL` 拒掉，看到历史数据里的这种卡，说明是旧行为。
