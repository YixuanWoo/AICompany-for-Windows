> 阶段：P3（清单 P3-1 ~ P3-5 + G-P3），2026-11-15 完成并自主验收。
> 验收结果：`npm test` 全量 **126/126** 通过（新增 `tests/p3.test.js` 31 条）；真实 HTTP 落盘冒烟全通过。

## 一、这步到底是咋回事（大白话）

P3 之前，干活的是「命令行 agent」：控制面把任务包塞给它，它在黑框框里干完，把结果直接吐回来。但现实中还有另一类干活方式：**人坐在一个图形界面（GUI）软件前面，把任务粘进去，软件在窗口里跑**。

让 AI 公司能派活给这种「窗口型选手」，就是 P3。规矩只有一条核心：**只认文件，绝不读屏**。

打个比方：GUI 软件就像一个只收信件的邮局柜台。控制面不趴在玻璃上偷看柜台里发生什么（不读屏、不 OCR、不看窗口标题判断任务完没完），而是：

1. 把一封信（提示词）放进信封（任务目录）；
2. 按配置里写的动作把信递进去（激活窗口 → 快捷键 → 粘贴 → 回车，每一步都来自配置，源码里零写死）；
3. 然后就蹲在投递口等**文件**：窗口那边干完了，会把「完成报告」和「产物」写成文件放在约定目录；
4. 控制面拿到文件先验真伪（schema、验收项、checksum、不许把文件写到约定目录外面），验过了才算完成。

这样不管对方是豆包、是你手工操作、还是任何窗口软件，控制面都不挑——因为控制面根本不在乎窗口里是什么产品，只在乎文件到没到。

## 四、验收前修掉的坑（自主推演 + 测试暴露）

1. **默认提示词模板漏了 `{{changeRequestsDir}}` 绝对路径**——agent 想中途变道都不知道把变更文件写去哪；补上后模板槽位校验才全线通过。
2. **4 处测试里 `engine.submit()` 忘了 `await`**——异步没等完就去断言，链路假失败；修掉。
3. **环境检查失败最初只 `skipped` 不回写任务状态**——违反任务书 §8.6「任务留 `todo`」；补了补偿回写 + 审计。
4. **`createServer` 返回的是原始 `http.Server`**，冒烟脚本想当然直接 fetch 被拒；改成显式 `listen(0)`。

## 五、老实交代的边界与偏差

1. **本轮全部用「模拟驱动」验收**。`gui-driver.js` 里的 `command` 驱动已经支持把真实窗口操作命令全部由配置提供（激活 / 按键 / 粘贴 / 截图命令都来自 `gui-template` 配置，源码零写死），但**没有真去抢过任何真实窗口的焦点**——那是你之前明确说「后续针对 Windows 优化再考虑」的部分，本轮不碰。
2. **变道后任务卡停在 `in_progress`**，这是**按分阶段设计刻意留的**：`awaiting_decision` 挂起 + 现场快照 + 四种出口（resume / redo / derive / cancel）整体属 **P4-8**（任务书 §12 / 开发清单原文）。P3 只负责「不判失败、不重试、变更请求落库交控制面」，这条已验。
3. **GUI 审计动作不单独写**：提示词 / 焦点 / 锁的证据都在磁盘（`task.json`、`prompt.txt`、`screenshots/`）和驱动 trace 里，`audit` 表只记状态转换与变道事件——避免重复留痕。
4. **超时判定靠轮询次数上限**（`maxPolls` + `pollIntervalMs`），不是真实墙钟挂表；效果等价（到点没文件就判失败 + 截图留证），实现更简单。
5. **`gui-template` 是通用 adapter 类型名**：配置里给什么窗口标题就是什么产品，源码里没有任何具体 GUI 产品的名字（开源可移植，§6B）。
6. **互斥锁是进程内的**：同一控制面进程内绝对互斥；跨进程场景由可选文件锁（`lockPath`）承接，本轮未启用。
7. **G-P3 的 10 连发在测试里是顺序提交**（真实 GUI 场景本来就受互斥锁约束同一时刻只有一个在跑），不是并发压测——并发互斥在 P3-1 用双请求测试单独验了。
