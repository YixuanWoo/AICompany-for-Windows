# 工程岗不下场：身份注入断了，派活手段也没给

> 2026-11-17 董事会问：「CEO 能顺畅把任务交给工程，但工程执行总自己干活，不往执行层派。
> 是提示词注入的问题，还是身份文档的问题？」
>
> 答案：**两个都是，而且是同一处断口**——身份与组织图只注入了 webhook 席位，
> GUI 席位（工程岗现在坐的那条路）拿到的是光秃秃的「你是执行席位」；
> 再加上提示词从来没告诉它「派活用哪条命令」，它就算知道自己该派，也没有手。
> 另外还有一个结构性漏洞：子卡可以派给自己。

## 一、真机证据（不是猜测）

`work-prod` 库里，工程岗接过的最典型三张卡：

| 卡号 | 谁派的 | 工程岗实际做了什么 |
|---|---|---|
| T-1301cc93 | 总经理 | 自己读源码、复现、修 bug、跑门禁、推 CI —— 全程自己干 |
| T-465c3869 | 总经理 | 自己推送、自己盯 CI —— 全程自己干 |
| T-906d3686 | 总经理 | 拆了 5 张子卡（T-2808b112 / T-ea66c981 / T-6bbc9f72 / T-2d0ed7e9 / T-ec534530），**5 张的 assignee 全是 engineering 自己**，标题都是「逐条复核与验收取证」 |

第三行最关键：它确实「拆」了，但拆出来的每一张又落回自己手里 ——
表面上走了拆解流程，实际一张都没到执行岗（doubao）。
审计里 6 条 `spawn_task`，只有 1 条（T-5f7f52f6）真的派给了 doubao。

打开 `tasks/T-1301cc93/brief.md` 看它当时收到的原文，第一句是：

```
你是本公司的一个执行席位。请完成任务，并把结果写成文件。
```

往下是完整的实现要求（先写失败断言、改代码、`build.ps1` 0 警告、推 CI）。
**全文没有一个字提到**：这个席位是工程岗、它的下级是执行岗、它不许自己写代码、
它可以派卡、派卡的命令是什么。

## 二、根因一：身份只注入了 webhook 席位，GUI 席位漏了

`src/org-chart.js` 里的 `seatBriefing()`（你是谁 / 组织图 / 边界 / 上报规则 /
交付路由 / 仓库台账 / 拆完卡别急着交）是写得很全的，但它只被
`src/adapter-webhook-exec.js` 调用 —— 也就是 8080 上那个按量计费的规划 agent。

工程岗在 2026-11-17 从 `seat`（拉模式）改成了 `gui-template`（抢窗口、Ctrl+N、贴卡、回车）。
`src/gui-adapter.js` 的提示词只走 `src/gui-prompt.js` 的模板：

- `DEFAULT_PROMPT_TEMPLATE` / `DRAFT_PROMPT_TEMPLATE` 只讲「产物写到哪个目录、报告写到哪个文件」；
- 模板里连「你是谁」都没有，更别说岗位边界、下级是谁、能不能派卡；
- `config/company.prod.yaml` 里 engineering 岗位的 `duties` / `boundaries` 写得再准，
  **根本没有代码把它读进 GUI 提示词**。

所以换轨那天，工程岗的身份就悄悄退化成「一个执行席位」了 —— 这是**提示词注入**的问题，
不是身份文档的问题：文档是对的，只是没人把它送到那个窗口里。

## 三、根因二：没有任何一句话告诉它「用哪条命令派卡」

即使身份注入补上，「工程岗该派活」也还是一句空口号。系统里真有派活接口：

- CLI：`node scripts/seat.js spawn --as engineering --parent <本卡> --assignee doubao ...`
- HTTP：`POST /api/bridge/spawn`（本机 127.0.0.1:3100，本地单机免 token）
- 引擎侧 `spawnChild()` 的三道闸：必须是本卡承接人、必须有 delegate 能力、只能派进自己的子树

能力齐了，但**提示词里一次都没出现**。模型看不到工具，就只能用自己手里的手
（读文件 / 写文件 / 跑命令）去完成卡上的事 —— 这不是它不服从，是它没有别的路径。

## 四、根因三：子卡能派给自己（结构性漏洞）

`src/org.js` 里「自己是自己的上级也算合法」是为「给自己派活不越级」留的，
结果 `spawnChild` 也允许 `assignee === assignerId`。
于是最省力的「拆解」出现了：把一张卡拆成 5 张复核卡，全派给自己，
既满足了「我拆了」的仪式感，又不必把活真的交出去。

对比 CEO 那边早就有一道硬闸（`resolveChildSeat`：总经理点自己的名字会被强制改派给执行席位），
工程岗这条线一直没有对应的闸。

### 补：CEO 侧「派活太细」具体压掉了什么

真机卡 T-1301cc93 的 instructions 里有这些句子——全是**工序**，不是结果：

- 「先用一份英文资料复现」「不许跳过复现直接改」→ 该由工程岗决定怎么验证
- 「定位真正没被覆盖的那条路径，报告里写清 文件:行」→ 这是技术判断
- 「补断言覆盖：英文句末三点、点间带空格…；原有 254 条断言一条都不许删或放宽」→ 这是实现手段 + 把方案钉死
- 验收写了 15 条，其中一半是工序清单

新提示词把这类写法列为 ✗ 清单，要求换成结果口径（「修好后用户点一次就能跳过整段省略号」），
并把验收条数压到 3–6 条；要十几条就说明该拆成多张卡，而不是把一张卡写成施工图。


## 六、工程岗现在收到的提示词长什么样

（真机配置渲染出来的开头，节选）

```
【你是谁】
工程执行（engineering），担任者「WorkBuddy agent」。
职责：定技术方案、拆解工程任务并派卡、给执行岗提供技术支持、代码审查、管理代码仓库与 git 提交推送 GitHub
边界：
- 不亲自写实现代码：实现与改 bug 拆给执行岗（骨架/方案产物可直接移交）
...
【公司组织（你在这张图里）】
董事会（人｜最终拍板）
└─ 总经理（ceo）…
   └─ 工程执行（engineering）…
      └─ 执行（doubao） — 开发写代码、改 bug、写文档…
· 下级：执行（doubao）

【你的活是「派」，不是「做」】
- 任务说明里写得再具体，那也只是「需求」，不是让你照着做：把它翻译成
  ①技术方案 ②验收条件 ③边界，然后派卡。
- 能接活的下级：执行（doubao）。派给自己等于换个名字继续自己干，会被控制面直接拒掉。

【派卡就是跑一条命令（在项目根目录，PowerShell）】
node scripts/seat.js spawn --as engineering --parent <你这张卡的编号> --assignee <下级 id> \
  --title "<一句话标题>" --instructions "<完整说明>" --acceptance "条件1;条件2"
  可选：--repo <仓库id>（代码活必须写）；--handoff review（默认回你审）
- 派完不是收工：子卡回来先看结果（node scripts/seat.js reviews --as engineering）…
```

模板原文仍然在后半段（产物目录、`report.draft.json`、硬性要求），顺序是
**身份 → 派活手段 → 分隔线 → 模板**。

## 八、还没解决 / 一个待办

1. **工程岗仍然有「自己干」的手**（能读写文件、能跑命令）。本轮是靠提示词 + 自派闸矫正，
   不是把工具收走。要硬性禁止，只能给它换一条没有写权限的通道，代价是连方案文档都写不了。
2. **本轮改的是提示词约束，不是硬校验**：CEO 如果还是写出施工图，系统不会拦。
   要真拦住，得在 `engine` 的卡片校验里加一条「instructions 里出现 `build.ps1` / `文件:行` 这类
   方法词的卡，审计留痕并打回 CEO 重写」。这是行为改动，容易误伤（董事会本人也可能这么写），
   所以留作待办，等真机上再出现一次再决定。**董事会 2026-11-17 明确表示不需要硬校验**，
   这条按「不做」处理；改用「CEO 每张卡必须带授权话术 + 承接人第 0 步先判断」双保险。
3. 2026-11-17 把工程岗从 `seat`（拉模式）切到 `gui-template` 这件事，
   **只写在 `company.prod.yaml` 的注释里，`docs/` 没有对应记录** —— 建议补一份换轨说明，
   免得下次又出现「文档是 A，配置是 B」的断口。
