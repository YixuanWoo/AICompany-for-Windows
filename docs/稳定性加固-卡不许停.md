# 稳定性加固：卡不许停、动作要慢、卡住要有人管

> 2026-11-17。董事会的原话是：「稍微一偏离就无法继续推」「agent 要确认，必须走引擎向上级汇报，不许在会话里问我」「卡不许停下来，要么验收要么上报」「卡长时间停在一个状态要有跳出机制」「GUI 动作都慢一点，等几秒再下一步」。
> 这份文档写清：现状到底弱在哪、参考项目 paperclip 是怎么做的、这次改了什么、怎么验证、还剩什么。

## 一、为什么「稍微一偏离就推不动」

不是模型笨，是**出口太少**。一张卡走不完时，只有两条路：交合格报告 → 送验收；交不合格报告 → 重试 → blocked。而 blocked 之后，原来的实现是**直接出一张人审批单**，也就是「停下来等你」。于是出现三种典型停摆：

| 现象 | 真实机制 |
|---|---|
| 员工在会话里问「要不要我按 A 还是 B」 | 会话界面里没有上级、也没有董事会。它写出来的问题**不落盘、不产生事件**，控制面只看到「这个 Run 迟迟不交活」→ 超时 → 失败 → 重试 → blocked → 审批单。人看到的是一张卡莫名其妙停住，还附一句看不懂的技术理由。 |
| GUI 明明启动了却没发出去 | `gui-adapter` 每执行一步，**紧接着**就校验一次前台窗口标题。窗口激活是异步的（几百毫秒到几秒），慢半拍就判「失焦」，整趟退回 deferred。人看到的是「它好像起来了，又没起来」。 |
| 卡躺在「待验收 / 阻塞 / 挂起」很久没人管 | `observe.js` 只有**体检项**（`stuck_running` / `stale_event` / `awaiting_overdue`），`engine.js` 的 30 分钟 `stuck` 只是把列表塞进状态输出给医生看。**没有任何一处会因此采取动作**。 |

一句话：以前这套系统的「恢复能力」全靠人盯着看板点按钮。

## 二、paperclip 里值得抄的部分

参考项目是 `paperclipai/paperclip`（MIT，Node.js 服务端 + React 控制台，把一群 agent 当成一家公司来编排）。它把稳定性写成了产品的一等公民，不是靠提示词：

| paperclip 的做法 | 对应到我们这边的问题 |
|---|---|
| **Heartbeat 唤醒队列**：DB 支撑的唤醒队列 + 合并（coalescing），每个 agent 到点被叫起来查活，而不是等人派 | 我们的 `pump` + `reconcile` 心跳就是同一思路；这次把「卡住的人」也接进心跳 |
| **Atomic task checkout**：单 assignee + 执行锁，防止两个 run 抢同一张卡 | 我们早有 `gui-lock` 与「同卡 run 让路」，但让路原来是**静默**的（上一轮已补审计 `wake_deferred`） |
| **Bounded recovery / self-healing runs**：失败只做**有界**恢复，超出边界就把「需要人处理」明确浮出来 | 这次新增的「救活最多 2 次 + 到顶才出审批单」就是这个边界 |
| **Enforced Outcomes（watchdogs, recovery actions, review gates）**：验收门、看门狗、恢复动作是**系统强制**，不是约定 | 这次的心跳看门狗 |
| **Budget hard-stop**：额度到顶自动暂停该 agent 的活，而不是只在面板报警 | 我们的配额闸已有；这次让「复审补审 / 看门狗」都带次数上限，避免为了兜底把额度烧空 |
| **Agent 不能自主招人、CEO 的策略必须先过审**：autonomy is a privilege you grant | 我们的 `gates`（strategy / hiringBudget）已有同类设计，保持不动 |

结论：paperclip 真正值得抄的不是某个算法，而是**「每条失败路径都有一条系统强制的下一步」**这个原则。这次改的就是把这句话落成代码。

## 三、这次改了什么（4 处，全部落盘并已重启生效）

### ① 向上汇报成了硬出口（`src/engine.js`）

- 新增统一函数 `reportUpward(task, {reason})`：**卡走不下去时，先算「汇报线上的上级是谁」**。
  - 上级是员工（总经理 / 工程岗）→ 给他建一张「处理升级：…」的处置卡并叫醒他，原卡状态不再被改写成第二种含义；
  - 汇报线真的到顶（`resolveDecisionMaker` 只能指回自己，或者指向 board / human）→ 才出审批单，**这是唯一合法的「停下来等人」**；
  - 同一张卡已有处置卡在跑 → 不重复建（避免上级被同一件事反复叫醒）。
- `escalation` 事件（blocked 卡的上报）不再直接 `requestApproval`，改为走 `reportUpward`。**上级不再形同虚设**。
- `change_request`（员工写变更请求要拍板）里的 `needsDecision`：决策者是员工时，除了挂起，还会立刻给他建一张处置卡 —— 以前这里只写一条审计就 `return`，卡挂着但**没有任何人被叫醒**。
- 处置卡收尾（done / blocked / cancelled）→ 原卡自动复活：`blocked → todo`、`awaiting_decision → in_progress`，带着上级的处置意见重新派给原执行人（审计 `resumed_after_escalation`）；上级自己也没办成 → 再往上一层报。
- 防止额度黑洞：同一张卡最多被「救活」2 次，超过就不再复活，改走 `reportUpward` 到顶。
- 新增审计：`reported_upward`（谁→谁、为什么）、`change_request_handed_up`、`resumed_after_escalation`、`reported_to_board`。

### ② 卡住看门狗（`src/engine.js` 的 `reconcile`）

心跳里新增第三段扫描，**每分钟**跑：

- `blocked` / `awaiting_decision` 停超过 `stuckMinutes`（公司档 30）：
  - 已有处置卡在跑、已有待批单、已经报过 → 跳过；
  - 否则 `reportUpward` 一次，审计 `stuck_escalated`。
- `todo` / `in_progress` 停超过阈值：常规补投一分钟一次已经在推；只有当这张卡**被唤醒 ≥3 次仍没动**（数 `wake` 审计）才升级为向上汇报，避免两条路一起补投（等于一分钟叫三次）。
- 有人正在跑、依赖没满足、拉模式席位在等人领 → 都不算卡住。
- `reconcile` 返回值新增 `stuckRequeued` / `stuckEscalated`，方便观测。

### ③ GUI 动作放慢（`src/gui-adapter.js` + `src/gui-driver.js`）

- 新增 `waitForeground()`：前台校验不再是「看一眼就判」，而是**在观察窗内反复看**，只有一直不在前台才算真失焦（抛 `GuiError('focus')` → deferred）。
- 每个动作之后加 `settleMs` 等待，再进入下一步；激活之后额外先等一次。
- 默认值（只在真机 command 驱动下生效，simulation 保持 0，测试不被拖慢）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `settleMs` | 1200 | 动作之间等多久（毫秒） |
| `focusTimeoutMs` | 6000 | 激活/切会话后，最长观察多久才判失焦 |
| `focusPollMs` | 500 | 观察窗里的轮询间隔 |

### ④ 提示词里把「不许问人」写成第 ⑤ 条（`src/org-chart.js`）

在 `taskIntakeBriefing` 末尾新增：

- 会话界面上没有上级、也没有董事会；打出来的「要不要我……」**没人回答、也不留记录**；
- 要拍板只有两条路：`change-requests/<crId>.json` 或 `handoff=escalate`；两条都会被引擎变成给上级的处置卡，处置完原卡自动回来；
- 一张卡的结局只有两种：做完送验 / 带理由上报，**没有第三种**。

## 七、补丁（20:50 真机事故后）：手动重派 + GUI 命令上限

### 事故形状（这次是真的抓到了）

20:38 CEO 拆了 3 张卡给工程岗，20:41:07 起跑 `R-387d746b`（卡 `T-61275b02`）。
到 20:50，**十分钟里卡目录里除了 `brief.md` / `task.json` 什么都没有，审计一行没长，run 一直显示 running**。
自动补偿也不动它：卡不是 blocked、也没有积压事件，看门狗要等 30 分钟，`run_timeout` 要等 2 小时。
人在看板前唯一的动作是「再点一次下单」或者重启引擎 —— 这正是要消掉的那个形状。

根因在 `src/gui-driver.js`：`runCommand()` 用 `spawn(shell:true)` 起命令后**没有超时**。
某条命令（激活窗口 / 新开会话 / 粘贴）一挂住，外层 `await mod.execute(ctx)` 就永远等下去，
`wake()` 里的收账、状态机推进全都停在门外。慢不是问题，**没有上限**才是问题。

### ① 每条 GUI 命令都有上限（`src/gui-driver.js`）

- 新导出 `DEFAULT_COMMAND_TIMEOUT_MS = 60000`，`createCommandDriver({ commandTimeoutMs })` 可覆盖；
- 超时后杀**进程树**（Windows 用 `taskkill /T /F`，只杀外层会留下还在跑的子进程 —— 测试里就留过一个 60 秒不退的 node），
  并抛 `GuiError('timeout')`；
- 效果：卡住的那一步明确失败 → Run 收账 → 卡进 blocked → 走上一条已经修好的路（向上汇报），
  而不是「显示进行中、实际上什么也没发生」。

### ② 手动重新派单（看板按钮 / 接口 / 命令）

| 入口 | 用法 |
|---|---|
| 看板 | 任务表每行多一个「重派」按钮；点了就重派，失败原因原样显示 |
| 接口 | `POST /api/tasks/<taskId>/redispatch`，body `{ reason, force }`；**拒绝也返回 200**（业务判断不是服务端故障） |
| 命令 | `npm run redispatch -- T-xxxx`、`--reason "..."`、`--force`、`--latest` |

它做的事（`engine.redispatchTask`）：

1. 清掉「等会儿再试」的短延迟自检；
2. 卡置为 `todo`、`attempt` 归零（否则下一次失败立刻被判死）；
3. 留账：`manual_redispatch`（actor=`human`/`board`/`cli`，记原状态与理由）；
4. 发一条 `issue_assigned`（`wakeReason=manual_redispatch`）并立刻 `pump()`。

守住的界线（不是所有卡都该重派）：

- `done` / `cancelled` → 拒绝（终态就是终态）；
- 还有子卡没做完 → 拒绝（事在子卡手里，重派父卡不会推进任何事）；
- 真有一趟 Run 在跑 → 默认拒绝，并告诉你是哪一趟、跑了多少分钟；**看清楚再「强制重派」**；
- `force` 打断时：把那一趟在库里判成 `interrupted`，并审计 `run_interrupted_by_redispatch`；
  那一趟以后要是还回来了，`wake()` 只会关「自己开的那一趟」（`WHERE status='running'`），
  `handleResult` 也会把它丢掉并记 `run_result_after_abandon` —— **不许把迟到的结论写回状态机**；
- 已经排着一条没消费的派活事件时不再叠一条（连点两下不会排出两趟）。

### ③ GUI 锁跟着死掉的 Run 一起放（`recoverOrphanRuns`）

同一个事故里还埋着第二个坑：引擎重启后 `R-387d746b` 已按中断收账，但 `gui.lock` 里仍写着
「GUI 正被 R-387d746b 占用」，而锁的 stale 保护是 **30 分钟**。
于是重启后每一次派活都被 `env_check_failed` 拦下 —— 人看到的是「点了重派，什么也没发生」。

现在 `recoverOrphanRuns` 收尸时顺带 `releaseGuiLockForRun()`：

- 只放「owner 就是这个死掉的 runId」的锁，别人的锁一律不碰；
- 记一行 `gui_lock_released_orphan`；
- 手动 `force` 重派打断那一趟时同样放锁，记 `gui_lock_released_redispatch`。

### 根因一（制度层）：提示词明确要求它「守着等」

`src/org-chart.js` 原来的原文：

- `【把卡拆给下级之后：总任务还在你手上】`
- `你不是交完就走。子卡一张张回来，你得逐张看结果`
- `派完不是收工：子卡回来先看结果（node scripts/seat.js reviews --as …）`

GUI 席位一次会话是独占的：它按这句话留在会话里「等子卡回来」，等于**把自己的执行槽按住不放**。
而下级要开工，恰恰需要这个槽空出来。于是它等的正是被它自己挡住的那条队列 ——
等不到 → 它判定「下级叫不起来」→ 取消子卡自己干。**制度与机制互相打架，这是主因。**

### 根因二（机械层）：事件泵串行，一次只能跑一趟

`pump()` 是「取一个事件 → `await handleEvent` → 再取下一个」，而 `handleEvent` 里的
`await wake()` 会一直等到整趟 GUI 会话结束（几分钟）。所以 `runPolicy.maxConcurrent: 2`
在 inline GUI 模式下**实际等于 1**：总经理在验收时，执行岗的派活事件只能排队。

### 改了什么

**① 制度重写（`src/org-chart.js`）** —— 把「守着等」改成「派完即交活」：

- 新段落标题：`【派完之后：立刻交活，会话到此结束】`
- `spawn` 返回子卡编号 = 活已派出；对方何时开工是引擎的事；
- 派完**立刻**写 `output/report.draft.json`（或 `completion.json`）然后结束会话；
- 交活时子卡未收尾 → 系统把父卡挂起（`waitingChildren=1`），这是正常流程，不是失败；
- 子卡全部收尾后系统自动拼 `output/总任务汇总.md` 送审，**那时才叫你来审**；
- 下级叫不起来 → `reportUpward` 交上级查，**不是取消子卡的理由**。
- `delegationBriefing` 里同步写成三步 SOP：① `spawn` 拿编号 → ② 立刻交活 → ③ 结束会话。

**② 硬闸：发布者不许作废自己的子卡（`engine.cancelTask`）**

```
cancel_child_rejected / PARENT_CANNOT_CANCEL
```

发布者（父卡承接人）调用取消 → 拒绝并留账；上级或董事会取消仍然可以。
「作废」是治理动作，不是执行动作 —— 这正是它上次绕过流程的那一步。

**③ 机械兜底：父卡占着会话干等就把它收掉（`reconcile` 新段）**

新增 `runPolicy.parentWaitMinutes`（代码默认 0 = 关，公司档 8 分钟）：

- 父卡有未收尾子卡、`waitingChildren=0`、却还挂着一趟超过 8 分钟的 `running`；
- → 那趟 Run 判 `interrupted` + 放 GUI 锁 + `waitingChildren=1` + 审计 `parent_wait_cut`；
- 子卡随即被补投唤醒，父卡在子卡收尾后自动汇总送审。

**④ 配置**：`src/config.js` / `config/company.schema.json` / `config/company.prod.yaml`
同步 `parentWaitMinutes: 8`。

### 已知限制（写清，不假装解决）

泵仍是串行的：一趟 GUI 会话在跑时，别的席位的派活事件只能排队。
所以现在最多做到「父卡派完立刻收工 → 子卡紧接着一张张跑」，**不是真并行**；
`maxConcurrent: 2` 对 inline GUI 仍等于 1。

要真并行只有一条路：把「执行」从「消费事件」里解耦成后台 Run（每席位 1 并发 + 全局计数）。
那会改动 `pump` 的语义，现有一批测试依赖「提交完就同步看到结果」，回归面很大 ——
本轮**没有做**。等出现「两摊活确实需要同时开」的真实场景再动，届时要单独一轮回归。

## 九、验收归属（23:40）：中层派的活，验收到中层手上，不是一分钟后摆到 CEO 面前

### 现场判断

读代码时发现这条链路是**结构性**走偏，不是偶发：子卡交活后（`handleResult` ④），
验收人是中层时只写一条 `review_queued` 就撒手；中层是拉模式（`pull` 语义），
**没有任何东西会叫醒它**。而心跳补审（`reconcile` ②）里写死了一句：

```js
emitEvent({ type: 'review_requested', ..., agentId: ceoId() })
```

不看真实验收人是谁。于是：子卡交活 60 秒后，「该工程岗审」的活就摆到了 CEO 面前。
中层名义上是审查人、实际从没审过；CEO 每张子卡都要跑一轮验收 run —— 这是额度被吃掉的来源之一。

### 改动（4 处）

**① 交活时就把验收请求发给真审查人**（`handleResult` ④ 末端）

```js
emitEvent({ type: 'review_requested', taskId, agentId: reviewer,
  payload: { wakeReason: 'review_requested', kind, asReviewer: true },
  dedupeKey: `review-seat:${taskId}:${runId}` });
```

不再等心跳、也不再默认交给 CEO。

**② 被叫醒的中层跑的是「验收会话」，不是「干活」**（新 `reviewerBriefing` + `ctx.briefing` 拼接）

`src/org-chart.js` 新增 `reviewerBriefing()`：这次叫醒你是因为卡 X 由 Y 做完交上来了，
你是审查人；产出不是代码、不是重做，而是一个结论；审法、`seat.js reviews` / `verdict` 两条命令、
打回必须写清要改什么、审完把结论也写进报告保证会话正常收尾。
`src/engine.js` 在 `wakeReason='review_requested'` 且 `agentId !== ceo` 时把这段拼到 `ctx.briefing` 后面，
并给 `ctx.review = { asReviewer: true, taskId }` 供 adapter 识别。

**③ 结论有两条合法来路，引擎不替它判**（新 `seatReview()`）

- 会话里执行 `seat.js verdict` → 走 `reviewTask` 已落库，这趟回来时卡已不在 `in_review`（审计 `seat_review_settled`）；
- 报告里给 `verdict: pass|reject` → 引擎补调 `reviewTask`（审计 `seat_review_verdict`）；
- 两条都没有 = 跑完没结论 → **不猜、不替它判**，卡留 `in_review`（审计 `seat_review_no_verdict`），心跳继续兜底。

**④ 补审按真实审查人分流**（`reconcile` ②）

| 真实审查人 | 补审发给谁 |
|---|---|
| 董事会（人） | **不补**（审批单已经出了，agent 不许代审；审计 `review_skip_human`） |
| 中层 | 先叫中层；超过 `runPolicy.seatReviewFallbackMinutes`（生产 20 分钟）才转 CEO，并留 `review_fallback_ceo` 账 |
| CEO | 照旧（1 分钟粒度） |

席位不是人喊就到的：发给中层的补审按 **5 分钟**粒度去重（CEO 仍 1 分钟），避免每分钟刷一条空账。

**⑤ 顺带堵掉「人审卡被 agent 代审」**：`handleEvent('review_requested')` 开头先看库里真实审查人，
是 `human` 就直接 `review_skip_human` 返回 —— 以前人还没点，CEO 那一轮验收可能已经把卡判过了，
审批单还挂着没人收。这一条和 ④ 在同一处，属于同一类越权，一并处理。

### 配置

`runPolicy.seatReviewFallbackMinutes`：代码默认 **0**（= 不等待，保持老配置/老测试语义，补审仍归 CEO）；
`config/company.schema.json` 加 integer ≥ 0；`config/company.prod.yaml` 写 **20 分钟**。
重启后实测加载：`seatReviewFallbackMinutes: 20`（`parentWaitMinutes: 8`、`stuckMinutes: 30` 不变）。

  S3 中层跑完没给结论 → 不替它判、卡留待验收；

1. 中层被叫起来审的这趟 run 挂在**子卡**上（`agentId=engineering`、`taskId=子卡`），看板上表现为

## 十、制度回执（2026-11-18）：CEO 提的排班单，不许「说了没做」

### 现场（`T-51a0595b`）

董事会下单「没有给自媒体工作台配置定期维护计划吗？要配制哦，按月度」。CEO 跑完 `R-5eb652aa` 后，库里是这样的：

| 时间 | 审计 | 含义 |
|---|---|---|
| 16:12:09.465 | `recurring_suggestion_rejected`：`自媒体工作台：每月项目体检…｜reviewBy 不可用：不能让自己审自己（engineering）` | 它把执行人和审查人都写成了工程岗 |
| 16:12:09.468 | `tasks_created`：**0 张** | 什么都没派 |
| 16:12:09.472 | 卡 `in_review → done`；看板消息 `MSG-70fb1439` 标题「**完成**：没有给自媒体工作台配置定期维护计划吗…」 | 董事会看到的是一条「已完成」 |
| — | `recurring_jobs` 只有 2 条 demo-editor 旧计划 | **工作台那条根本没注册** |

四个问题叠在一起：

1. **规则本身对，拒绝方式错**：不能自己审自己是对的；但撞车的正确动作是「往上抬一级」，不是「把整条建议扔掉」。
2. **拒绝不回执**：只写一条审计，CEO 下一轮拿不到任何原因，自然以为办成了。
3. **同一类事两套脾气**：报告不合格 → `report_rejected` → 自动重投（≤2 次）→ blocked+上报；排班建议不合格 → 静默丢弃。报告有回执，排班没有。
4. **零落地也标完成**：`tasks_created: 0` 照样走 `in_review → done`，消息模板还写「完成：…」「你不用管，这件事已经办完」。

### 改了什么（结构性，一步到位）

**① 审查人撞车 → 自动上升，不再拒单**（`resolveCycleReviewer`，`src/engine.js`）

- CEO 只定三件事：**这活是什么、多久一次、谁来干**（`assignee`）。`reviewBy` 变成可选、不推荐；
- 不写 → 引擎按「执行人的上级」推（日常活落到工程岗）；
- 写了且撞到执行人自己 → 取它的 `reportsTo`；再撞 → `human`（董事会）；审计 `review_by_escalated` 写明 `doubao→engineering`；
- 撞车不再 `throw`，所以「执行人和审查人同一个」这种写法不会再把整条建议废掉。

**② 校验跑在动手之前，拒绝变成回执 + 重投**（`planRecurringApprovals` / `commitRecurringApprovals` / `feedbackRuleViolation`）

- 拆成两段：**纯校验**（可重复调用，不加任何副作用）+ **提交**（写审批单）。原来「边校验边写」的版本会写出半截单，重试还会重复建卡；
- 任何一处不合规 → **整轮什么都不落**（0 卡 / 0 单），发 `issue_assigned` 带 `reviewNote` 回执，重新唤醒**同一个** agent；
- 回执必带三样：违反哪条（code）、为什么（撞了谁/缺什么）、**正确写法**（能照抄的 JSON 示例，执行人取公司里真有的执行席位，不写死产品名）；
- 上限 **2 次**，第 3 次 `blocked` + 沿汇报线上报；CEO 的上级是董事会 → `escalateTask` 把「自己」映射成 `human`（原来会 `ceo→ceo` 上报给自己，自己叫自己）；
- 同时删掉了 `softRoute`（`route_field_rejected`）：`reviewBy` / `handoff` 写错不再「留痕后当没写」，同样进回执；
- 删掉死代码 `requestRecurringApprovals`（定义了从未被调用，活的实现是 CEO 分支里的内联副本）。现在只有一套实现。

**③ 零落地不许标「完成」**

- 一轮结束算「落地件数」= 新卡 + 新审批单（项目/排班/战略门禁）；
- `= 0` 但有回话 → 走 `closeAsReport`，消息是「**总经理回复：…**」（kind=`answer`），并留审计 `ceo_no_delivery`；
- `= 0` 且连回话都没有 → 按违规回执重投（`empty_round`），不许静默收工；
- 合规轮次把 `attempt` 清零，避免一次小磕碰拖累下一单。

**④ 提示词补四条硬规矩**（`src/adapter-webhook-exec.js` + `src/org-chart.js`）

1. 排班你有「提」的权、没有「直接排」的权；
2. 日常运维 / 体检 / 清理的执行人写下级席位，**不要点自己**；
3. **审的人不用你写**，引擎按执行人的上级自动定，撞车自动抬级；
4. **只有拿到 `AP-xxx` / `JOB-xxx` 回执才能说「已经安排好了」**；被引擎打回时按回执改，不许声称已办成；
5. 被打回时，`ctx.task.reviewNote` 会以「【这一轮是打回重做】+ 引擎原话」的形式放在提示词最前面——原来这里什么都没传，CEO 被重新叫起来看到的还是同一张卡，只能瞎猜。
