# 证据层：有证据的 running（L1 / L2 / L3）

> 2026-11-18 · 董事会口径：执行 1 小时、验收 30 分钟；GUI 证据取轻量；ack 不强制，只体现为「少给耐心、多给怀疑」。
> 测试全部用模拟席位（不派真活），逻辑跑通后再由董事会亲自下单实测。

## 一、要解决的老毛病

以前引擎只有一个判断：「`runs.status = running` 就当他一直真在干活」。于是下面这些事全都伪装成「干活中」：

- 提示词粘歪了 / 根本没按回车 → 没有 agent 收到活；
- 窗口没激活、焦点被抢 → adapter 一直重试，但卡永远不落地；
- agent 半路停下来「想跟董事会确认」 → 会话不结束，run 一直挂着；
- agent 回了一句「正在处理」然后什么都没写。

后果都一样：并发名额被占、验收补审让路、看板显示「干活中」，直到 2 小时僵死收尸才有人知道 —— 这中间没有任何人收到消息。

现在的原则：**不看 agent 说了什么，只看盘上留下了什么。缺证据不判死，只缩短耐心；探不到证据就重派，重派用尽就向上收束。**

## 二、证据分级（四把尺子）

| 级别 | 名称 | 判据（全部是本地文件观测，零 token、零模型调用） |
|---|---|---|
| L0 | 无 | 只有引擎自己的账，盘上什么都没有 |
| L1 | 已启动 | `tasks/<taskId>/dispatch.json` 且 `runId` 对得上（由 adapter 在进程/窗口真的起来之后写）。**只证明席位被拉起来，不证明 agent 收到或开工** |
| L2 | 在动 | `ack.md`（agent 改过的那一行）/ `progress.json` / `output/**` 非空文件 / 项目交付目录（`projects.<id>.rootDir`，2026-11-24 补）/ `report.draft.json`，任一 mtime 晚于本趟 run 的 `startedAt` |
| L3 | 已交活 | 本轮已写 `completion.json` 或 `report.draft.json` |

配套文件：

- `dispatch.json`：adapter 写。GUI = 按下回车且 `driver.send` 成功之后；webhook = 服务端返回 `ok=true` 之后；process = 子进程真的拉起来之后。
- `run-heartbeat.json`：adapter 轮询期的心跳（GUI 每 6 次轮询 ≈ 30 秒）。只证明「机器还活着」，**不算** agent 产出。
- `ack.md`：派单时由控制面预置一行 `收到｜预计 ? 分钟｜我的理解：?`。agent 改这一行就算回执；**没改不算回执**（模板本身不给耐心）。
- 所有证据都按 `runId` / `startedAt` 归属：上一轮残留的报告、草稿、回执一律不算本轮（沿用 T-906d3686 的防线）。

## 三、三阶处置（L1 → L2 → L3）

### L1 启动确认

- `ackTimeoutSec`（生产 120 秒）内没有 `dispatch.json` → 判「没启动」，而不是「干得慢」。
- 动作：中断这趟 run（`interrupted` + `interruptedReason`），释放 GUI 锁，把卡放回 `todo`，补一条 `issue_assigned`（`wakeReason=redispatch`），审计 `redispatch_no_dispatch`。
- 拉模式席位（`dispatch: pull`）直接跳过：它们本来就没有「引擎启动回执」这回事，不能被启动超时误杀。
- 闸门拦下（`gate_blocked` / `deferred`）不算送达失败：那种情况 run 很快就结束并回 `todo`，由闸门重试链负责，不走证据层。

### L2 活动证据

- 已启动之后看 agent 侧痕迹。耐心口径 **2026-11-19 已改**：不再按「有没有 ack」减半（见第 10.1 节），
  改为按席位预算给 —— 有预算的给到预算一半（最多 2×`idleTimeoutSec`），没预算的退回 `idleTimeoutSec`（生产 15 分钟）。
- 到点先**探一次盘**（就是上面的 L1–L3 探测）。探到任何新鲜痕迹 → 继续等，不打扰。
- 仍然什么都没有 → 中断重派，审计 `redispatch_no_evidence`；同一张卡的重派额度由 `maxDispatchAttempts` 控制（生产 2 次，含首次）。

### L3 升级闭环

- 重派额度用尽 → 不再自动重试，走 `reportUpward`：先中断最后一趟假跑的 run（不占并发、不再显示「干活中」），再给汇报线上的上级 agent 开一张**处置卡**（`role=escalation`），带证据包：
  - 证据级别 / 证据种类 / 引擎判定原话 / 机器心跳与产物情况；
  - 执行卡同时置为 `blocked`（等上级处置），避免常规补投每分钟又派一次；
  - 验收卡保持 `in_review`（验收动作只认这个状态），并暂停自动补审，等上级给结论；
  - 二选一：按证据**代验收**并收束，或打回重做；
  - 验收卡额外写明合法出口：`node scripts/seat.js verdict --as <agentId> --task <id> --pass|--reject --reason "…"`；
  - 底线两条：上级不许自己重做这张卡的活；处置卡必须给出明确结论，不许停在原地。
- 处置卡收尾后由 `resumeParentAfterEscalation` 把原卡救活（最多 2 次）；再走不完就继续往上一层报，汇报线到顶才出人工审批单 —— 这是唯一允许「停下来等人」的地方。

## 四、参数（生产口径）

`config/company.prod.yaml → runPolicy`：

```yaml
evidenceEnabled: true
ackTimeoutSec: 120        # 2 分钟没启动回执 → 判没启动
idleTimeoutSec: 900       # 15 分钟没产出痕迹（没 ack 则 7.5 分钟）→ 中断重派
maxDispatchAttempts: 2    # 含首次；用尽 → 开处置卡
seatReviewFallbackMinutes: 40
```

席位预算：

- `doubao`（执行）：`maxMinutes: 60`
- `engineering`（工程执行，兼验收）：`maxMinutes: 60`、`reviewMaxMinutes: 30`

`reviewMaxMinutes` 只在验收轮生效（`ctx.review.asReviewer`），执行轮仍用 `maxMinutes`；没配就退回 `maxMinutes`，老配置行为不变。

## 五、与既有机制的关系

| 机制 | 关系 |
|---|---|
| 僵死 run 收尸（`maxRunHours` 2h） | 最后一道硬上限；证据层在它之前就把假跑的 run 收掉，不用等 2 小时 |
| 卡住看门狗（`stuckMinutes` 30） | 管**卡状态**（blocked / awaiting_decision / 叫不醒的 todo）；证据层管**run 是否真在跑**，两者互补 |
| 验收补审 | 证据层先把假跑的验收 run 收掉，补审才不会一直「有 run 在跑 → 让路」 |
| 父子互卡（`parentWaitMinutes`） | 不变：父卡派完子卡还占会话，照样按中断收账 |
| 桥接（`bridge.enabled: false`） | 不变：停用但代码保留；`/api/bridge/review` 是验收结论唯一落库通道，仍放行 |

## 六、看板上的证据徽标

任务卡「状态」列的第二行直接显示证据级别，不用再去翻库：

| 徽标 | 含义 |
|---|---|
| 未派单 | 卡在排队，还没跑过任何一趟 |
| 未见回执 · 已等 N 分 | 已派出但系统没观测到启动回执（满 2 分钟会被中断重派） |
| 已启动 · 等开工 | 进程/窗口起来了（dispatch.json 或心跳有），agent 还没写出任何东西 |
| 已启动 · 未开工 N 分 | 同上但已超过 5 分钟仍无产出痕迹：标黄，多半卡在授权/等模型/空转 |
| 已收到 · 回执 | agent 改了 `ack.md`（只回了收到，还没有产物） |
| 有进度 · 产物 / 进度 | 有新鲜产物或进度文件，附最近活动时间 |
| 已交活 · 报告 / 草稿 | 本轮已写出可验收的交付物 |
| 没启动 · 已中断 / 无产出 · 已中断 | 被证据层收账的那一趟，卡片通常已回到排队或被上级接手 |

颜色：绿=已交活，蓝=在动，黄=可疑或中断。历史卡（done / cancelled）不显示徽标，避免满屏噪音。

2026-11-24 用词修正：L1 一律叫「已启动」，不再叫「已送达」——CLI（process）席位的
dispatch.json 只证明进程被拉起来了，agent 可能一直没开工（真机 T-5457e8a0：显示「已送达」，
实际 10 分钟 CPU 一动不动、产物一个字没写）。「收到」只能由 ack 证明，「有进度」只能由产物证明。
接口零新增：全部来自 `/api/runs` 已有字段。

## 八、运维口径

- 看某张卡最近的证据：查 `runs` 表 `evidenceLevel / evidenceKinds / lastActivityAt / dispatchConfirmedAt / ackAt / interruptedReason`，以及审计 `redispatch_no_dispatch / redispatch_no_evidence / evidence_escalated / evidence_watch`。
- 证据层只读盘：不需要额外进程、不需要截图、不消耗模型额度。
- 关掉证据层：`runPolicy.evidenceEnabled: false`（默认就是关），行为完全回到老版本。
- 改 `src/*.js` / `config/*` 需重启：`npm run win:stop` → `npm run win:start`；只改 `board.html` 即时生效。

## 九、已知边界（如实写）

- 证据只能证明「有东西在写」和「写到了哪一级」，不能证明「写得好不好」；质量仍由验收方判断。
- GUI 证据是轻量的（回执 / 文件 mtime / 心跳），不做定时截图差分：截图只作最后仲裁，避免 CPU 与噪声成本。
- 进程型席位（`process`）没有轮询心跳，但会有启动回执 + 产物文件；若活本身不产出文件，会被判「无证据」——这类席位应在提示词里要求写 `progress.json` 或产物。
- 证据层不会替 agent 决定「该不该向上确认」；它只保证**卡不会因为 agent 停下来等人而永远不动**。

## 十、2026-11-19 心跳续命（真机误伤后补）

**现场**（`T-6493fc51`）：执行席位这趟 `dispatch✓ heartbeat✓`、`ack✗ activity✗`，7.9 分钟没写 progress，
被按「无 ack 耐心减半 = 7.5 分钟」中断重派；重派的那一趟 **3 分钟就干完了** —— 说明第一趟本来就在干，
只是没写盘。看门狗比干活的人还不耐烦。

**根因两条**：

1. `probeRun` 的 `activityCandidates` 只算 `ack / progress / 产物 / report.draft`，心跳不参与 →
   一直「没产出」；
2. `machineAt` 曾经回退到 `dispatchAt`（送达时间），而送达是一次性事件，不能当持续心跳；
   反过来若不回退，又会让「只有心跳」这种情况被判成死。

**修法（结构性）**：

| 点 | 规则 |
|---|---|
| 活体判据 | 只认 `run-heartbeat.json`（`probe.heartbeatAt`），`dispatch.json` 不再算心跳；`machineAt` 只留作审计展示 |
| 心跳新鲜 | `heartbeatGraceSec`（默认 180s）内 → **不重派**，每趟只写一条 `stall_wait_heartbeat` 审计 |
| 封顶 | 席位自己承诺的 `adapter.config.maxMinutes` + `seatBudgetSlackSec`（默认 300s）都没产出 → 直接收掉 + 向上收束（`evidence_escalated`），**不再重派**（再派一次只会再失控） |
| 心跳也没了 | 回到老逻辑：探不到证据就重派；额度用尽仍按 L3 升级 |

**为什么心跳不抬证据等级**：心跳只证明「这一趟还在 adapter 的轮询里、窗口还开着」，
不证明「agent 在写盘」。所以它只用来**推迟重派**，`evidenceLevel` 仍然是 1。

**测试**：`tests/evidence.test.js` 新增三条 ——
L2b（心跳新鲜 → 不重派 + 留一条 `stall_wait_heartbeat`）、
L2c（心跳过期 → 照旧重派）、
L2d（心跳在但跑穿 `maxMinutes` → 不重派、收 run、向上收束且汇报方向是 `doubao→engineering`）。
专项 7/7，全量 **453/453**。

**配置**：`runPolicy.heartbeatGraceSec` / `runPolicy.seatBudgetSlackSec`（schema + `company.prod.yaml` 均带注释）。

### 10.1 二次修正（同日）：耐心不再按「有没有 ack」打折

用户复核后指出：一个一小时的活，7.5 分钟就掀翻太激进 —— 接入的模型 / 工具 / 运营商各不相同，
七八分钟可能才把文件读完，还没来得及动手；而且 adapter 在等一次长模型回复时本来就不写心跳，
3 分钟判「心跳没了」等于逼它秒回。

改两处：

| 点 | 旧 | 新 |
|---|---|---|
| 耐心口径 | 有 ack 给 `idleTimeoutSec`；没 ack **减半**（900s → 7.5 分钟） | 不再看 ack。有预算的席位：`max(idleTimeoutSec, min(预算/2, 2×idleTimeoutSec))`；没预算的席位：`idleTimeoutSec`。GUI 席位（60 分钟预算）实际耐心 **30 分钟** |
| 心跳宽限 | `heartbeatGraceSec: 180` | `600`（10 分钟）：长模型回复期间心跳本来就是空的 |

判断优先级不变：心跳新鲜 → 继续等；跑穿 `maxMinutes + 300s` 仍无产出 → 收掉并向上收束；
心跳也没了且过了耐心 → 重派（额度用尽照旧升级）。

新增用例 `L2e`：一小时预算、没有心跳也没有 ack —— 25 分钟不动它、35 分钟才重派。
专项 **8/8**，全量 **454/454**；控制面已重启（23:25:55），线上值 `idleTimeoutSec=900 / heartbeatGraceSec=600 / seatBudgetSlackSec=300`。
