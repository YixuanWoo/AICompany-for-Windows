# 总任务收束：父卡、子卡、谁向谁交账

> 2026-11-16 董事会问：「CEO 给我派一张总卡，我拆 8 张给豆包，豆包做完我审 8 张、
> 8 张全完成 = 总任务完成。按这个原则，我是不是也会给 CEO 写一份汇报，最终收束到 CEO 手里？」
>
> 答案：**是，而且现在代码里真的这么跑。** 这之前是断的 —— 父卡拆完就被当成「已完成」送审，
> 而子卡一张都还没动。本文记录这条链和补上的那一节。

## 一、一句话概括

**谁发布，谁验收；谁验收，谁向董事会汇报。**
子卡是「活」，父卡是「这一摊活的总账」。总账只在子卡全部收尾后才出现。

## 二、整条链（以「CEO 派总卡 → 工程拆 8 张 → 豆包做」为例）

```
董事会 ──① 提需求──▶ 总经理（CEO 的请求卡）
                        │
                       ② 拆一张「总卡」交给工程岗（publish = ceo）
                        ▼
                    工程岗（父卡，承接人）
                        │
                       ③ 再拆 8 张子卡给豆包（spawn，publish = engineering）
                        ▼
                豆包 1..8（子卡）
                        │
                       ④ 每张交活 → 回工程岗审（谁发布谁审）
                        ▼
              子卡逐个 done（终态）
                        │
                       ⑤ 最后一张收尾 → 父卡自动收束
                        │   · 拼总汇报 output/总任务汇总.md
                        │   · 父卡 in_review，交 CEO 验收
                        ▼
                    总经理（CEO）
                        │
                       ⑥ 验收通过 → 父卡 done
                        ▼
              消息区：一条「总经理汇报：xxx」（署名 CEO）
```

## 三、三个关键时刻的规则

### ① 拆完卡就交活 —— 会被挂住，不送审

父卡承接人（工程岗）把卡拆给下级后交活，此时它交上来的只是**拆解方案**，
不是总任务的结果。引擎的处理：

- 父卡留在 `in_progress`，打上 `waitingChildren = 1`；
- 写好「拆解方案」原件备份，不产生任何验收请求；
- 审计记 `parent_waiting_children`（看板据此显示「等子卡：3/8 已收尾」）。

> 没有这一道闸：CEO 会在 8 张子卡一张都没动的时候，收到一张写着
> 「我拆了 8 张」的完成报告，点通过后总任务显示「完成」——而活根本没干。

### ② 最后一张子卡收尾 —— 父卡自动收束

触发点：子卡到达 `done` / `blocked` / `cancelled`（都算收尾）。

- CAS 抢位（`waitingChildren 1 → 0`），保证多张子卡同时收尾时只出一份总汇报；
- 汇总每张子卡的「标题｜状态｜谁做的｜一句话结论」；
- 落 `output/总任务汇总.md`，并把父卡的 `completion.json` 改成总汇报
  （原拆解说明备份为 `completion.plan.json`）；
- 父卡 `in_review`，按**父卡自己的发布者**路由：
  - 发布者是 CEO → 叫 CEO 验收（`review_requested`）；
  - 发布者是董事会且要求亲审 → 出待拍板单；
  - 发布者明确落盘（董事会直投 / `handoff: land`）→ 直接 done，不叫人。
- 有子卡没成（blocked / cancelled）也照样收束，但总汇报里如实写「N 张没成」，不拿完成数糊过去。

### ③ 验收通过 —— 由验收人向董事会汇报

父卡 done 时，消息区那条消息**署名验收人**：

- CEO 验的 → `总经理汇报：xxx 已办结`，正文「这摊活办完了，8 张子卡全部收尾……」；
- 董事会自己点的 → `总任务收束：xxx`，走「你点通过了」。

不是署名工程岗：干活的人自说自话，董事会看不出「这单是谁背的」。

## 四、两种发布者的差别（回顾「谁发布谁审计」）

| 谁发布父卡 | 子卡齐了之后 | 董事会消息 |
|---|---|---|
| 董事会直投（`handoff` 默认 land） | 直接落盘，父卡 done | 总任务收束（署名干活的人） |
| 董事会明确「给我审」 | 出待拍板单 | 你点通过了 |
| 总经理派给工程岗 | 父卡交 CEO 验收，通过才 done | 总经理汇报（署名 CEO） |
| 总经理在卡上写 `handoff: land` | 直接 done | 总任务收束 |

## 五、看板与提示词

- 看板任务列表：父卡停着时显示「等子卡：3/8 已收尾」，不用点进去猜；
- 工程岗提示词：新增「把卡拆给下级之后：总任务还在你手上」，明确「拆完就交会被挂住」；
- 总经理提示词：新增「你派的卡被继续拆时，回到你面前的是整件事的结果，不是他排了哪些工」；
- CEO 验收提示词：多一句「这张卡下面拆过子卡的话，先看 output/总任务汇总.md」。

## 六、边界与已知副作用

1. **子卡审查人是拉模式席位（工程岗）时，子卡会停在 `in_review` 等人叫醒。**
   整条链的节拍器因此是「董事会叫一声工程岗」。父卡收束本身不需要人，但子卡逐张审需要。
   缓解：看板 `holdReasons` 会显示排队原因；循环卡排队时有消息提醒。
2. **父卡收束固定按 document 路由。** 子卡里的代码各自走过代码审查，父卡收的是总账，
   不再二次触发「受管代码必须挂仓库」。
3. **blocked 也算收尾。** 一张子卡被救回来后，父卡不会重新挂起（它已经交审了），
   救回来的那张会单独再报一次。
4. 父卡重新拆新子卡：仅当它被打回 `in_progress` 后再交活时，会按新一轮子卡重新挂起。

## 七、验证

`tests/parent-child.test.js` 四条：

- C1 子卡没干完就交父卡 → 挂起、`waitingChildren=1`、不叫 CEO；
- C2 子卡全部收尾 → 父卡 in_review、总汇报落盘、CEO 通过后 done、消息署名 CEO；
- C3 一张子卡取消 → 照样收束，总汇报写明「1 张没成」；
- C4 董事会直投的总卡 → 子卡齐了直接落盘，不惊动 CEO。

全量 **360/360**。
